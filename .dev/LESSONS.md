# Уроки проекта — bervel

Записывать только проверенные устойчивые выводы.

## 2026-10-16 — Docker и восстановление

- Для shell-скриптов первой инициализации PostgreSQL закреплять `eol=lf` в `.gitattributes`: локальный успешный запуск не доказывает работоспособность свежего Windows checkout с CRLF.
- БД n8n переносится вместе с прежним ключом шифрования. До первой записи при восстановлении проверять ключ, все дампы, пустоту всех целей и контрольные суммы оригиналов. Отдельная проверка восстановления приложения должна читать данные через установленный API в изолированной БД и volume.
- На Windows завершение родительского `docker.exe` само по себе не завершает дочерний `docker-compose.exe`. Проверочный Watch-процесс завершать вместе с принадлежащим ему деревом процессов; не оставлять скрытое наблюдение после теста.
- Linux-браузер с API, использующим `crypto.randomUUID`, требует secure context. Проверенный стенд использует localhost в сетевом пространстве тестового frontend и не отключает browser security.
- Readiness PostgreSQL для зависимых контейнеров проверять по TCP: временный сервер первой инициализации может отвечать через Unix socket раньше готовности основного сервера к сетевым подключениям.

## 2026-10-14 — хранение и учебный CSV этапа 3.1

- Неизменяемость пары ID/версия схемы недостаточна: URI `$id` тоже должен быть уникален. Коллизия могла изменить разрешение ссылок и ослабить проверку прежних данных.
- Составной ответ истории проверяет права на все возвращаемые виды данных: чтение оригинала само по себе не разрешает выдачу конвертов результатов.
- Общую квоту тела и ключ доступа проверять до multipart-разбора. Ошибка из receive внутри парсера может превратиться в общий HTTP 400; ранняя граница возвращает явный 413.
- Граница `.dev → приложение` подтверждается запуском установленного wheel из пустого cwd, а не только поиском импортов в исходниках. Проверка выполнена для учебного этапа; полная переносимость окружения проверяется отдельно.

## 2026-10-14 — ручное восстановление n8n

- Родитель после успешного повтора остался crashed, со ссылкой retrySuccessId; список ошибок без учёта дочерних попыток не является очередью необходимых восстановлений. Два одновременных запроса повторили уже восстановленного родителя и создали два новых исполнения. Защита команды и эффекта нужна в ядре.
- Повтор исходной схемы после публикации новой сохранил v1, а новые запуски использовали v2. Повтор с текущей сохранённой схемой изменил тело под старым ключом и был отклонён приёмником. Такое отклонение не означает, что n8n сам проверяет идемпотентность. Доказательства — docs/quality/core-stage-2-n8n-manual-report.md. После этих испытаний владелец принял профиль для разработки v0.1 в ADR-0002; защита ядра ещё не реализована, эксплуатационные условия остаются открытыми.

## 2026-10-14 — первый эксперимент движка процессов

- Ответ readiness n8n не доказал готовность worker и webhook; измерительный стенд должен дождаться фактического старта этих компонентов. Повтор webhook запуска создал отдельное исполнение, поэтому идемпотентность команды остаётся ответственностью ядра.
- В n8n 2.43.5 проверенный аварийный worker оставил исполнение crashed без автоматического продолжения; штатный ручной retry завершил его. Защиту повторного эффекта обеспечил приёмник. Различать эти гарантии и не выдавать ручное восстановление за автоматическое.
- Импорт назначил версиям n8n новые ID; CLI-публикация дала расхождение текущего и исполняемого опубликованного указателей. Публикация через API корректно разделила v1/v2. Эти наблюдения ограничены испытанным выпуском/профилем; решение DEC-02 остаётся открытым. Доказательства — docs/quality/core-stage-2-n8n-report.md.

## 2026-10-14 — граница .dev

- Пользователь закрепил .dev как место всех материалов разработки, не необходимых самому приложению: спецификаций, документации, тестов, примеров и инструментов. Зависимости разрешены только из .dev к приложению; сборка, установка и работа приложения не должны требовать .dev.
- Исполняемые схемы, миграции, ресурсы и настройки приложения хранятся вне .dev. Примеры контрактов из спецификации не подменяют файлы приложения. Проверка независимости будет выполнена после появления продуктового кода.

## 2026-10-14 — стандартизированное хранилище

- По выбору владельца разработки единообразными являются происхождение, редакции, доступ и конверт результатов; предметные поля проверяются собственными схемами. Расширение формата не означает отказа от предметных таблиц и миграций.
- Загруженная складская выгрузка и действующий остаток — разные данные. Извлечённый результат становится предметным источником только через публикацию владеющим компонентом; одновременно редактируемые дубли источника истины не создаются.

## 2026-10-06

- В КП есть ядро, радар и пресейл, а поздний опросник посвящён ядру и радару. Это требует подтверждения объёма; само по себе не доказывает ни включение, ни отмену пресейла.
- Вопрос, уже заданный в опроснике, не является новым пробелом. Дополнительный запрос отделяет новые вопросы от уточнений и условных блоков.
- Отметка «получено» в опроснике не даёт разработчику сами файлы. Наличие и качество данных проверяются по доступным образцам.
- Сопоставление каталога, допустимость замены, изготовимость и срок выполнения — разные предметные решения.
- Подготовленные сценарии проверки и успешная проверка ссылок не означают, что продукт реализован или испытан.

## 2026-10-15 — браузерная загрузка CSV

- Для проверки повтора после потери ответа важно сначала дождаться реального ответа API и commit, затем оборвать ответ на пути к браузеру. Успешный повтор проверять по прежнему ID и числу наборов/строк в PostgreSQL, а не только по сообщению страницы.
- В текущем Windows/Edge-окружении при параллельном запуске трёх браузерных наборов наблюдался timeout клавиатурного открытия filechooser. Последовательный запуск набора прошёл; в проверочном инструменте такие сценарии выполняются последовательно, без увеличения таймаута и изменений продуктового поведения.

## 2026-10-06 — полученный пакет заказчика

- Список из агрегатора, полный комплект закупочной документации и внутренние данные завода — три разных входа. Excel «Контур Закупок» содержит ссылки, но не технические позиции; ручной разрыв скачивания документации прямо назван заказчиком.
- Чужой AI-отчёт полезен как пример вида ответа, но не как первичная заявка или эталон производственных правил. В двух PDF и JPG найдены ошибки итогов; цветовая отметка не заменяет отдельные проверки соответствия, производства и срока.
- Состав болтокомплекта берётся из конкретного источника: в тендере одна шайба, в примере0168 соотношение количества соответствует двум. Перечень чертежей не доказывает наличие чертежа.
- Идентификатор, видимый текст Excel и URL — разные данные. Повтор номера с другим дедлайном не удалять без сопоставления; сумму по нескольким валютам и исторические результаты закупок не считать готовой экономикой или экспертной разметкой.

## 16 октября 2026 — версии n8n и согласованное чтение процессов

В n8n 2.43.5 native retry с `loadWorkflow=false` сохраняет исходный executable snapshot, но отдаёт `workflowVersionId=null`. Происхождение версии можно восстанавливать по `retryOf` только после точного сравнения сохранённых nodes/connections/settings и привязки входов; текущая опубликованная версия для этого непригодна. Подтверждение — живой N02 и тесты адаптера этапа 3.2.

При PostgreSQL READ COMMITTED два SELECT внутри одной транзакции могут читать разные снимки. Состояние процесса, результат и история попыток должны формироваться одним SQL statement; иначе API может показать RUNNING вместе с попыткой COMPLETED. Гонка воспроизведена барьером между чтениями, исправлена ordered JSONB aggregation. Источники и доказательства — `docs/quality/core-stage-3.2-report.md`.

### Реализован этап 3.2: процессы n8n, защита публикации и восстановление; объяснена текущая архитектура

Сессия: `01a14526-2188-7781-b557-64b2446818d1` · Ваня · Codex Desktop

Подтверждённая публикация результата PostgreSQL имеет приоритет над поздней сетевой ошибкой; состояние исполнения и качество данных различаются. Восстановление выполнять через API ядра, сохраняя резервирование попытки и защиту публикации.
