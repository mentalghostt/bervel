# n8n с ручным восстановлением для ядра v0.1

Владелец разработки 14 октября 2026 принял для ядра v0.1 n8n в режиме очередей, отдельные main/worker, PostgreSQL и Redis, ручное восстановление по исходной версии и обязательную защиту от дублей в ядре. Основание — явный ответ «Принять профиль n8n для ядра v0.1» в текущем диалоге после испытаний. Принято решение для разработки; промышленная эксплуатация и следующий продуктовый этап требуют отдельного согласования.

КП содержит n8n + Python. n8n сохраняет близость к предложенному решению и интеграциям. Temporal рассматривался как альтернатива, но не испытывался: после первой проверки пользователь выбрал продолжение n8n с ручным восстановлением. Два движка одновременно не вводятся.

Бизнес-правила и версии результатов остаются вне визуальной схемы конкретного оркестратора. См. [стек](../architecture/08-stack-deployment.md).

## Эксперимент от 14 октября 2026

Пользователь выбрал n8n для первого эксперимента. [Отчёт](../quality/core-stage-2-n8n-report.md) фиксирует сохранение ожидания, защиту от повторного ответа, штатный ручной повтор и корректную смену версий через API. Автоматическое продолжение после аварии worker не прошло; команда публикации CLI в проверенном выпуске дала расхождение текущего и опубликованного указателей. Защита от повторной команды запуска принадлежит ядру, а не проверенному webhook n8n.

По итогам первого эксперимента предлагалось сравнить Temporal либо отдельно рассмотреть ручное восстановление n8n. Тогда выбор оставался открытым; последующее исследование и приёмка описаны ниже. Два движка и собственный оркестратор не вводятся.

## Продолжение по выбору владельца разработки

Пользователь выбрал продолжить проверку n8n с ручным восстановлением. [Четыре дополнительных испытания](../quality/core-stage-2-n8n-manual-report.md) подтверждают обнаружение аварии, штатный повтор исходной версии после новой публикации и отказ изменённого эффекта по прежнему ключу. Два одновременных повтора старого аварийного исполнения создали два новых исполнения; единственность эффекта обеспечил приёмник, а не движок.

### Принятый профиль и его границы

Для ядра v0.1 выбран n8n в режиме очередей, отдельные main/worker, PostgreSQL и Redis, с явным ручным восстановлением аварийных исполнений. Повтор сохраняет исходную схему и входы. Уникальность команды восстановления, защита публикации, прослеживаемость попыток и согласование предметного действия принадлежат ядру. Автоматическое продолжение после аварии не обещается; второй оркестратор не создаётся. Эти гарантии ядра ещё предстоит реализовать и проверить.

Предлагаемый [регламент](../operations/n8n-manual-recovery.md) требует проверки уже успешных/активных попыток, неизменного ключа, версии и результата операции. Публикацию через проверенный API следует предпочесть испытанному неудачному пути Server CLI; стабильный программный контракт управления ещё требуется выбрать. Версия 2.43.5 — испытанный выпуск стенда; профиль промышленной поставки и версии сервисов отдельно подтверждаются.

Статус accepted относится к архитектуре разработки ядра v0.1. Детализация команды восстановления, прав и изменений состояния требует согласования до продуктовой реализации. Стабильный контракт адаптера, способ поставки, нагрузка, роли операторов, RPO/RTO и требования заказчика остаются открытыми. Развилка выбора движка для разработки в DEC-02 закрыта; клиентские эксплуатационные условия DEC-02 и оставшиеся проверки B06 не закрыты. Независимость приложения от Open Server Panel и `.dev` сохраняется.
