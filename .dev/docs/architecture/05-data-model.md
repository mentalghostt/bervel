# Модель данных и владение

Обновление28.10.2026: файловый контракт заменён моделью [отдельных неизменяемых файлов](25-independent-files.md), принятой в [ADR-0006](../adr/0006-independent-files.md). Описание редакций файлов ниже сохраняется как история; собственные редакции результатов, обращений и схем этим решением не отменяются. Статус установки указан в новом документе.

Статус: концептуальная модель. Схема физических таблиц и миграции будут определены после реальных образцов R12. Эти имена не являются уже существующей схемой 1С.

Полученный пакет уточняет требования к модели: [происхождение импортированных строк, комплект документов и уровни требований](11-data-sources-and-intake.md). Образцы внешних полей появились; внутренних выгрузок каталога/производства/цен ещё нет.

Уточнение от 14 октября 2026: [спецификация ядра v0.1](12-core-v0.1-spec.md) разделяет общие технические `ArtifactRevision`/`DatasetRevision` и предметные данные владельцев. Ядро владеет сохранением, редакциями и доступом; компонент документов — интерпретацией источника. Результаты хранятся по версионным схемам, а действующие каталог, остатки и бизнес-состояния — в предметных моделях. Извлечённый снимок не публикуется в них автоматически.

| Сущность | Владелец | Содержание и ограничения |
|---|---|---|
| SourceDocument / DocumentRevision | Документы — предметная роль; ядро — техническая ArtifactRevision | DocumentRevision ссылается на техническую редакцию и не создаёт второй оригинал; checksum, источник и доступ сохраняются |
| ImportBatch / SourceRecord | Адаптеры и импорт | Предлагаются: файл, схема, лист/строка, ID/URL источника, исходные значения, ошибки и статус сопоставления |
| PackageManifest | Документы | Предлагается: роли и версии документов дела, статусы получения, ссылки на отсутствующие приложения |
| EvidenceReference | Документы | Документ, страница/строка/область, исходный фрагмент; координаты появляются при обработке |
| RequirementLine / ProductSpec | Общий предметный слой | Внешние требования и нормализованные параметры; неизвестное не заменяется нулём |
| CatalogItem | Справочники | Внутренний ID и ID источника, параметры, актуальность |
| CapabilityProfile | Производственные знания | Подтверждённые условия выпуска, источник и эксперт |
| StandardMapping | Производственные знания | Пара стандартов/редакций, условия, исключения, утверждение |
| ReferenceSnapshot | Справочники | Набор версий исходных справочников, используемый анализом |
| PriceSnapshot / CapacitySnapshot | Экономические данные | Единицы, временная применимость, источник; используются только в нужном сценарии |
| MatchAssessment | Общий предметный слой | Кандидат, отдельные проверки, противоречия и неизвестное |
| EconomicCalculation | Экономика | Входы, методика и версия, результаты и ограничения |
| ProcessRun | Ядро | Модуль, версия процесса, состояние исполнения и корреляция |
| Approval | Ядро | Действие, редакция, проверяющий, решение и актуальность |
| ExternalAction | Ядро | Намерение, ключ, внешний ID, подтверждённый/неизвестный результат |
| Tender / TenderRevision / Lot | Радар | Идентичность источника, редакции, условия лота, дедлайн |
| TenderAssessment / ParticipationDecision | Радар | Анализ и отдельное решение сотрудника |
| CustomerRequest / Correspondence | Пресейл | Клиент, каналы, вложения и уточнения |
| OfferRevision / OfferLine | Пресейл | Коммерческие условия, ограничения и валидность конкретной редакции |

## Связи и правила

TenderRevision -> DocumentRevision -> RequirementLine -> MatchAssessment.
Анализ фиксирует ReferenceSnapshot и EconomicCalculation. Approval указывает конкретную редакцию анализа/предложения. ExternalAction ссылается на разрешившее действие и согласованные артефакты.

Один оригинал может встречаться в нескольких делах: совпадение checksum позволяет экономить хранение, но права доступа каждого дела проверяются отдельно. Нельзя сделать документ доступным другому пользователю только потому, что байты совпали.

Для исходных записей нужны origin_system, external_id и source_revision при наличии. Если стабильного ID нет, правило сопоставления создаётся после анализа образцов. Новое сопоставление не должно незаметно переписать старую историю.

## Разделение результатов

technical_match: MATCH / MISMATCH / UNKNOWN.
production_feasibility: CURRENT / NEEDS_TOOLING / NEEDS_NEW_PROCESS / UNKNOWN.
supply_method: OWN / PURCHASE / MIXED / UNKNOWN.
economics: PASSES_POLICY / FAILS_POLICY / INCOMPLETE.
human_decision: REVIEW / PARTICIPATE / DECLINE / CLARIFY.

Названия предварительные; смысл уточняется с заводом. UNKNOWN обязателен как отдельное состояние.

Доступность и подтверждённый срок поставки сохраняются отдельно от технического совпадения и производимости. Требования могут относиться к компоненту, комплекту, лоту либо договору. Состав комплекта, покрытие, испытания, общий срок и примечания не теряются при нормализации строк. `original_request` и `third_party_assessment` обозначают разные роли источников; вывод второго не обновляет `CapabilityProfile` без проверки.

## Деньги и измерения

Деньги и значимые размеры представляются десятичными значениями с единицами, а не неявными float. Трактовка налогов, валюта, конверсия и округление утверждаются в R14. Для времени сохраняются UTC и исходный часовой пояс/контекст дедлайна.

## Хранение

PostgreSQL хранит структурированные записи и бизнес-историю. Объектное хранилище - оригиналы и документы результата. Qdrant - производный индекс. История исполнения - в выбранном оркестраторе. Политика восстановления охватывает связанные слои и версии; поисковый индекс можно перестроить только при сохранённых источниках и параметрах.
