# Этап 3.2: исполнение учебного процесса через n8n

Дата: 16 октября 2026. Основание: запрос владельца «АВТОНОМНО — Приступай к реализации плана 3.2». Разработка продолжает контракт ядра 0.1.0 и ADR-0002; промышленная эксплуатация не утверждается.

## Цель и границы

Загрузка искусственного CSV остаётся прежней. Новый асинхронный запуск сохраняет точную редакцию оригинала, версию модуля и опубликованную версию workflow; n8n в режиме очередей вызывает разрешённую операцию приложения. Ядро атомарно публикует результат и завершает процесс. Оператор видит состояние и восстанавливает аварийное исполнение по исходной версии.

Вне этапа: LLM/OCR, реальный тендерный радар, согласования сотрудником, второй модуль, актуальность предметных источников, промышленная авторизация и автоматическое восстановление аварийного worker. Синхронный API и существующий интерфейс CSV сохраняются совместимыми.

## Границы компонентов

- `core/processes.py`: прикладной сценарий запуска, сверки, восстановления и обработки callback; зависит от портов, не от HTTP/SQL/n8n SDK.
- `core/process_models.py`: команды и сведения о закреплённом workflow/исполнении.
- `infrastructure/process_repository.py`: PostgreSQL, команды, попытки и атомарная защита публикации.
- `infrastructure/n8n.py`: публичный `/api/v1`, аутентифицированный production webhook, ограниченные таймауты, безопасные ошибки. Внутренний `/rest` не используется приложением.
- `modules/document_review/workflows/`: принадлежащая модулю поставляемая схема workflow. Бизнес-правила CSV остаются в Python.
- `process_api.py`: пользовательские маршруты запуска/чтения/сверки/восстановления и отдельные внутренние callback.

Ядро хранит идентичность процесса, снимок входов, технические попытки, результат и аудит. n8n хранит исполнения workflow. Собственный планировщик или второй оркестратор не создаётся.

## Команды и состояния

Пользовательские права: `process:start`, `process:read`, `process:recover`; запуск также требует существующих `artifact:read` и `dataset:publish`. Чтение проверяет область и права источников. Отдельный worker Bearer-ключ допускается только на внутренних маршрутах и не открывает обычное API.

- `POST /api/v0.1/demo/document-review/processes`: те же ссылки/ожидаемая редакция, что у синхронного извлечения, плюс ключ команды; ответ 202 с сохранённым процессом.
- `GET /api/v0.1/processes` и `GET /api/v0.1/processes/{id}`: ограниченный список/история попыток в своей области.
- `POST /api/v0.1/processes/{id}/reconcile`: явно сверить состояние с n8n, не запускать работу.
- `POST /api/v0.1/processes/{id}/recover`: ключ команды, ожидаемая попытка, основание; повтор возвращает прежний процесс. Сверка обязательна; активное/неизвестное исполнение не повторяется вслепую.
- Внутренние `POST /api/internal/v0.1/processes/{id}/claim` и `/execute`: worker-ключ, execution ID и секрет привязки запуска. Область/входы/права берутся из сохранённого запуска.

Процесс: `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED`, `RECOVERY_REQUIRED`. Попытка: `DISPATCHING`, `RUNNING`, `COMPLETED`, `FAILED`, `UNKNOWN`. Потерянный ответ сети означает неизвестный исход, а не доказанный отказ. Завершённый результат сохраняет приоритет над ошибкой позднего сетевого ответа.

## Основные гарантии

1. Ключ команды ограничен субъектом, областью и операцией; другое значимое тело под тем же ключом отклоняется. Одновременные одинаковые команды создают один процесс/одну команду восстановления.
2. Снимок хранит точный оригинал, версию обработчика и ожидаемую редакцию результата. Повтор не переключается на текущие документы.
3. Начальный запуск закрепляет ID и опубликованную версию workflow. Callback проверяет реальное исполнение через публичный API n8n. Восстановление использует штатный `POST /executions/{id}/retry` с `loadWorkflow=false`; новая публикация не меняет старый процесс.
4. Каждая попытка имеет возрастающий номер. Callback связывается с конкретным execution ID и допустимым родителем `retryOf`. После разрешения новой попытки старая теряет право публиковать.
5. Проверка действующей попытки, запись набора/строк/редакции/аудита и завершение процесса происходят в одной транзакции. Потерянный HTTP-ответ после commit не создаёт второй результат. Ошибка посередине откатывает весь результат.
6. Парсер и сетевые вызовы не удерживают блокировку строки процесса. Перед публикацией повторно проверяются попытка и ожидаемая редакция набора.
7. Неизвестный исход запуска/повтора сверяется по исполнениям n8n с ограниченной пагинацией. При неполной истории/нескольких подходящих исполнениях автоматическое решение не принимается. Утрата истории движка показывается явно.
8. Чужая область не раскрывает процесс, оригинал, результат или попытки. Секреты/ответы внешнего API не попадают в ошибки и отчёты.

В живом n8n 2.43.5 обнаружено: native retry сохраняет `workflowData`, но возвращает `workflowVersionId=null`. Адаптер восстанавливает происхождение версии по `retryOf` только при точном совпадении сохранённых `nodes`, `connections`, `settings`, привязки процесса и секрета входа с исходным исполнением. Текущая опубликованная схема для этого не читается. Несовпадение, цикл или отсутствие исходной истории дают явный отказ; глубина цепочки ограничена 20.

## Проверка

PostgreSQL-тесты: повтор/конфликт запуска; конкурентное восстановление; чужая область и права; неподходящая версия/родитель; неизвестный ответ; повтор после commit; откат; устаревший обработчик и конкурирующая редакция. Проверки API и HTTP-адаптера дополняют их.

Живой Docker-сценарий использует отдельный проект/volumes и синтетические данные: webhook → worker → приложение → SQL; авария только тестового worker, ручной повтор исходной версии, смена опубликованного workflow и сохранность старого результата. Рабочие данные и старые исполнения n8n не удаляются.

Приложение собирается и работает без `.dev`. Рабочие инструкции, испытания и отчёты располагаются в `.dev`.
