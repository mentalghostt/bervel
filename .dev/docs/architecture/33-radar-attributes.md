# Радар 1.6: объекты закупки, готовность и выгода

Реализация от 2 ноября 2026. Новый стандартный запуск без отдельной экономики использует pipeline1.6 и schema1.6.0. Сохранённые результаты и команды1.3–1.5 читаются с прежней версией. Архитектура — существующий модульный Python-монолит; новые службы, зависимости и миграции не добавлены.

## Источник потребности

Контур-адаптер сохраняет каждый Objects как procurement_objects: object_id, name, quantity, unit, unit_price, total_price, currency, characteristics. Характеристики не теряют Name, Values.Value, Values.Okei и FillingInstruction. Отображаемое description содержит дословные строки объектов с идентификаторами; API-заголовок, покупатель и прочие реквизиты не участвуют в товарном evidence, предварительном отборе по имени или извлечении потребности.

Если Objects отсутствует полностью, ограниченный адаптер читает вложенные описания объекта/ТЗ/спецификации. Наличие неполного Objects не разрешает подменить его документами. Приложения выбираются по назначению; обоснование НМЦ и проект контракта не используются как товарный источник. HTTPS-download ограничен публичными адресами, закреплённым проверенным IP и TLS hostname; ключ Контур не передаётся, перенаправления запрещены. Лимиты5МиБ/файл,10МиБ суммарно,3файла; ошибки/неполнота сохраняются как причины unknown.

В первом проходе ИИ извлекает позиции с исходными количествами и единицами. При наличии явных цен описания допускаются unit_price/total_price/currency/price_quote. Сервер проверяет дословные числа, валюту и локальное происхождение цены, не допускает использования цены соседнего объекта. Второй проход сопоставляет позиции с кандидатами только выбранного склада. Проверенные цены добавляются сервером из первого прохода. Для структурных Objects цены берутся непосредственно из API.

## Склад и подтверждение соответствия

StockImporter сохраняет произвольные плоские технические значения в specs и фактические характеристики в characteristics. Поля source_* и mock_* являются происхождением, не свойствами SKU. Скопированные source_requirements не доказывают характеристики собственного товара. Масса weight_per_piece_kg положительна; две указанные массы в CSV/JSON должны совпадать после Decimal-нормализации. Цена продажи из склада новому запуску не нужна: обязательна себестоимость unit_cost. Старый sale_price читается для прежних форматов, но не определяет выручку1.6.

Соответствие подтверждается конкретным объектом и SKU: проверяются все явно заданные требования, диапазоны, инструкции, размеры и шаг резьбы. Универсального обязательного standard/thread/strength/coating нет. Дополнительные свойства склада не становятся требованиями тендера. Противоречащие данные имени/колонок/характеристик не разрешаются выбором удобного значения. Сходные объекты связываются по исходным блокам и object_id, а не произвольным порядком ответа модели.

## Расчёт

Доменные правила в attributes.py, без HTTP/БД/файлов. Все количества и деньги рассчитываются Decimal.

- Единый процент готовности =100×покрытые подтверждённые штуки/все требуемые штуки. Неподтверждённая позиция в штуках остаётся в знаменателе с нулевым покрытием.
- Килограммы/граммы/тонны переводятся в штуки по массе конкретного подтверждённого SKU. Нельзя складывать массу со штуками напрямую. Для комплектов/упаковок нужен явный размер состава. Неизвестный знаменатель или остаток даёт null с причиной, а не фиктивные0/100.
- Повторные строки SKU внутри одного тендера расходуют общий остаток. Другие тендеры его не резервируют. Неполная потребность не выдаётся за полный состав.
- Выручка определяется ценами позиций тендера. Если раскрыта только итоговая стоимость строки, выручка сохраняет её точное значение; производная цена единицы не используется для обратного умножения.
- Противоречие quantity×unit_price и total_price проверяется с допуском точности денежного округления, без процентного допуска. Цены и себестоимость сохраняют свои исходные единицы; себестоимость переводится по потребности изделия.
- Выгода =100×(выручка−себестоимость)/выручка. benefit_percent ограничен[-100,100]; фактическая маржа и суммы остаются в economics_check. Нехватка остатка не мешает вычислить известную себестоимость, но неизвестный товар/цена/валюта не превращаются в выгодную полную закупку.

## Публичный контракт и интерфейс

У элемента отчёта1.6: analysis_status(analysed/not_analysed/error), readiness_percent, benefit_percent, readiness_check(required_pieces/covered_pieces/lines/reasons). Значения процентов — строки Decimal либо null. economics_check сохраняет фактические суммы, margin_percent и строки с исходной единицей цены. DTO api.py явно сохраняют новые поля, trace и версию1.6; это проверяется HTTP roundtrip.

UI показывает один список прошедших анализ тендеров. Пропущенные/ошибочные видны отдельным раскрываемым списком без фиктивных процентов. Две сортировки: готовность по убыванию с выгодой как вторым ключом; выгода по убыванию с готовностью как вторым ключом. Неизвестные значения последними, равные сохраняют порядок.

Фильтры включительны: готовность от0до100, выгода от−100до100. Полный диапазон сохраняет unknown, суженный исключает неизвестный показатель. Ошибочные границы объясняются. Отображение неполной готовности не округляет её до100%; очень малое положительное значение не показывается как0. Историческая пометка определяется версией отчёта, включая null-поля старого ответа DTO. PDF показывает те же серверные показатели и исходные суммы, старые шаблоны совместимы.
