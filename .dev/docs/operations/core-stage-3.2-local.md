# Локальный запуск ядра 3.2: n8n и учебный CSV

> Историческая реализация. С 22 октября 2026 n8n и Redis выведены из рабочего запуска. Актуальная [Python-реализация](python-background.md). Приведённые ниже старые команды и результаты сохранены как история.


Рабочий корень: `C:/OSPanel/home/bervel.local`. Существующий Docker-профиль: API/frontend/PostgreSQL и дополнительные n8n main/worker/Redis. Новые таблицы вводит миграция `0003_core_processes`; прежние оригиналы/результаты не изменяются.

## Что изменилось

У модуля `demo.document-review` появился асинхронный путь: точная редакция CSV → процесс ядра → аутентифицированный webhook → n8n worker → служебное API → атомарно сохранённый результат. Существующая кнопка «Загрузить в БД» использует прежний синхронный API. Переключение интерфейса на процессы в этот этап не входит.

Ядро хранит снимок входов, producer, опубликованную версию workflow и историю попыток. n8n исполняет три технических шага `Start → Claim → Execute`; CSV разбирает существующий Python-модуль. LLM, анализ реальных тендеров, согласование сотрудником и второй модуль ещё не подключены.

## Конфигурация и установка workflow

Секреты находятся только в исключённом из Git `.env`. В [примере](../../../.env.example) перечислены:

- `BERVEL_N8N_URL`: внутренний адрес, в Docker `http://n8n-main:5688`.
- `BERVEL_N8N_API_KEY`: публичный API-ключ n8n; runtime нужны чтение workflow/исполнений, поиск и retry. Provision дополнительно создаёт credentials/workflow и публикует его.
- `BERVEL_N8N_WEBHOOK_KEY`: отдельный случайный ключ входа в workflow.
- `BERVEL_PROCESS_WORKER_KEY`: другой случайный ключ служебного API; обычное API его не принимает.
- `BERVEL_N8N_WORKFLOW_ID`: ID опубликованного workflow.
- `BERVEL_N8N_WEBHOOK_PATH`: по умолчанию `bervel-document-review-v1`.
- `BERVEL_N8N_CALLBACK_URL`: внутренний адрес приложения, по умолчанию `http://api:8011`.

Пустой `BERVEL_N8N_URL` сохраняет запуск синхронного приложения без n8n. Пользовательские ключи для нового API должны явно иметь `process:start`, `process:read`, `process:recover`; чтение также требует `artifact:read`/`dataset:read`, запуск — `artifact:read`/`dataset:publish`.

На новой установке сначала создать публичный API-ключ в n8n через Settings → n8n API. Три ключа приложения должны различаться и иметь не менее 32 ASCII-символов. Не заменять существующий `N8N_ENCRYPTION_KEY` и не переносить ключи в JSON workflow.

Из корня проекта:

```powershell
.dev/scripts/docker.ps1 -Action orchestration
docker compose -f compose.yaml -f compose.orchestration.yaml build api
docker compose -f compose.yaml -f compose.orchestration.yaml run --rm --no-deps api python -m bervel provision-orchestration
```

Команда provision использует публичный `/api/v1`, устанавливает workflow из пакета приложения и выводит только его ID/версию/путь. Сохранить `workflow_id` в `BERVEL_N8N_WORKFLOW_ID`, затем:

```powershell
.dev/scripts/docker.ps1 -Action start
```

Для уже подготовленного текущего окружения достаточно `orchestration` и `start`. Повтор provision с известным ID не перезаписывает опубликованную схему. Скрипт разработки `stage32_bootstrap.py` использован только для подготовки локального стенда/существующего учебного аккаунта; приложение и новая установка от него не зависят.

## Проверка вручную через Swagger

1. Открыть `http://127.0.0.1:8011/docs`. Скопировать обычный ключ командой `.dev/scripts/docker.ps1 -Action key` и ввести через Authorize.
2. В `POST /api/v0.1/artifacts` загрузить `.dev/fixtures/core-stage-3.1/requirements-v1.csv`, указав новый `command_key`. Сохранить `artifact_id` и `revision` ответа.
3. В `POST /api/v0.1/demo/document-review/processes` передать эти значения как `artifact_id`/`artifact_revision` и другой ключ команды. Ответ 202 содержит `process_run_id`.
4. Прочитать `GET /api/v0.1/processes/{run_id}`. До завершения видны `QUEUED`/`RUNNING`, затем `COMPLETED`, ссылка `result` и ID исполнения в `attempts`. Список доступен в `GET /api/v0.1/processes` с фильтром `state` и пагинацией.
5. Прочитать результат через прежний `GET /datasets/{dataset_id}/revisions/{revision}` и `/records`. Для v1 количества — `10` и `null`, качество `PARTIAL`.
6. Повторить пункт 3 с прежним телом/ключом: процесс тот же. Другое значимое тело под прежним ключом даёт 409 `IDEMPOTENCY_CONFLICT`.

В n8n по адресу `http://127.0.0.1:5688` видно соответствующее техническое исполнение. Успех HTTP webhook означает принятие запуска, а итог определяется сохранённым состоянием процесса.

## Ошибка и ручное восстановление

1. Прочитать процесс и вызвать `POST /processes/{run_id}/reconcile`: операция только сверяет историю n8n, работу заново не запускает.
2. При подтверждённой аварии вызвать `POST /processes/{run_id}/recover`, передав уникальный `command_key`, текущий `expected_attempt` и непустое `reason`.
3. Ядро атомарно резервирует одну новую попытку и вызывает native retry с `loadWorkflow=false`. Повтор команды возвращает тот же процесс. Новая публикация workflow не меняет сохранённые входы/модуль исходного процесса.
4. Проверить новое исполнение/связь с родителем в `attempts`, состояние и `result`. Ошибка прежнего родителя может остаться в истории n8n после успешного повтора.

Активные исполнения не повторяются. `RECOVERY_REQUIRED`/`ENGINE_RESPONSE_UNKNOWN` означает неопределённый исход или недостаточную историю; сначала нужна сверка, новый ключ сам по себе проблему не решает. Если нет единственного подтверждённого исходного исполнения, автоматический повтор не выполняется. Не удалять историю движка до завершения восстановления.

Если результат уже зафиксирован до потери ответа/аварии worker, ядро возвращает его и не создаёт новую попытку. Поздний callback старой попытки после разрешённого восстановления получает 409 `STALE_ATTEMPT`. Более новая редакция набора защищена отдельной проверкой `expected_revision`.

n8n 2.43.5 не возвращает ID версии у native retry. Адаптер устанавливает её происхождение только по `retryOf` и точному совпадению сохранённой схемы/входов. Изменённая схема или отсутствующая исходная история отклоняются; цепочка ограничена 20 исполнениями. Поиск истории ограничен 20 страницами по 100 записей отдельно для обычного и running-списка.
