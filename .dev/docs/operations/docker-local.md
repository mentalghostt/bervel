# BERVEL в Docker: устройство и ежедневная работа

Проверено 16 октября 2026 на Windows 11, Docker Desktop 4.95.0 / Engine 29.8.2 / Compose 5.6.0, Linux amd64. Рабочая папка остаётся `C:/OSPanel/home/bervel.local`. Все команды ниже выполняются в PowerShell из этого корня. Локальные Python, Node, PostgreSQL и Redis для обычного запуска и проверок больше не нужны; Docker Desktop должен работать.

## Что запускается

```text
Браузер → frontend :5173 → api :8011 → PostgreSQL
                              └────→ volume оригиналов

n8n main :5688 → Redis (очередь) → n8n worker
       └────────── PostgreSQL ─────────┘
```

| Сервис | Роль | Доступ с Windows |
| --- | --- | --- |
| `frontend` | Отдаёт собранный интерфейс, передаёт `/api` в API | http://127.0.0.1:5173 |
| `api` | Проверяет права, сохраняет оригиналы, обрабатывает CSV | http://127.0.0.1:8011/health/ready |
| `postgres` | Метаданные, строки результатов и история n8n в отдельных БД | `127.0.0.1:5433` |
| `migrate` | Обновляет структуру БД перед запуском API; завершение с кодом 0 штатно | Отдельного порта нет |
| `redis` | Постоянная очередь экспериментального n8n | Только внутренняя сеть Docker |
| `n8n-main` | Редактор процессов и приём запусков | http://127.0.0.1:5688 |
| `n8n-worker` | Исполняет задания из очереди | Только внутренняя сеть Docker |

Внутри Docker имя `postgres` обозначает контейнер PostgreSQL, а `api` — контейнер API. `127.0.0.1` внутри контейнера указывает на сам этот контейнер. Поэтому браузер обращается к frontend по localhost, а frontend — к API по имени `api`. Порты опубликованы только на loopback Windows; доступ из локальной сети не включён.

Redis и n8n подключаются отдельным профилем `orchestration`. Прямая загрузка CSV их не использует. Перенос профиля сохраняет эксперимент с движком процессов; продуктовая интеграция следующих этапов ядра этим не реализована.

## Первый запуск и обычная работа

На текущем компьютере конфигурация уже создана и данные перенесены. Для нового разработчика:

```powershell
.\.dev\scripts\docker.ps1 -Action init
.\.dev\scripts\docker.ps1 -Action start
```

`init` создаёт исключённый из Git `.env` со случайными паролями и ключами. Существующий файл сохраняется. Если доступен исторический ключ n8n, сохраняется именно он. Значения `.env.example` служат описанием параметров, а не рабочими паролями.

`start` собирает API и frontend, дожидается PostgreSQL, выполняет миграции, затем дожидается готовности приложения. При повторном запуске используются прежние volumes с данными. Откройте http://127.0.0.1:5173 и скопируйте ключ в буфер:

```powershell
.\.dev\scripts\docker.ps1 -Action key
```

Вставьте его в поле ключа интерфейса. Helper не печатает ключ в терминал. Ключ определяет пользователя, область данных и разрешения; перенос данных не меняет прежние ID и области доступа.

```powershell
.\.dev\scripts\docker.ps1 -Action status
.\.dev\scripts\docker.ps1 -Action stop
.\.dev\scripts\docker.ps1 -Action start
.\.dev\scripts\docker.ps1 -Action orchestration
```

`stop` останавливает сервисы проекта, включая запущенные тестовые и n8n, сохраняя данные. `orchestration` включает Redis и оба процесса n8n. Учётная запись владельца n8n перенесена из прежней БД; ключ API BERVEL не является паролем n8n. Историческая локальная учётная запись записана в исключённом из Git `.dev/local/core-stage-2/owner.env`.

Журналы:

```powershell
docker compose -f compose.yaml -f compose.orchestration.yaml logs --tail 100 api postgres
docker compose -f compose.yaml -f compose.orchestration.yaml logs --tail 100 n8n-main n8n-worker
```

## Изменения кода и Git

```powershell
.\.dev\scripts\docker.ps1 -Action dev
```

Команда занимает терминал, собирает профиль разработки и включает Compose Watch — наблюдение за исходниками Windows. Для API изменённые файлы `src/bervel` синхронизируются в установленный пакет контейнера, после чего API перезапускается. Для интерфейса Vite получает изменения `frontend/src`, `public` и настроек. Изменения манифестов зависимостей вызывают пересборку. Windows `venv` и `node_modules` в контейнеры не копируются.

Остановите наблюдение сочетанием Ctrl+C. Чтобы вернуться к собранному интерфейсу без наблюдения, выполните `-Action start`. Если контейнеры уже остановлены, данные остаются на месте.

Git-процесс сохраняется: редактируете файлы, смотрите diff, делаете коммит и push. В Git передаются Dockerfile, Compose и lock-файлы. Контейнеры, `.env`, БД, оригиналы и резервные копии в Git не входят. В основном checkout `core` агент менял только рабочие файлы; staging, commit и push выполняет человек.

При добавлении Python-зависимости нужно обновить `pyproject.toml` и Linux lock-файлы, затем пересобрать и проверить образ. Инструмент генерации — `.dev/scripts/docker_lock.py`; исторический Windows lock не подменяет Linux-проверку. Для frontend изменяются `package.json` и `package-lock.json`, установка внутри образа выполняется через `npm ci`.

## Где находятся данные

| Volume | Содержимое |
| --- | --- |
| `bervel_postgres_data` | БД приложения, тестов и n8n |
| `bervel_objects` | Байты оригиналов приложения, адресуемые по SHA-256 |
| `bervel_redis_data` | Очередь n8n, включено AOF-сохранение |
| `bervel_n8n_main_data`, `bervel_n8n_worker_data` | Локальное состояние процессов n8n |
| `bervel_test_objects` | Изолированные оригиналы браузерных тестов |

Docker управляет этими хранилищами в согласованном диске `C:/Users/Evan/AppData/Local/Docker/wsl/disk/docker_data.vhdx`. Удаление и пересоздание контейнера сохраняет volume. Образ содержит программу и библиотеки; данные volume не включаются в образ. Для передачи существующего состояния нужны отдельная резервная копия и секреты.

Команды `docker compose down -v`, удаление volumes в Docker Desktop и очистка диска Docker удаляют постоянные данные. Helper `stop` таких действий не выполняет.

## Проверки

```powershell
.\.dev\scripts\docker.ps1 -Action tests
.\.dev\scripts\docker.ps1 -Action e2e
```

Первая команда собирает отдельный тестовый образ и запускает pytest. PostgreSQL-проверки используют только `bervel_core_stage31_test` и временные схемы; чужое имя БД отклоняется. Вторая запускает 15 браузерных сценариев интерфейса и 3 сценария с живым API, затем сверяет результат SQL-запросами: обычная загрузка, повтор после потери ответа без дубля, отклонённый CSV.

Playwright и Chromium находятся в закреплённом тестовом образе. В рабочие образы они не включены. Логи и результаты — `.dev/local/docker/backend` и `.dev/local/docker/frontend`.

Проверка сохранности старых данных и эксперимент n8n имеют отдельные инструменты: `.dev/scripts/docker_validate_migration.py` и `.dev/experiments/n8n/docker_probe.py`. Эксперимент временно перезапускает процессы n8n; инструкция и результаты — в [отчёте Docker](../quality/docker-environment-report.md). Для повседневного запуска он не нужен.

## Резервная копия и проверка восстановления

```powershell
.\.dev\scripts\docker_backup.ps1
.\.dev\scripts\docker_backup_verify.ps1 -BackupPath .dev\local\docker\backups\docker-20261016T140756Z
```

Первая команда создаёт новый каталог с UTC-временем. На время выгрузки останавливаются пишущие сервисы этого проекта; PostgreSQL остаётся работать. Сохраняются логические дампы приложения и n8n, архивы оригиналов, Redis и локальных данных n8n, `.env`, отдельный ключ шифрования n8n и manifest с SHA-256. В конце запускаются сервисы, которые работали до копирования. Есть короткий перерыв в доступности приложения.

Вторая команда проверяет контрольные суммы и восстанавливает приложение в новую временную БД и новый volume. Через установленный API она читает оригиналы и редакции результатов, проверяет SHA-256 и количества. Рабочая БД не перезаписывается; временная БД и volume удаляются после проверки. Замените путь на нужную копию. Перед этой проверкой должен быть собран тестовый образ (`-Action tests`).

Проверенная копия `docker-20261016T140756Z` содержит 9 материалов, 13 редакций оригиналов, 5 наборов, 9 редакций результатов и 18 строк. Исходная копия Open Server — `source-20261016T135336Z`; форматы этих двух копий различаются.

В копиях есть секреты и пользовательские данные. Они исключены из Git. Копия на том же диске защищает от неудачной правки, но не от потери этого диска. Внешнее резервное хранилище для серверного размещения выбирается отдельно.

### Восстановление на чистом окружении

Полное восстановление выполняется до первого запуска API и n8n, в пустые БД и volumes. Порядок важен: сначала прежняя конфигурация и ключи, затем данные, затем миграции и процессы.

1. Для Docker-копии сохранить её `docker.env` как `.env`; не генерировать новый `N8N_ENCRYPTION_KEY`. Проверить все SHA-256 из `manifest.json`.
2. Собрать API и frontend и запустить только `postgres`. Его инициализация создаст пустые БД с ролями и паролями из восстановленного `.env`.
3. Убедиться, что целевые БД и volumes пусты. Копировать два дампа в контейнер PostgreSQL и применить `pg_restore --no-owner --no-acl --single-transaction --exit-on-error`: `bervel_core_stage31.dump` в `bervel_core_stage31` с ролью `bervel_core_stage31`, `bervel_n8n.dump` в `bervel_n8n` с ролью `bervel_n8n`. Внутреннее подключение для этой операции выполняется администратором `postgres`.
4. Восстановить архивы `bervel_objects.tar`, `bervel_redis_data.tar`, `bervel_n8n_main_data.tar`, `bervel_n8n_worker_data.tar` в соответствующие пустые volumes. Сохранить владельцев файлов из архивов; API использует UID 10001. Перед распаковкой проверять пути архива, не распаковывать его в папку исходников Windows.
5. Выполнить `-Action start`, затем при необходимости `-Action orchestration`. Проверить готовность, вход в n8n, чтение прежних ID и SHA-256 оригиналов; выполнить проверку резервной копии.

Автоматический `docker_backup_verify.ps1` проверяет восстановление приложения и оригиналов, но не поднимает вторую копию всей очереди n8n. Реальный перенос БД n8n из Open Server уже проверен запуском main/worker и четырьмя сценариями. Полный аварийный запуск всех архивов очереди на другой машине отдельно не испытан.

Для исходной копии Open Server предусмотрен `.dev/scripts/docker_restore_source.py`: он проверяет прежний ключ, оба дампа, оригиналы и пустоту целей до записи и отказывается восстанавливать заполненную БД. Этот инструмент использован при текущем переносе; Docker-копия с полем `files` предназначена для порядка восстановления выше, а не для этого скрипта.

### Возврат к исходному окружению

Исходные БД и три оригинальных файла Open Server не изменялись и не удалялись. Остановите Docker-сервисы и используйте [прежнюю локальную инструкцию](core-stage-3.1-local.md) и [запуск интерфейса](frontend-csv-upload.md). Модулями панели управляет пользователь. Новые записи, созданные уже в Docker, автоматически в старую БД не попадают; перед возвратом требуется отдельный перенос новых данных.

## Передача другому разработчику и сервер

Другому разработчику нужны репозиторий и Docker. Для нового чистого окружения достаточно `init` и `start`; для прежних данных дополнительно передаются проверенная копия и секреты отдельным защищённым способом. Git не переносит содержимое volumes.

Рабочие API и статический frontend собираются без `.dev`; это подтверждено сборкой API из отдельного контекста только с файлами приложения. Обычный прямой запуск: `docker compose -f compose.yaml -f compose.orchestration.yaml up --build -d --wait api frontend`. Проверочные профили и Watch используют `.dev` отдельно.

Для production можно использовать те же Dockerfile и версии зависимостей. Конкретный сервер ещё не настраивался: нужны домен/HTTPS, серверные секреты, внешние резервные копии и проверка ресурсов. Текущие localhost-порты и учебные ключи относятся к локальному окружению. Подтверждена Linux amd64; ARM отдельно не проверен.

Обновление версии зависимости — явная правка версии/digest и lock-файлов с повторной сборкой и проверками. Автоматическое обновление `latest` не используется.
