# BERVEL в Docker: запуск и данные

Актуально на 11 ноября 2026. Команды выполняются из корня клонированного репозитория; расположение папки произвольное. На этой машине корень `C:/OSPanel/home/bervel.local`. Для обычного запуска нужны Docker Desktop с Compose и PowerShell. Python, Node и PostgreSQL из Open Server Panel не используются.

```text
Браузер → frontend :5173 → api :8011 → PostgreSQL
                              ↓             ↑
                         оригиналы       worker Python
```

| Сервис | Обязанность | Доступ с Windows |
| --- | --- | --- |
| frontend | Сайт и Nginx; добавляет серверный ключ к публичному API | http://127.0.0.1:5173 |
| api | Загрузка, просмотр, прямой разбор и постановка фоновых заданий | http://127.0.0.1:8011/health/ready |
| postgres | Структурированные данные и очередь заданий | 127.0.0.1:5433 |
| migrate | Применяет структуру БД перед стартом; завершение с кодом 0 штатно | Нет |
| codex | Общий модельный сервис для чатов, радара и пресейла | Нет |
| worker-knowledge | Строит общую память загруженных файлов | Нет |
| worker-chat | Обрабатывает сообщения чата | Нет |
| worker-ai-tender-radar | Выполняет задания тендерного радара | Нет |
| worker-presales | Выполняет задания пресейл-конвейера | Нет |

n8n и Redis удалены из рабочего запуска по решению владельца. [Действующие роли и восстановление](../architecture/22-independent-workers.md), [архитектурное решение](../adr/0005-python-background-processes.md).

## Ежедневная работа

```powershell
.\.dev\scripts\docker.ps1 -Action start
.\.dev\scripts\docker.ps1 -Action status
.\.dev\scripts\docker.ps1 -Action stop
.\.dev\scripts\docker.ps1 -Action dev
```

`start` собирает приложение, применяет миграции и запускает 8 постоянных сервисов из таблицы и одноразовый `migrate`. `dev` включает наблюдение за исходниками API, фоновых исполнителей, модельного сервиса и сайта. Такой же состав сервисов выбран для обычного `docker compose up -d --build`. Контейнер `migrate`, завершившийся с кодом 0, штатный и переиспользуется Compose; удалять его после каждого запуска не требуется.

Обычная остановка сохраняет постоянные данные. На новой машине сначала выполнить `-Action init`: создаётся исключённый из Git `.env`, включая фактический абсолютный путь нового checkout для инженерных mounts. При повторном `init` прежние секреты и права сохраняются; отсутствующий серверный веб-ключ выбирается из подходящей существующей привязки.

Для ответов модели настройте собственный доступ в разделе настроек или через `BERVEL_CODEX_BASE_URL`, `BERVEL_CODEX_MODEL`, `BERVEL_CODEX_API_KEY`. Если используете уже настроенный MOX на хосте, добавьте `-Mox` при запуске; его существующие credentials монтируются только для чтения. Доступ к Контур задаётся через `KONTUR_API_KEY`, embedding-провайдер — через переменные из `.env.example`. Доступы других разработчиков и локальные release-файлы из `.dev/local` в Git не поставляются.

## Дополнительные сервисы и очистка

Инженерный чат инспекции требует ещё 3 сервиса: `worker-inspection`, `inspection-reader`, `inspection-test-postgres`. Последний — отдельная временная БД для проверок кода, а не вторая рабочая БД. Обычные чаты, файлы, радар и пресейл от неё не зависят.

```powershell
.\.dev\scripts\docker.ps1 -Action start -Inspection
# Или напрямую, с уже подготовленным .env:
docker compose --profile inspection up -d --build
```

`-Inspection` при `start` также собирает образы инструментов `inspection-backend-tests` и `inspection-frontend-tests`. Для `dev`/`worker` он включает исполнителя инспекции и его зависимости; образы инструментов предварительно подготовьте через `start -Inspection`. Без этого флага инспекция и её тестовая БД не запускаются. `status` и `stop` учитывают все профили основного Compose.

Профиль `test` нужен только для тестов, `inspection-tools` — для сборки инженерных инструментов. Симулятор Контур добавляется отдельным `.dev/docker/compose.kontur-simulator.yaml`, туннель — отдельным помощником. В обычном запуске их нет. Не включайте `--profile "*"` при `up`: он намеренно включает все тестовые и дополнительные сервисы.

Одноразовые команды выполняйте с `docker run --rm` / `docker compose run --rm`. У Compose этот флаг убирает только контейнер команды, поэтому помощник `e2e` в `finally` дополнительно останавливает и удаляет только `frontend-e2e`, `api-e2e`, `migrate-test`, в том числе при провале тестов. Рабочая PostgreSQL и именованные тома сохраняются. Самостоятельно запущенные preview удаляйте адресно после проверки; одного `stop` недостаточно.

Не используйте глобальную очистку `prune`, `down -v` или слепой `--remove-orphans`: дополнительные overlay могут содержать нужный симулятор или другой сервис, отсутствующий в основном Compose. Старые тома n8n/Redis сохранены как архив данных; отсутствие использующих их контейнеров не означает разрешение удалить данные.

Сайт: http://127.0.0.1:5173; загруженные файлы: http://127.0.0.1:5173/#/files. Ключ не вводится в браузере и не хранится в нём. Все посетители работают с общей настроенной областью, без входа сотрудников. [Устройство доступа](frontend-server-access.md).

Внутри Docker `postgres` и `api` — имена сервисов. Браузер обращается к localhost, Nginx — к `api:8011`, API и worker — к `postgres:5432`. Порты опубликованы только на loopback; публикация в интернете требует отдельной настройки доступа, адреса и HTTPS.

## Данные и резервирование

| Volume | Содержимое |
| --- | --- |
| bervel_postgres_data | База приложения, тестов и сохранённая историческая БД прежнего движка |
| bervel_objects | Оригиналы загруженных файлов |
| bervel_test_objects | Отдельные тестовые оригиналы |

Данные не входят в Git и не заменяются копированием исходников. Именованные volumes сохраняются при пересоздании контейнеров.

Старые backup/restore helpers сняты: они обращались к удалённым artifact_revisions и прежним сервисам, поэтому невалидны для текущей схемы. Готового универсального автоматического backupworkflow сейчас нет. Существующие архивы, .dev/local/docker/backups и volumes сохраняются.

Для новой копии нужны адресный pg_dump фактической БД, согласованный снимок objectvolumes и приватной конфигурации, затем изолированная репетиция восстановления с текущей схемой/образами. Эта зачистка не выполняет такие операции и не перезапускает runtime. Не применять старый установщик/backuphelper из исторического отчёта.

Перед удалением прежних сервисов создана полная копия `docker-20261022T091022Z`: обе БД, оригиналы, исторические volumes и ключи. Старый эксперимент целиком сохранён в `retired-experiment` внутри этой копии. Историческая БД и volumes не используются новым worker и оставлены для сохранности данных; новая копия приложения сама по себе не является копией этих архивных сервисов.

## Проверки и журналы

```powershell
.\.dev\scripts\docker.ps1 -Action tests
.\.dev\scripts\docker.ps1 -Action e2e
docker compose logs --tail 100 api worker-ai-tender-radar worker-presales postgres
```

Тесты используют отдельную БД и тестовые оригиналы. Сборка API, сайта и Linux-зависимостей выполняется в контейнерах. `.dev` содержит инструменты и тесты, но не требуется установленному приложению. Приложение не зависит от структуры каталогов Open Server. Перенос на отдельный промышленный сервер этой локальной проверкой не подтверждается.

Проверка состава Docker без запуска приложения: `python -m pytest -c .dev/pytest.ini --rootdir=. --basetemp=.dev/local/docker-config-tests .dev/tests/test_docker_compose.py -q`. Нужны Python с pytest и Docker CLI; проверки помощника дополнительно требуют PowerShell. Используются примерные значения `.env.example`, текущие секреты в отчёт не выводятся.
