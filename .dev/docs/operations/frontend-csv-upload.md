Рабочий корень: `C:/OSPanel/home/bervel.local`. Код интерфейса и конфигурация Vite находятся в `frontend/` внутри корня, без зависимости от `.dev`. Новые зависимости приложения, миграции и изменения Python API не потребовались.

## Исторический прямой запуск

Нужен уже включённый пользователем PostgreSQL 17 на `127.0.1.49:5432`. База приложения — `bervel_core_stage31`, роль — `bervel_core_stage31`. При недоступности модуль включает пользователь в Open Server Panel. Самостоятельно менять состояние модулей или VPN не нужно.

В первом терминале Git Bash из корня проекта запустить существующий PowerShell-инструмент. Он настроит окружение, скопирует первый API-ключ в буфер обмена и запустит Python API. Ключ не печатается в терминал и не сохраняется в файл.

```bash
cd /c/OSPanel/home/bervel.local
powershell.exe -NoProfile -ExecutionPolicy Bypass -Command '
  $launcher = "C:\OSPanel\home\bervel.local\.dev\scripts\core_stage_3_1_local.ps1"
  & $launcher -Action configure
  ($env:BERVEL_ACCESS_KEYS | ConvertFrom-Json)[0].key | Set-Clipboard
  & $launcher -Action serve
'
```

API будет доступен на `http://127.0.0.1:8011`. Оставить терминал открытым. Повторный независимый запуск инструмента обычно создаёт новые ключи; страница должна использовать ключ именно работающего API.

Во втором терминале, если Vite ещё не запущен:

```bash
cd /c/OSPanel/home/bervel.local/frontend
npm run dev -- --host 127.0.0.1
```

Открыть адрес из терминала, обычно `http://127.0.0.1:5173`. Если Vite уже работает на 5173 после проверки первого этапа, достаточно обновить страницу. Оба сервера останавливаются Ctrl+C в соответствующем терминале.

Vite перенаправляет `/api` на Python API; браузер использует относительные адреса. Для другого адреса API перед запуском Vite можно задать переменную окружения, например `export BERVEL_API_TARGET='http://127.0.0.1:8012'`. Она не содержит ключа и не требует Open Server. Промышленный веб-сервер должен отдельно маршрутизировать `/api` к backend; настройка промышленного развёртывания в этот этап не входит.

## Ручная проверка

1. Выбрать или перетащить `C:/OSPanel/home/bervel.local/.dev/fixtures/core-stage-3.1/requirements-v1.csv`.
2. Ключ добавляет сервер, вводить его в браузере не нужно.
3. Нажать «Загрузить в БД». Без нажатия файл не отправляется. Кнопка активна после выбора подходящего файла.
4. Во время запроса появляются состояния загрузки, обработки и получения результата. Повторные клики и изменения файла заблокированы.
5. После успеха появляются «Сохранено в PostgreSQL», `2 строки`, состояние «Есть пропуски», ID оригинала и ID результата с редакциями и кнопками копирования. Кнопка загрузки становится отключённой «Сохранено».
6. «Есть пропуски» ожидаемо для примера: во второй строке количество отсутствует и сохраняется как `UNKNOWN` с JSON `null`, а не как ноль. Оба ряда сохранены.
7. Для нового файла выбрать другой CSV или явно выбрать тот же заново. Новый выбор означает новую операцию загрузки; глобальное устранение одинаковых файлов этим интерфейсом не обещается.
8. Проверить неверный ключ, файл с неправильными колонками или недоступный API: показывается понятная ошибка вместо сообщения об успешном сохранении.

Ключ хранится только в памяти страницы и передаётся в заголовке `Authorization`. В URL, `localStorage`, `sessionStorage` и сборку он не попадает. После обновления страницы нужно заново выбрать файл и вставить ключ.

## Как устроено сохранение и повтор

Страница выполняет три последовательных запроса:

1. `POST /api/v0.1/artifacts` — оригинал попадает в настроенное файловое хранилище, его метаданные — в PostgreSQL. При отправке явно указывается тип `text/csv`: Windows может определять CSV как файл Excel. Байты и имя файла сохраняются.
2. `POST /api/v0.1/demo/document-review/extractions` — сервер проверяет UTF-8, структуру и значения, затем атомарно публикует обработанные строки и связанные сведения в БД.
3. `GET /api/v0.1/datasets/{id}/revisions/{revision}` — страница получает сводку сохранённого набора. Успех показывается по ответу сервера.

Если запрос завершился ошибкой, доступна кнопка «Повторить». В пределах текущего выбора файла, ключа и открытой страницы сохраняются ключи команд и подтверждённые ссылки. Повтор загрузки использует тот же ключ команды; после подтверждённого оригинала повторяется обработка; после подтверждённой записи набора повторяется только GET сводки. Это защищает от дублей при потерянном ответе, включая ответ после commit в PostgreSQL.

Если сохранённая ссылка на набор уже получена, а GET сводки завершился ошибкой, страница прямо сообщает, что результат уже записан. При ошибке самого запроса обработки его исход может оставаться неизвестным до повтора. Ошибочный CSV может иметь сохранённый оригинал, но не публикует обработанные строки.

Перезагрузка страницы, смена ключа или новый выбор файла сбрасывают сведения о попытке. После неоднозначной ошибки не следует обновлять страницу для повтора: используйте «Повторить». Восстановление истории после перезагрузки не входит в текущий интерфейс.

## Проверить строки в DBeaver

Подключиться к текущей локальной базе `bervel_core_stage31` на `127.0.1.49:5432` с ролью `bervel_core_stage31`. В этом учебном окружении пароль роли не настроен. Скопировать ID результата со страницы и выполнить запрос, заменив текст `ВСТАВЬТЕ_ID_РЕЗУЛЬТАТА`. Использовать номер редакции со страницы; для новой загрузки он равен 1.

```sql
SELECT ordinal + 1 AS row_number,
       record #>> '{payload,name}' AS name,
       record #>> '{payload,quantity,state}' AS quantity_state,
       record #>> '{payload,quantity,value}' AS quantity_value,
       record #>> '{payload,quantity,unit}' AS unit
FROM public.data_records
WHERE dataset_id = 'ВСТАВЬТЕ_ID_РЕЗУЛЬТАТА'::uuid
  AND revision = 1
ORDER BY ordinal;
```

Ожидаются две строки: значения количества `10` и SQL `NULL`, состояния `KNOWN` и `UNKNOWN`, единицы `piece`. Сами оригиналы находятся в файловом хранилище; в `artifact_revisions` хранятся их метаданные. В `datasets`, `dataset_revisions` и `data_records` — наборы, редакции и обработанные строки.
