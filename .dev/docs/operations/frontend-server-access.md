# Веб-интерфейс без ручного API-ключа

19 октября 2026 владелец выбрал общий доступ без входа сотрудников. Поле ключа убрано с обеих страниц; список прежних файлов открывается сразу, включая обновление браузера. Рабочий корень: `C:/OSPanel/home/bervel.local`, основная ветка `core`. Записи в Git не выполнялись.

```text
Браузер: загрузить CSV / показать файлы
  │ запрос без секретного ключа
  ▼
Веб-сервер Nginx (при разработке — Vite)
  │ добавляет ключ из серверного окружения
  ▼
Python API: проверяет права и область данных
  │
  ▼
PostgreSQL + хранилище оригиналов
  └── ответ с данными → веб-сервер → браузер
```

Это ключ Python API BERVEL, отдельный от n8n и языковой модели. API продолжает проверять ключ и права. Все посетители сайта работают с одной настроенной областью данных. Разделения по сотрудникам в этом режиме нет. Секрет не передаётся в HTML, JavaScript, запросах браузера, localStorage или sessionStorage. При прямом обращении к Python API по-прежнему нужен Bearer-ключ.

## Настройка и перенос

В исключённом из Git `.env` задаётся `BERVEL_WEB_ACCESS_KEY`. Значение должно совпадать с одной привязкой `BERVEL_ACCESS_KEYS` с правами `module:read`, `artifact:read`, `artifact:write`, `dataset:read`, `dataset:publish`. Подходит токен из 32 и более латинских букв, цифр, `_` и `-`. Сгенерированные ключи проекта уже соответствуют формату. Пример параметров без рабочих секретов — `.env.example`.

```powershell
.\.dev\scripts\docker.ps1 -Action init
.\.dev\scripts\docker.ps1 -Action start
```

`init` сохраняет прежние секреты. Если веб-ключ отсутствует, добавляет первую подходящую привязку; уже настроенный совместимый выбор сохраняет. При несовместимых настройках останавливается без записи. Ключи не печатает. Compose передаёт ключ frontend во время запуска; образ собирается без него. Nginx не запускается с пустым или неподходящим токеном. После изменения `.env` требуется пересоздать frontend обычной командой `start`.

Путей Windows и имени компьютера в механизме нет. В Docker веб-сервер обращается к `http://api:8011`; серверный адрес задаёт `BERVEL_API_TARGET`. Браузер использует относительные адреса. Для переноса нужны код, серверные настройки, данные PostgreSQL и volume оригиналов. Нужен хостинг с Docker или поддержкой работающих веб-сервера и Python API; одного статического хостинга недостаточно. Конкретный внешний сервер этим этапом не настраивался: домен, HTTPS и публикация портов относятся к его конфигурации.

Vite читает серверные параметры из окружения либо корневого `.env`. Префикс `VITE_` для секрета не используется. Dev и preview применяют одинаковые проверки. Helper `docker.ps1 -Action key` сохранён для ручных запросов к API; для браузера он не нужен.

## Границы прокси

Ключ добавляется только к `/api/v0.1/`; внутренние worker callbacks не передаются. Браузер отмечает запрос публичным заголовком `X-Bervel-Web: 1`. Это не секрет и не вход пользователя. Маркер и отказ для `Sec-Fetch-Site: cross-site` мешают обычной форме постороннего сайта использовать неявный ключ. Входящий Authorization не меняет общую область: сервер подставляет свой ключ. Все посетители, которым доступен сам сайт, имеют согласованные общие права.
