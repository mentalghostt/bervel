# Доступ через веб-сервер

Браузер обращается к относительному `/api/v0.1/`. Nginx/Vite добавляет `BERVEL_WEB_ACCESS_KEY` из серверного окружения, Python проверяет права/область. Секрет не хранится в HTML/JavaScript, browser storage или браузерном Authorization. Прямой вызов Python API требует своего Bearer-ключа.

Все посетители сайта работают в общей настроенной области. Это не вход по сотрудникам и не индивидуальные полномочия. Входящий Authorization не меняет область: proxy использует серверный ключ. Публичный `X-Bervel-Web: 1` не является секретом; cross-site-запросы ограничиваются существующими проверками.

В `.env` веб-ключ должен соответствовать привязке `BERVEL_ACCESS_KEYS` с необходимыми правами приложения. Точный набор проверяет текущий helper/конфигурация; выведенные module/dataset-права не являются инструкцией создавать старую модель доступа. `docker.ps1 -Action init` сохраняет существующие секреты и проверяет совместимость, не печатая ключи. [Команды Docker](docker-local.md).

Nginx обращается к `api:8011` внутри Docker; браузер — к localhost. Серверный `BERVEL_API_TARGET` не является клиентским секретом. Секрет не имеет префикса VITE_. Для отдельной площадки нужны backend/БД/оригиналы, серверные настройки и разрешённый доступ/HTTPS; одного статического хостинга недостаточно.

Ключ подставляется только к публичному `/api/v0.1/`, внутренние callbacks/инженерные endpoints не становятся общедоступными. Публичная ссылка должна учитывать, что доступ к самому сайту даёт общие согласованные права.

Актуальные проверки — `.dev/tests/frontend-server-access.cjs`, `test_docker_env.py`, `test_api_permissions.py`. [Файловый контракт](../architecture/25-independent-files.md), [безопасность](../architecture/07-reliability-security.md).
