# Раздел «Проверка»: встроенный Codex CLI

Локальный адрес: [127.0.0.1:5173/#/inspection](http://127.0.0.1:5173/#/inspection). Каждый диалог — отдельный сохраняемый native Codex thread. «Обращения» остаются внутренними тикетами; обычный ассистент, радар и голос используют прежние режимы.

Пользователь явно заменил промежуточную схему ограниченных инструментов и подтверждаемых патчей полноценным встроенным CLI. Инспектор читает реальные файлы, запускает команды, тесты и Docker, меняет код и данные по задаче без карточки разрешения или подтверждения патча. Native профиль — `danger-full-access`, `approval_policy=never`, сеть доступна. Правила пользователя про VPN, Open Server Panel, основную Git-ветку и размещение материалов остаются инструкциями агенту; это не техническая песочница, ограничивающая полномочия CLI.

## Как проходит запрос

Текст из поля ввода передаётся непосредственно в настоящий Codex CLI через уже установленный `@openai/codex-sdk` 0.163.0: `startThread` для нового расследования, `resumeThread` для продолжения, `runStreamed` для выполнения. BERVEL не добавляет JSON-план, output schema, вручную выбранные выдержки истории или classifier, разрешающий действия. Искусственного лимита 4000 символов у inspection ввода нет; физически слишком большой транспортный запрос отклоняется явно, без тихой обрезки.

Контекст, его окно и сжатие ведёт сам CLI. Один диалог связан с одним native thread ID; соответствие и native rollouts сохраняются в `bervel_codex_state`, отдельно от legacy generate-контекста. Перезагрузка страницы не начинает расследование заново. Старые pre-native сообщения сохраняются в BERVEL как архив; они не превращаются автоматически в огромный prompt нового thread. При необходимости агент может прочитать доступную историю через API.

У приложения нет общего бюджета шагов, времени или токенов для native задания. Конкретные SDK/сеть/провайдер сохраняют собственные технические ограничения. Старый inspection timeout 180 секунд на модельный вызов и старое окно «восемь раундов / 240 секунд» не управляют native запуском. Кнопка «Остановить» отправляет отмену CLI. Остановка или потеря связи не откатывает сделанные изменения: исход уже запущенной команды может требовать проверки. После перезапуска сервиса незавершённый job становится `unknown` и не запускается автоматически повторно.

## Прогресс, результаты и файлы

Интерфейс показывает engine `codex-cli`, native thread ID, текст прогресса и реальные события команд/изменений файлов. Прежние исследовательские фазы и активные кнопки подтверждения patch не используются. Исторические карточки предложений могут отображаться как архив, но не являются способом выполнить новый код. Ошибка CLI остаётся ошибкой; скрытого fallback к прежнему planner нет.

Ответ поддерживает Markdown/GFM, таблицы, сноски, безопасные ссылки и встроенные разрешённые изображения. CLI создаёт документы и изображения обычными программами, доступными в контейнере; прежнего allowlist PDF/DOCX/SVG/TXT/CSV, шаблона SVG из подписей и квоты `code.propose` для native действий нет. Конкретный формат требует установленного подходящего инструмента. Сырые HTML/опасные URL в браузерном ответе по-прежнему не исполняются.

Чтобы передать готовый файл пользователю, агент вызывает `bervel-export <path>`. Helper загружает реальный файл в существующий ArtifactService, получает подтверждённые метаданные и записывает export record. Workflow сверяет artifact ID и доступ текущего actor/scope, строит обычную карточку просмотра/скачивания. Сообщение модели «файл создан» само по себе не создаёт attachment. Ошибка загрузки или чужой/отсутствующий artifact показывается как неподтверждённое вложение. Файл может быть создан в проекте, но оставаться недоступным в UI до успешного экспорта.

## Реальная среда и данные

Codex работает в настоящем RW-корне `/workspace/project`, связанном с `C:/OSPanel/home/bervel.local`. Это не копия проекта и не предварительно замаскированный snapshot. Образ `codex-agent` содержит Python 3.12 с runtime/pytest, Node 24/npm, SDK/CLI, Git, ripgrep, curl и Docker CLI 29. У Codex есть Docker socket и сети codex/default/inspection-tests; он может работать с BERVEL через API, Docker и исходники. Изолированная `inspection-test-postgres` с `public.vector` доступна для тестов; выбор безопасного тестового окружения — обязанность выполняющего задачу агента, а не закрытый test broker.

Правки файлов не означают автоматической публикации: BERVEL не запускает самостоятельный post-patch deploy hook. При этом сам CLI имеет реальные команды Docker/сборки и может выполнить нужную установку в рамках прямой задачи и пользовательских правил. Нет старых технических квот patch 20 файлов/2 МиБ/существующие parent directories или ограничения тремя диагностическими командами. Нельзя трактовать это как отмену правил пользователя или разрешение несвязанных действий.

Пользовательский запрос и инструментальный контекст модели не фильтруются и не нарезаются приложением. Секреты скрываются только после CLI — при показе/сохранении отображаемых событий и истории. Превью команд/прогресса может быть коротким; это не сокращает raw CLI input, context или final answer. Агент обязан не печатать и не экспортировать credentials. Display-фильтр не гарантирует распознавание неизвестного секрета в произвольном файле и не является доказательством очистки содержимого экспортированного attachment.

## Запуск и обслуживание

Из корня проекта `.dev/scripts/docker.ps1 -Action init` сохраняет существующие секреты и добавляет недостающие локальные настройки. `BERVEL_ENGINEERING_HOST_PROJECT_ROOT` — настоящий абсолютный путь Docker host с прямыми слешами, например `C:/OSPanel/home/bervel.local`; Windows helper передаёт его явно вместо контейнерного `/workspace`. Compose project binds используют этот host path, чтобы Docker CLI внутри Linux-контейнера не подменил путь своим `/workspace/project`.

Штатный полный запуск — `.dev/scripts/docker.ps1 -Action start -Mox` с существующей MOX-привязкой либо без `-Mox` для отдельного провайдера. Он управляет всем стеком; для проверки уже работающей установки его повторять не требуется. Codex теперь собирается главным Dockerfile target `codex-agent`; API и workers — согласованным runtime image. Native CLI использует прежний выбор provider/model, существующий `codex_state` и внешние readonly MOX auth/config/CA bindings. Не нужно менять или пересоздавать внешние auth/config, VPN или OSP.

Reader остаётся private сервисом для post-CLI display masking и совместимости исторических операций; его RO-границы не ограничивают native CLI. Прежний `inspection-executor` больше не является зависимостью нового инспектора и удаляется адресно после успешной native установки. Основная схема остаётся `0018_inspection_engineering`; новые native jobs/thread mapping хранятся в codex_state, миграции 0019 нет. Основной PostgreSQL ради native режима не пересоздаётся. Изолированный test PostgreSQL использует tmpfs и readonly `docker/inspection/test-init.sql` для `CREATE EXTENSION ... vector`; на уже работающей установке extension предварительно проверен.

API/workers/reader/codex соответствуют проверенным source hashes; старый executor удалён адресно. В точечном r2 обновлены только Codex runner (штатные retry defaults) и frontend inline artifact preview; API/workers/оба PostgreSQL сохранили IDs. # Обновление 2 ноября 2026: файлы и графики

Оригиналы и CLI export больше не ограничены 5 МиБ. Загруженный оригинал и скачиваемый поток сохраняют SHA256; повтор той же команды не создаёт новый artifact. В API временные upload-файлы должны спулироваться на дисковый originals volume (`TMPDIR=/data/objects`), а не в tmpfs `/tmp`. Голосовые записи и лимиты отдельных декодеров/модельного контекста — отдельные ограничения.

В «Проверке» fenced `mermaid` отображается схемой, fenced `html` и HTML-вложения — изолированным интерактивным просмотром. HTML должен быть автономным, без CDN/HTTP: родительский CSP блокирует сетевые переходы iframe, внутренний CSP — загрузку ресурсов. Оригинал скачивается прежним способом. На ошибке Mermaid доступен текст исходника. Сырой HTML по-прежнему не исполняется в DOM самого приложения.
