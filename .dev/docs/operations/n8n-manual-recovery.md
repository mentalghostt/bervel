# Предлагаемый порядок ручного восстановления n8n для ядра v0.1

Дата: 14 октября 2026. Статус: подробная процедура предложена по [результатам этапа 2](../quality/core-stage-2-n8n-manual-report.md), не принята в эксплуатацию. Профиль n8n с ручным восстановлением по исходной версии и защитой ядра от дублей принят для разработки в [ADR-0002](../adr/0002-durable-orchestration.md). Дежурство, роли и время реакции ещё не назначены. Это описание будущей процедуры; очереди восстановления и её защита в приложении пока отсутствуют.

## Ответственность

Оператор восстанавливает техническое исполнение в пределах своих полномочий. Владелец бизнес-процесса решает вопросы неизвестного внешнего эффекта и допустимости дальнейшего действия. Ручной повтор не заменяет одобрение конкретной редакции документа. Модули Open Server включает или переключает пользователь; эта процедура не разрешает агенту управлять их состоянием.

## Порядок

1. Найти аварийное исполнение в списке ошибок. Сопоставить его с процессом ядра, модулем, исходной версией, точными входами и последним сохранённым этапом. Один лишь статус `crashed` недостаточен.
2. Проверить `retrySuccessId` и дочерние исполнения `retryOf`. Если восстановление уже успешно завершено либо находится в работе, не запускать ещё одно. Сверить состояние ядра; при расхождении оформить разбор. В испытании родитель оставался `crashed` даже после успешного повтора.
3. Проверить состояние эффекта последнего шага. Если результат известен и операция допускает повтор по прежнему ключу, можно продолжать. Если адресат мог получить внешнее действие, но подтверждение отсутствует, выполнить сверку с владельцем процесса. Не заменять неизвестный исход новым ключом или повтором «с начала».
4. Зафиксировать одну команду восстановления, оператора, основание и ожидаемое состояние процесса. Реализация ядра должна атомарно допускать одну действующую команду и возвращать прежний результат при её повторной доставке. Ручная дисциплина оператора не заменяет такую защиту: n8n в испытании допустил два одновременных повтора старой аварии.
5. Выбрать повтор с исходной схемой — **Retry with original workflow**. Сохранить прежние входы и ключи публикации. Повтор с текущей сохранённой схемой является иной обработкой и требует отдельного решения; изменения в редакторе не разрешают изменить семантику старого процесса. Обе опции описаны в [документации n8n](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions.md).
6. Сохранить ID нового исполнения и связь с исходным. Проверять реальные статусы: ожидание решения сотрудника, завершение либо новая ошибка. HTTP 200 не означает завершённого бизнес-процесса. При потере ответа сначала искать уже созданную попытку; не нажимать повтор ещё раз вслепую.
7. При конфликте ключа и тела остановить восстановление и разобрать причину. Не подавлять конфликт, не перезаписывать прежний результат и не выдавать новый ключ ради прохождения. В MR04 новая схема под старым ключом была отклонена без изменения сохранённого эффекта.
8. После завершения сверить сохранённый результат и журнал. Отметить восстановление в очереди, сохранив историю родителя и попыток. Дальнейшее предметное согласование выполняется по правилам точной редакции и актуальности источников из [спецификации](../architecture/12-core-v0.1-spec.md).

## До включения в продукт

При реализации требуется уточнить публичную команду восстановления, её права, конкурентные изменения состояния, регистрацию попыток и обработку неизвестного ответа движка. Эти детали не добавляются в принятую спецификацию без согласования. Стабильный программный способ управления n8n ещё не выбран; обращения стенда к API интерфейса не становятся зависимостью приложения автоматически.

Нужно назначить владельца наблюдения за очередью, доступные часы реакции, эскалацию, сроки сохранения истории и проверку после обновления движка. Время восстановления из искусственного стенда не принимается за SLA или RTO. Отдельно проверяются отказ БД/Redis, резервное копирование и восстановление площадки.

Запись результата остаётся ответственностью ядра и владеющего компонента; n8n отвечает за техническое исполнение и штатный повтор. Второй собственный оркестратор для этого профиля не создаётся. Файлы процедур и испытаний находятся в `.dev`; приложение должно устанавливаться и работать без них.
