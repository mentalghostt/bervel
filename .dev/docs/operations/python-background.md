# Фоновая обработка на Python

Историческая инструкция: учебный CSV-сценарий удалён 26 октября 2026. Его команды API ниже больше не доступны. Worker продолжает выполнять чат и радар; текущее устройство — [после удаления учебного CSV](../architecture/20-retired-educational-csv.md).

С 22 октября 2026 для фонового CSV используется Python и PostgreSQL. n8n и Redis удалены из рабочего запуска. [Решение](../adr/0005-python-background-processes.md), [устройство](../architecture/15-python-background-processes.md).

```text
Запрос на обработку → API → сохранённое задание в PostgreSQL
                                      ↓
                              Python-исполнитель
                                      ↓
                    прочитать оригинал → разобрать CSV
                                      ↓
                    сохранить строки и завершить попытку
```

Загрузка с сайта по-прежнему использует прямой API: сохраняет оригинал и затем получает строки. Она не обязана ждать фонового исполнителя. Фоновый API — отдельный способ обработать уже сохранённую редакцию CSV.

## Запуск

Из корня проекта в PowerShell:

```powershell
.\.dev\scripts\docker.ps1 -Action start
.\.dev\scripts\docker.ps1 -Action status
docker compose logs --tail 50 worker
```

`start` запускает PostgreSQL, миграции, API, сайт и `worker`. Исполнитель использует тот же установленный Python-пакет и хранилище оригиналов, что API. Код и обычный запуск не требуют локальных Python, Node или Open Server Panel. Для разработки `-Action dev` наблюдает и за API, и за исполнителем.

## Запуск через API

Нужен ключ приложения с `process:start`, `artifact:read` и `dataset:publish`. Тело запроса `POST /api/v0.1/demo/document-review/processes`:

```json
{
  "artifact_id": "UUID уже сохранённого файла",
  "artifact_revision": 1,
  "command_key": "уникальная-команда-обработки"
}
```

Ответ 202 содержит ID процесса. `GET /api/v0.1/processes/{id}` возвращает состояние, попытки и ссылку на результат. `GET /api/v0.1/processes` показывает процессы своей области данных. Для чтения нужны `process:read`, `artifact:read` и `dataset:read`.

Повтор того же ключа команды с теми же параметрами возвращает прежний процесс. Изменённые параметры под прежним ключом дают конфликт. Разные ключи означают разные намеренные запуски; одинаковое содержимое файла само по себе не запрещает новую загрузку.

## Прерывание и восстановление

Исполнитель держит блокировку PostgreSQL на время работы. Второй исполнитель пропускает занятое задание. При разрыве соединения блокировка освобождается сервером БД; это не обещание мгновенного обнаружения сетевого разрыва.

`POST /api/v0.1/processes/{id}/reconcile` проверяет состояние. Если исполнитель уже не владеет незавершённой попыткой, возвращается `RECOVERY_REQUIRED`. Оператор с `process:recover` может вызвать `/recover`, указав новый ключ команды, ожидаемый номер попытки и причину. Активное или ещё ожидающее в очереди задание повторно запустить нельзя.

Новая попытка сохраняет исходную редакцию CSV. Опоздавшая старая попытка уже не может записать результат. Запись строк и завершение процесса происходят одной транзакцией. Ошибка CSV даёт `FAILED`, сохраняя оригинал. Ошибки разбора не повторяются автоматически.

Старые завершённые процессы и результаты доступны для чтения. Процессы с исторической схемой выведенного движка не запускаются новым исполнителем: для новой обработки нужен новый ключ команды и ссылка на сохранённый оригинал. Исторические учебные сценарии ожидания не переносятся в Python автоматически.

Проверки используют отдельную тестовую базу и хранилище. Тесты очереди включают конкурентный запуск, принудительное завершение отдельного Python-процесса, явное восстановление, позднюю попытку, откат публикации и сохранение точной редакции источника.
