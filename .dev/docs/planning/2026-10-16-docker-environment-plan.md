## Как устроены локальный запуск и контейнеры

Локальная разработка означает, что вся необходимая система работает на компьютере разработчика: интерфейс, API, PostgreSQL и, когда нужен профиль оркестрации, Redis и n8n. Каталог `bervel.local` содержит исходники и конфигурацию; исполняют их процессы с соответствующим окружением.

Серверный запуск означает размещение приложения и нужных сервисов на отдельной машине, например Linux VPS. Пользователь открывает интерфейс по сетевому адресу. Деление на контейнеры при этом может остаться тем же; добавляются настройка внешнего доступа, HTTPS, эксплуатация и требования к сохранности данных. PostgreSQL является серверной программой даже тогда, когда работает локально на компьютере разработчика. Слово «сервер» в вопросе об охвате обозначало отдельную машину размещения.

Контейнер — запущенный процесс с изолированным окружением и собственной ролью. В контейнере API находятся Python, код BERVEL и библиотеки FastAPI/SQLAlchemy; отдельный контейнер на каждую библиотеку не нужен. Frontend, PostgreSQL, Redis и процессы n8n имеют другие роли и свои контейнеры.

Dockerfile описывает сборку образа — подготовленного окружения с программой и зависимостями. Контейнер запускается из этого образа. Compose описывает, какие контейнеры нужны, как они соединяются, где лежат данные и в каком порядке проверять готовность. Docker Desktop с WSL 2 обеспечивает среду выполнения Linux-контейнеров на Windows.

В локальном профиле разработчик продолжает редактировать файлы в `C:/OSPanel/home/bervel.local`. Согласованное подключение исходников позволяет процессам в контейнерах видеть изменения. Установленные пакеты Linux не смешиваются с Windows venv и `node_modules`. Перенос папки проекта в WSL не является частью предложения.

Путь загрузки CSV:

1. Браузер на Windows показывает интерфейс, который отдаёт контейнер frontend.
2. Интерфейс посылает запрос `/api`; frontend передаёт его контейнеру API по имени сервиса `api`.
3. API проверяет ключ и файл, сохраняет байты оригинала в постоянное файловое хранилище.
4. API сохраняет метаданные и строки результата в PostgreSQL по имени сервиса `postgres`.
5. Браузер получает ID и результат. После пересоздания контейнеров БД и оригиналы должны остаться в постоянных хранилищах.

Redis хранит очередь задач для выбранного профиля n8n. Он не заменяет PostgreSQL и не нужен текущей прямой загрузке CSV. Основная БД, файлы оригиналов и очередь имеют разное назначение. Именованный volume — управляемое Docker постоянное хранилище; место его физического хранения обсуждается отдельно ниже. Наличие volume не заменяет резервную копию.

## Препятствия для переноса

1. `Settings.__post_init__` в `src/bervel/config.py` допускает только loopback-адрес. Контейнерный API должен слушать интерфейс контейнера, обычно `0.0.0.0`. Это изменение существующего ограничения: тест `test_configuration_has_no_server_or_development_path_defaults` сейчас прямо требует отклонять такой адрес.
2. Vite по умолчанию направляет `/api` на `127.0.0.1:8011`. В контейнере этот адрес обозначает сам frontend. Уже предусмотренная переменная `BERVEL_API_TARGET` позволяет задать `http://api:8011` без изменения браузерного контракта.
3. Миграции запускаются отдельно командой `python -m bervel migrate`. При создании API происходит обращение к таблицам, поэтому БД и миграции должны завершить подготовку раньше API. Одного порядка запуска процессов недостаточно.
4. Рабочая БД и файлы оригиналов хранят разные части одного состояния. Перенос только SQL оставит ссылки без файлов. Адаптер файлов использует атомарное создание hard link через `os.link`; работу выбранного хранилища нужно проверить в Linux-контейнере.
5. PowerShell-helper привязан к Windows venv и адресу PostgreSQL `127.0.1.49`. Инструменты браузерной проверки рассчитывают на локальные процессы API/Vite, Edge и Playwright из кэша Codex. Это нужно заменить воспроизводимым профилем проверок, сохранив существующий локальный запуск как отдельный способ.
6. Прямые Python-зависимости закреплены в `pyproject.toml`, но полный снимок находится в `.dev/requirements-core-stage-3.1.lock`. Рабочая сборка приложения не должна читать `.dev`. Для воспроизводимой Linux-сборки нужен отдельный runtime lock вне `.dev`; существующий снимок нельзя объявлять проверенным для Linux без установки и проверки.
7. n8n пока не связан с API приложения. Его тестовые workflow обращаются к наблюдателю по `127.0.0.1:5689`, а проверочные скрипты управляют локальными Node-процессами. Контейнерный профиль эксперимента должен учитывать эти адреса и способ управления своими процессами.
8. Корневой `.gitignore` исключает `.env` и `.env.*`, включая будущий `.env.example`. Если используется этот шаблон, понадобится точное исключение для него. Реальные ключи и пароли остаются вне Git и Docker-образов.

## Варианты окружения

| Вариант | Состав | Последствия |
| --- | --- | --- |
| Все текущие компоненты в Compose | API, frontend, PostgreSQL; n8n/Redis по отдельному профилю | Рекомендуется для поставленной цели: единый способ запуска, меньше зависимостей от Windows и панели |
| Только инфраструктура в Compose | PostgreSQL/Redis/n8n в Docker, Python и Node на Windows | Проще сохранить текущие инструменты, но локальные версии runtime и пакетов по-прежнему надо обслуживать отдельно |
| Единое окружение сразу для разработки и сервера | Дополнительно сборка статического интерфейса, внешний HTTP-вход, HTTPS, эксплуатация | Имеет смысл при известной серверной площадке; сейчас расширяет число решений и проверок |

Предлагаемая основа: один `compose.yaml` с сервисами `postgres`, `migrate`, `api`, `frontend`. `migrate` — короткая подготовительная задача на том же образе, что и API. PostgreSQL имеет отдельные базы и роли для приложения, тестов и при необходимости n8n. На этом масштабе отдельный сервер PostgreSQL на каждый компонент не требуется.

Профиль оркестрации добавляет `redis`, `n8n-main` и `n8n-worker`. Он переносит уже выбранное окружение n8n, но не реализует следующую стадию интеграции с ядром. Один и тот же сохранённый ключ шифрования нужен main и worker. При выборе внешних task runners соответствующий контейнер добавляется к worker и закрепляется той же версией, что n8n. Состав runners проверить по используемым узлам workflow; существующий HTTP/Wait-эксперимент не является основанием добавлять обработку произвольного кода. См. [queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode.md) и [task runners](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners.md).

Qdrant, S3/MinIO, OCR, модель и собственный фоновый worker ещё не являются зависимостями реализованного CSV-сценария. Добавлять их при появлении использующей их функции. Docker не устраняет зафиксированные ограничения восстановления n8n и не реализует отсутствующие бизнес-механизмы.

## Принятые решения реализации

- Охват: локальное окружение с переносимой Linux-сборкой. Production-площадка не настраивается без её параметров; проверен как статический frontend, так и профиль разработки.
- Хранение согласовано пользователем 16 октября 2026 после объяснения вариантов: именованные Docker volumes для постоянных данных BERVEL и штатное хранилище Docker для образов, физически в существующем диске `C:/Users/Evan/AppData/Local/Docker/wsl/disk/docker_data.vhdx`. Это точное разрешённое исключение из размещения материалов внутри рабочего корня. Исходники остаются в `C:/OSPanel/home/bervel.local`, резервные выгрузки — в `.dev/local/docker` внутри проекта. Перенос или перенастройка диска Docker не требуются.
- Compose обращается к хранилищам по именам, например `bervel_postgres_data` и `bervel_objects`. Windows-путь диска не становится параметром приложения; на Linux-сервере volumes создаются в хранилище того сервера. Пересоздание контейнера сохраняет подключённый volume. Резервные копии создаются отдельно. [Документация Docker по volumes](https://docs.docker.com/engine/storage/volumes/).
- Учебная история перенесена комплектом: рабочая БД приложения, три уникальных оригинала и БД n8n с прежним ключом. Исходное окружение Open Server сохранено без изменений.
- Реализовано изменение контейнерного bind-адреса API: явно заданный `BERVEL_HOST=0.0.0.0` при прежнем значении `127.0.0.1` по умолчанию. На Windows публиковать нужные порты через `127.0.0.1`; Redis и БД не публиковать без необходимости. Для DBeaver можно отдельно открыть PostgreSQL на свободном локальном порту, например 5433 после проверки.

## Общие ограничения

- VPN остаётся работающим и неизменённым. Возможные сетевые ошибки Docker исследуются без изменения VPN и его адаптера.
- Модули Open Server включает, выключает и переключает пользователь. Старые сервисы не удаляются и не перенастраиваются ради свободного порта.
- Корень проекта и привязка чата сохраняются. Новый worktree не требуется для анализа; при выборе worktree для реализации согласовать личную категорию и полный допустимый путь отдельно, начать с актуальной ветки `core`.
- В обычном режиме каждый этап и новая развилка требуют выбора пользователя до зависимых изменений. Согласование общего плана не разрешает выполнить все этапы подряд.
- В текущем основном checkout Git-операции изменения выполняет человек. Этот план не предусматривает автоматические staging, commit, переключение веток, fetch/pull, push или PR.
- Рабочая сборка и запуск приложения не требуют `.dev`. Документация, тестовые инструменты, отчёты и резервные выгрузки остаются внутри `.dev` рабочего корня.
- Контейнеризация не включает реализацию этапов ядра 3.2/3.3, промышленной авторизации, тендерных интеграций, актуальности предметных данных или коммерческой поставки.
