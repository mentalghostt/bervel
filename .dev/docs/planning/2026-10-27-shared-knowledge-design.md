Все загружаемые оригиналы проходят извлечение, структурное разбиение, OpenAI Embeddings и индекс PostgreSQL/pgvector. Чат и радар используют общий DocumentMemory. Формат без декодера получает явный unsupported/metadata_only, не выдуманные эмбеддинги. Старые оригиналы предварительно сохраняются в .dev с проверкой SHA256, затем удаляются из активного каталога и повторно загружаются через штатный API. Исторические чаты/отчёты и их редакции сохраняются: удаление из каталога логическое, с tombstone в artifacts.

## Решение

- Развивать core; один существующий worker, без новых очередей/контейнеров ИИ и отдельной векторной БД. PostgreSQL17 с установленным pgvector собирается поверх прежнего закреплённого образа; volume не пересоздаётся. CREATE EXTENSION выполняется администратором, таблицы миграцией0008.
- Оригиналы остаются в FileObjectStore, источники/редакции — ArtifactService. Регистрация оригинала и постановка индексации атомарны в PostgreSQL.
- DocumentReader сохраняет страницы/строки/таблицы. Разбиение детерминировано по абзацам/предложениям и строкам таблиц, с контекстом заголовков; длинные блоки делятся без потери текста. Обычная граница около1500символов, embedding input ограничен6000байт UTF-8, что консервативно укладывается в8192токена text-embedding-3-small. Без LLM-вызова для разбиения. После измерения квоты добавлен точный токенизатор cl100k_base.
- Эмбеддинг-клиент отделён от клиента генерации. OpenAI /v1/embeddings, text-embedding-3-small,1536измерений, TLS проверяется; секрет только в BERVEL_EMBEDDING_API_KEY. MOX /v1/embeddings вернул HTTP403; отдельный OpenAI ключ получен, проверка HTTP200. Работающий временный провайдер local описан выше. Не перенастраивать доступ Codex ради эмбеддингов.
- Порции ограничены64элементами/8000токенами, каждый вход6000байт; последовательные вызовы с интервалом5секунд и бюджетом32000токенов за скользящую минуту при измеренном лимите40000TPM. При429/неизвестном исходе фиксируется ошибка, автоповтора нет. Успешные порции сохраняются, ручное продолжение не повторяет готовые векторы.
- knowledge_jobs: редакция, статус/ошибка, количество готовых фрагментов, состояние исполнения. knowledge_chunks: ordinal, текст/локатор, embedding_input, hash, модель/версия, vector. Фрагменты публикуются атомарно на уровне порции; готовность файла подтверждается полным покрытием. Подготовка/токенизация большого файла выполняется один раз, готовые части используются следующими порциями.
- Для local используется настоящий токенизатор модели и предел512токенов; при превышении структурные фрагменты делятся дальше без обрезания. Модель скачивается один раз в runtime volume embedding_models, индексирование и поиск выполняются локально. Документы внешним альтернативным провайдерам не отправляются.
- Индексирование проходит по одной ограниченной порции за итерацию worker, между ними возможен чат. Статусы доступны API и странице файлов. Ошибки извлечения и недоступность embeddings видны пользователю.
- Поиск ограничен разрешёнными точными редакциями. Векторная близость плюс лексическое ранжирование объединяются; возвращаются исходные выдержки, не векторы, с именем/редакцией/страницей/строками и признаком неполноты. Проверка доступа и целостности оригинала сохраняется. Ни старые редакции, ни другой scope не попадают в контекст.
- Радар сохраняет полное чтение выбранного профиля через тот же индекс и строгие ограничения полноты; не заменять полный проход радара top-k-поиском. Товарные/сроковые правила остаются в модуле радара.

## Проверки результата

1. RED/GREEN: границы фрагментов, отсутствие потери текста/табличных заголовков; HTTPadapter неверный JSON/размер/NaN/429/TLS; реальный pgvector поиск, доступ/scope/редакции, постановка/порции/продолжение/ошибки, готовность загрузок.
2. Полные существующие backend/browser проверки; установка wheel/API/worker без зависимости от.dev.
3. До удаления: полный pg_dump + оригиналы/манифест, сверка каждого файла с metadata sha256/size. Логическое удаление только после успешной проверки; повторная загрузка новым ID, сверка байтов, статус индекса.
4. До изменения поиска сохранить лексический baseline на фиксированных вопросах. После — те же вопросы/те же источники, Recall@k и фактические ответы тестового чата. Проверять перефразирование, точные обозначения, смешанные лоты, неизвестные данные, отрицательные примеры. При отсутствии улучшения — исследовать фрагменты/представление и повторять тот же набор, не подменять критерий.
5. Не объявлять доказанным общее повышение точности по одному удачному вопросу. Сохранить входы, разметку ожидаемых источников, найденные фрагменты/метрики/ответы и ограничения.
