# Разделение фоновых обработчиков

Уточнение текущей задачи: пользователь требует независимое параллельное выполнение загрузки/индексации, чата и радара. Выбран порядок: подготовить сейчас, установить после окончания текущей индексации. Основной корень C:/OSPanel/home/bervel.local, ветка core; Git только для чтения. Работа продолжает текущую автономную задачу; активные контейнеры при подготовке не менять.

## Решение

Один образ Python-приложения, три отдельных контейнера и явная обязательная роль worker: `knowledge`, `chat`, `radar`. Каждый процесс вызывает только свой обработчик. Оригиналы принимает API, длительную подготовку выполняет knowledge-worker. Очереди уже разделены таблицами/контрактами PostgreSQL; брокер и новые БД не нужны. Ошибка/ожидание одного worker не занимает цикл другого.

Общий Codex-runner допускает максимум два параллельных запроса с отдельным SDK-thread/контекстом для каждого. Третий запрос получает явный MODEL_BUSY; бесконечной очереди процессов и автоматических повторов нет. Это снимает существующую единственную блокировку генерации чата/радара. Внешняя квота провайдера остаётся общей.

Для OpenAI embeddings выделить 24000 токенов/минуту knowledge-worker и 8000 chat-worker. Суммарно 32000 при наблюдаемом лимите 40000, с запасом для небольших служебных проверок. Радар читает полный профиль без embedding-запроса. Полученный HTTP-заголовок может только уменьшать, но не повышать выделенный роли бюджет. Такой фиксированный бюджет соответствует трём текущим процессам; произвольное масштабирование реплик без общего лимитера не заявляется.

## Этапы и проверки

1. RED/GREEN ролей worker и CLI: обработка только своего типа, обязательная валидная роль, корректная остановка/освобождение ресурсов. Обновить Compose основного/тестового/dev окружения и docker.ps1. Не оставлять активный комбинированный worker.
2. RED/GREEN двух параллельных генераций, ограничения третьей, освобождения слота после ошибки и отсутствия смешивания запросов. RED/GREEN embedding-бюджета после HTTP-ответа. Внедрить выделенные бюджеты в сборке приложения.
3. Полные backend/runner проверки, проверка разрешённого Compose без вывода секретов, сборка отдельных кандидатных образов. Независимое ревью изменений; исправления и необходимые повторные проверки.
4. Дождаться готовности оставшегося Excel и завершения двух контрольных чатов. Сохранить состояние/образы; мягко остановить прежний worker, подтвердить отсутствие активной генерации. Установить новые API/Codex/три workers без изменения внешних MOX auth/config, volumes и VPN. Проверить роли процессов, доступность API, независимость от остановки одного worker и фактический параллельный runner в тестах.

## Границы

Одинаковая БД, хранилище, настройки модели и квоты провайдера сохраняются общими. Это изоляция исполнения фоновых сценариев, а не независимые микросервисы. Не добавлять workers для несуществующих модулей, Kafka/Redis, универсальный scheduler или отдельный DI-контейнер. API и бизнес-правила модулей не менять ради разделения процессов.

Текущую индексацию не перезапускать. Уже полученные векторы и прогресс сохранить. Сравнение качества выполнять на установленной версии до переключения; после переключения проверить соответствие установленного кода подготовленному исходнику.
