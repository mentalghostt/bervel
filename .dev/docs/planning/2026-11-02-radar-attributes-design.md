## Поведение

Для API единственный источник товарного анализа — Objects. Если состава нет вообще, читается приложение с описанием объекта закупки; название закупки, реквизиты и обоснование цены не становятся источником товаров. Наличие неполного Objects не разрешает заменять его другими данными. Каждая позиция сохраняет своё имя, количество, единицу, цену, все характеристики, единицы значений и FillingInstruction, а также происхождение.

Склад передаёт все фактические технические поля и характеристики. Служебные метаданные и исходные требования тендера не становятся свойствами товара. Не требовать стандарт/прочность/покрытие/резьбу, если конкретный объект их не требует. Сравнивать все заданные требования, включая диапазоны, размеры и шаг. Противоречие или недостающий требуемый параметр запрещают подтверждённое соответствие. Дополнительный параметр своего товара сам по себе не мешает соответствию.

Текущий склад 35 SKU имеет data_kind=mock. Подготовить новый явно маркированный МОК-источник с применимыми недостающими свойствами и массами для перевода в штуки; сохранить прежние SKU, остатки, себестоимость и единицы. По уточнению владельца удалить sale_price из нового склада: продажную цену задаёт тендер. Импорт нового склада требует unit_cost, а не sale_price. Исторический загруженный оригинал не изменять. Обоснования синтетических масс сохранять отдельно; они не являются реальными измерениями. Произвольные параметры поддерживаются через technical_parameters без создания колонки на каждое имя из API.

Готовность одного тендера = 100 × Σ подтверждённо покрытых штук / Σ всех требуемых штук. Для кг количество штук = масса / weight_per_piece_kg подтверждённого SKU, для г/т сначала привести массу к кг. Для комплектов/упаковок нужен явный размер состава. Исходные количества и цены сохраняются; пересчёт в эквивалент штук выполняется Decimal без промежуточного округления. Повторное использование одного SKU внутри тендера расходует общий остаток. Тендеры друг другу остаток не резервируют. Неподтверждённые позиции в штуках дают нулевое покрытие, но остаются в знаменателе. Если невозможно достоверно получить знаменатель, процент null с точной причиной, не фиктивные 0 или 100.

Выручка = Σ количества в исходной единице тендера × цену этой позиции из тендера. Затраты = Σ соответствующей потребности × себестоимость SKU с корректным преобразованием единиц. Прибыль = выручка − затраты. Маржа = 100 × прибыль / выручка. Атрибут выгоды ограничен [-100,100], фактическая маржа и суммы сохранены. Неполная стоимость закупки не выдаётся за полную; отсутствие сопоставления, цены, валюты или себестоимости объясняется. Наличие остатка не является условием математического расчёта себестоимости известного изделия.

## Контракт между задачами

TenderRecord дополнительно получает analysis_source: api_objects | description_attachment | unavailable; procurement_objects: list[dict]. Объект: object_id, name, quantity, unit, unit_price, total_price, currency, characteristics. Характеристики сохраняются в формате Контур Name/Values.Value/Values.Okei/FillingInstruction. description — точный читаемый текст этих объектов для существующих цитат; title для API не используется как товарное доказательство. Старые записи без новых полей совместимы.

StockItem.specs сохраняет плоские технические значения; characteristics — массив фактических характеристик; weight_per_piece_kg — положительная строка Decimal либо null. technical_parameters.source_requirements не считать складским фактом. Для иных технических полей не вводить закрытый перечень из пяти имён.

Новый отчёт schema_version=1.6.0. У каждой записи: readiness_percent: str|null, benefit_percent: str|null, readiness_check: dict с reasons/required_pieces/covered_pieces/lines. economics_check сохраняется, margin_percent — фактическая маржа. analysis_status позволяет отличать проанализированный тендер от пропущенного/ошибки. Старые отчёты читаются без выдуманных процентов.

## Интерфейс

Единый список тендеров без вкладок «Можно участвовать», «Требует внимания», «Вне анализа». На карточке два заметных атрибута: готовность к участию 0–100% и экономическая выгода −100…100%. Сортировка «Сначала полностью закрываемые» (готовность по убыванию, затем выгода) и «Сначала наиболее выгодные» (выгода по убыванию, затем готовность). Неизвестные значения последними; равные значения сортируются стабильно.

Фильтры задают включительные диапазоны готовности [0,100] и выгоды [-100,100], значения от/до. При полном диапазоне неизвестные результаты остаются видимыми с причинами; при сужении соответствующего диапазона неизвестные ему не соответствуют. Отдельно показать счётчик реально прошедших анализ; непроверенные записи не получают фиктивных атрибутов. PDF показывает те же расчётные атрибуты.
