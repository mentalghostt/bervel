## Результат

Новый запуск получает выбранный склад целиком, автоматически ищет закупки по его ассортименту и показывает подтверждённое частичное/полное покрытие свободными остатками. Ручного поля ключевых слов нет. Готовность и выгода рассчитываются прежними точными правилами, после подтверждения конкретного изделия. Непроверенная похожесть, диапазонные профили и списки *_options не доказывают точные свойства детали.

## Чтение и поиск склада

- Структурированный CSV читается строгими StockImporter/EconomicsImporter из неизменяемого оригинала. Готовность общего RAG-индекса не требуется ни в UI, ни при запуске. Сохраняются права, роль, хеш и полная валидация до расходования Контур-квоты.
- Полный CSV не передаётся одним промптом. Сервер читает все строки; LLM получает полный объект закупки и полные непустые факты релевантных SKU. Непустые характеристики, инструкции и неизвестность не удаляются ради размера.
- Сохраняется гибридный поиск: локальная E5-модель, уже предусмотренная приложением, плюс лексические и структурированные признаки. Radar владеет отдельным компактным индексом товаров в памяти с ограниченным кешем по хешу склада и версии модели. Глобальный RAG, его провайдер и индексы других модулей не переключаются.
- Для локальной модели используется закреплённый уже имеющийся кеш без обращения к API эмбеддингов. Разбиение поискового представления укладывается в512токенов; это не общий файловый чанкинг177-колоночной таблицы. Сохраняются ссылки на исходныйSKU/строку.
- Результат поиска — кандидаты. LLM и серверная проверка требований подтверждают соответствие. Отсутствие совпадения в ограниченной выдаче не объявляется доказанным отсутствием товара. Пустые свойства не сериализуются в промпт; все непустые остаются.
- Качество проверяется на размеченных парах из реальногоCSV и ранее подтверждённых позиций, включая синонимы, соседние размеры, шаги, покрытия, первую/среднюю/последнюю строки. Нельзя обещать равенство моделей без измерения.

## Автоматический Контур-поиск

- Термины выводятся из product_group/product_subtype/product, нормализуются и дедуплицируются. Используются только представленные на складе семейства. Общие металл/метизы/крепёж не должны размывать поиск при наличии конкретных типов.
- Перед применением основ слов проверить действующий API на одинаковых датах/стадиях: шайб/шайба/шайбы, болтокомплект и формы. Если основы не дают подтверждённого нужного охвата, использовать явные формы единственного/множественного числа. Неподтверждённый OR-синтаксис не вводить.
- Несколько самостоятельных поисков по семействам объединяются поID, равномерно формируют пул, общий предел полных карточек остаётся выбранным max_tenders(1–100). Повторные карточки не запрашиваются заново. Поисковые страницы также ограничены; реальные обращения/ограничение пула отражаются в источнике.
- Предварительный приоритет определяется только раскрытыми Objects/характеристиками (либо разрешённым вложенным описанием при полном отсутствии Objects). Он не равен подтверждённой готовности. Полный состав смешанного тендера сохраняется.
- В поисковой выдаче Objects отсутствуют; глобальная оптимальность по всем тысячам закупок не обещается. Приоритет относится к просмотренному пулу.
- Даты, выбранные стадии(включая завершённые/отменённые), фильтры и исторические команды сохраняются. Поле keywords скрывается из новой формы; сервер сам сохраняет эффективные слова в снимке команды.

## Анализ и устойчивость

- Новый pipeline1.7 изолирован от сохранённых1.0–1.6. APIObjects переносятся в каноническую потребность кодом, без повторного извлечения тех же чисел/характеристик моделью. Вложенное описание остаётся fallback только при полном отсутствии Objects.
- Порционирование идёт по объектам, с устойчивыми tender/object/occurrenceID, байтовым/ответным бюджетом и сохранением всех требований. Тендер с4432объектами не отклоняется из-за прежнего потолка50. Повторные объекты не схлопываются.
- Модель возвращает структурированный ответ по стабильнымID; поддерживаемый output_schema и один ограниченный repair для полученного, но невалидного ответа. Сервер не ослабляет проверку неизвестных/противоречивых параметров. Успешные проверки не повторяются при repair.
- По завершении все объекты собираются обратно; количества и цены берутся из исходного объекта. Общие остатки между повторнымиSKU, кг→штуки по подтверждённой массе, неизвестные знаменатели и деньги сохраняют правила1.6.
- Используется существующая очередь/checkpoint. В checkpoint сохраняется канонический проверенный результат, источники/версия/модель/хеш входа, а не восстановление из процентов. Временный явно отклонённый429 переводится в ожидание и возобновляется с незавершённой порции. Истинная квота/авторизация отличаются от временной частоты.
- При неизвестном исходе сетевого запроса нельзя безусловно повторять платный вызов. Выполненные этапы сохраняются, причина конкретна. Никакого completed для частичного непроверенного результата.
- Главный список результатов выделяет закупки с подтверждённым положительным покрытием; нулевые/неподтверждённые/ошибочные остаются доступными отдельно с причинами. Сортировки и диапазоны готовности/выгоды сохраняются.
