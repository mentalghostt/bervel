# Тендерный радар ИИ

Проект спецификации для согласования · 3 ноября 2026 года

## Результат для пользователя

В меню BERVEL появляется самостоятельный раздел **«Тендерный радар ИИ»**. Пользователь выбирает складской CSV, задаёт поисковую фразу и нажимает **«Проанализировать следующий тендер»**. Сервер получает один тендер через API Контур.Закупок, передаёт его позиции встроенному Codex CLI для сопоставления со складом и сохраняет карточку с проверяемым расчётом.

В первой версии запуск ручной. Один запуск обрабатывает один тендер целиком, включая все его лоты. По умолчанию поиск ограничен закупками с открытым приёмом заявок. Сервер берёт первый ещё не обработанный ID из выдачи Контура в порядке ответа API, в пределах ограниченного поиска. Если в просмотренной выдаче кандидатов нет, интерфейс сообщает об этом и предлагает уточнить фразу. Уже созданную карточку можно явно пересчитать по тому же ID с выбранным складом.

## Граница модуля

- Отдельные маршрут `#/ai-tender-radar`, API `/api/v0.1/ai-tender-radar`, Python-модуль `ai_tender_radar`, задания и хранение карточек. Все операции проверяют права и область доступа пользователя.
- Запуск идёт напрямую из нового раздела. Запуск, история, настройки, таблицы, отчёты и код модуля `tender_radar` не участвуют в работе. Сценарий проходит проверку при отключённом старом радаре.
- Общая инфраструктура BERVEL используется на уровне платформы. Это доступ к файлам с ролью `stock`, PostgreSQL и внутренний Codex runner. Контур.Закупки остаются внешним источником. У нового модуля собственный адаптер и собственный запрос, а серверная настройка учётных данных Контура может быть общей. При общем ключе квота провайдера общая для обоих разделов.

## Данные и сопоставление

1. **Сервер фиксирует входы.** Проверяет доступ к складскому CSV, читает его целиком, фиксирует ID и хеш оригинала, дату остатков при наличии. Для количества использует `free_quantity`, для идентификации `sku`, наименование, единицу и технические параметры. `unit_cost` и валюта служат входом для экономики. Отсутствие цены не блокирует проверку наличия. Карточка по тестовым данным помечается как тестовая.
2. **Адаптер Контура загружает полную карточку по ID.** Поисковая выдача нужна для выбора закупки. Состав берётся из объектов полной карточки. Сохраняются лот, заказчик, устойчивый ID строки, наименование, характеристики, количество, единица и доступные цены. Сводный состав и его разбивка по заказчикам учитываются один раз. При расхождении или неполном составе карточка фиксирует ограничение источника. Для первой версии, если Контур не раскрывает объекты, карточка получает статус «Недостаточно данных» с причиной. Анализ вложений закупки потребует отдельного согласования. [Проверка полей API по сохранённой схеме](../research/2026-11-02-kontur-procurement-objects.md) · [Документация Контур.Закупок](https://developer.kontur.ru/doc/zakupki.external_api?about=0).
3. **Codex CLI проверяет техническое соответствие.** Сервер ищет кандидатов по всему CSV, используя наименования, артикулы и технические признаки. CLI получает позицию с раскрытыми требованиями и факты по кандидатам. Для каждой позиции он возвращает ID строки, допустимые SKU, вывод и ссылки на конкретные поля позиции и склада. Большие тендеры разбиваются на порции одного задания без потери строк. Поиск по кандидатам помогает сократить контекст. Если его полноты недостаточно для вывода об отсутствии, статус позиции остаётся «Не подтверждено».
4. **Сервер проверяет ответ CLI.** Проверяет схему, состав строк, допустимость SKU, наличие доказательств и проверяемые ограничения, включая артикул, размеры, стандарт, класс и покрытие, когда они указаны. Все раскрытые обязательные характеристики должны выполняться. «Болт М12» допускает любой подтверждённый болт М12, если других требований нет. Если обязательный параметр скрыт, противоречив или его нельзя подтвердить по складу, положительное соответствие не засчитывается. Тексты тендера и CSV обрабатываются как входные данные. Для задачи используется отдельный контекст Codex CLI с ограниченным доступом, без shell, веб-поиска, ключа Контура и доступа к данным других задач. Стоимость и цены остаются на сервере. [Текущий структурированный запуск Codex в BERVEL](../../../codex-runner/server.mjs).

## Покрытие склада

Для каждой позиции сервер показывает требуемое количество, сколько выделено из доступного остатка, дефицит и подходящие SKU. Вердикт принимает одно из значений **«Есть полностью»**, **«Есть частично»**, **«Нет доступного остатка»**, **«Не подтверждено»**. Нулевой остаток подтверждается только при достаточных складских данных. Пустой остаток или непроверенная совместимость остаются неизвестными.

Свободный остаток каждого SKU распределяется один раз на весь тендер. Если одни SKU подходят нескольким позициям, сервер максимизирует покрытое количество в общей подтверждённой единице. Остаток используется в другой единице только при подтверждённом пересчёте. Для равных вариантов применяется стабильный порядок позиций и SKU. Распределение расчётное, складские остатки и резервы оно не меняет. Следующий тендер оценивается как отдельная возможность по своему снимку склада.

**Покрытие тендера = 100 × число покрытых единиц / число требуемых единиц.** Для карточки единицы приводятся к штукам. Пересчёт из кг, комплектов или упаковок допустим только по подтверждённой массе одного изделия или подтверждённому количеству единиц в комплекте или упаковке. Одна только похожесть на складской SKU не подтверждает коэффициент пересчёта. По отдельной позиции результат можно показать в её исходной единице. При неполном составе, неизвестном количестве, неподтверждённом остатке или отсутствии однозначного пересчёта, от которого зависит итог, карточка показывает «Покрытие не рассчитано» и причину. Известные результаты строк сохраняются. Значение `0%` означает подтверждённое нулевое покрытие.

## Экономическая выгода

- **Выручка по позиции** берётся из `PositionPrice`, либо из `ItemPrice × требуемое количество`, если полная цена позиции отсутствует или скрыта. Если обе цены раскрыты, суммы должны совпасть после округления до денежной единицы минимального номинала, например до копейки для RUB. Если ни одна цена не позволяет рассчитать сумму, цены расходятся или валюта неизвестна, выручка этой строки остаётся неизвестной. Общая начальная цена тендера не распределяется по строкам. Опубликованная цена задаёт сценарий оценки, итоговая цена торгов может отличаться.
- **Себестоимость по позиции** равна сумме `выделенное количество × unit_cost` по выбранным SKU. Для вердикта на весь объём нужна подтверждённая стоимость исполнения всего объёма. В первой версии подтверждённый источник затрат есть только у складского остатка, поэтому при дефиците вывод по экономике позиции остаётся неизвестным. Суммы сравниваются в одной валюте по указанным ценам. По решению владельца НДС на первом запуске отдельно не учитывается. В расчёт входят затраты, которые отражены в складской себестоимости.
- **Выгода по позиции** равна `100 × (выручка − себестоимость) / выручка` при положительной выручке. Вердикты **«Выгодно»**, **«В ноль»**, **«Убыточно»** определяются знаком разницы. Если расчёт невозможен, вывод **«Недостаточно данных»** сопровождается причиной.
- **Выгода по тендеру** считается той же формулой по суммам выручки и себестоимости всех позиций. Для общего процента нужны полный состав, сопоставимая валюта по всем строкам и известные выручка и себестоимость каждой позиции. На шкале карточки результат ограничивается диапазоном от `−100%` до `100%`. В деталях сохраняются исходный процент, признак ограничения шкалы, выручка, себестоимость и разница в деньгах. Сервер считает в десятичной арифметике. Округление применяется при отображении и при отдельной проверке согласованности опубликованных цен.

Пример покрытия. Тендер требует 100 болтов и 50 гаек. Склад покрывает 80 болтов и 50 гаек. Карточка показывает `86,7%` покрытия. Поскольку цена закупки недостающих 20 болтов неизвестна, по гайкам возможен отдельный экономический вердикт, а общая выгода не рассчитана. Если для другого, полностью покрытого тендера выручка составляет 20 000 ₽, а себестоимость 15 000 ₽, выгода составит `+25%`, разница в деньгах `+5 000 ₽`.

## Карточка и надёжность

- В списке видны название из Контура, номер закупки, **покрытие склада**, **экономическая выгода** и статус. В деталях раскрываются таблица позиций с двумя вердиктами, выделенный остаток, дефицит, цены, денежный результат, основания подбора и причины неизвестных значений. Карточка ссылается на тендер и складской снимок и показывает дату анализа.
- Раздел показывает ход работы в фоне. Открытие страницы или её обновление восстанавливает текущее задание. Один активный запуск на область доступа, повтор той же команды возвращает исходное задание. На один ID Контура в области доступа приходится одна карточка. Успешный пересчёт публикуется целиком и обновляет карточку с датой и снимком расчёта. Сбой пересчёта оставляет последнюю сохранённую версию доступной.
- Недостаток данных источника отделён от сбоя API или CLI. При частичном результате доступны проверенные строки с пометкой «Анализ неполный». Сбой либо неполнота, влияющие на итог, не превращаются в процент. Повторяемый расчёт использует сохранённые источники, проверенные решения и версию правил. При неизвестном исходе внешнего вызова автоматической повторной отправки нет.

## Этапы реализации и приёмки

| Этап | Результат | Что проверяем перед приёмкой |
| --- | --- | --- |
| 1. Самостоятельный модуль и входы | Собственное фоновое задание загружает один тендер и выбранный склад | Отключение старого радара, изоляция по правам, устойчивый ID позиции, полный CSV, повтор команды, пропуски и дубли состава Контура |
| 2. Codex CLI и расчёты | Проверенный ответ на каждую позицию и расчёт карточки по снимку | Полное, частичное и нулевое покрытие, конкуренция за SKU, ложный кандидат, неуказанный и скрытый параметр, разные единицы, отсутствие цен, нулевая и отрицательная маржа, ограничение шкалы |
| 3. Страница и сквозная проверка | Самостоятельный раздел с карточками, деталями и восстановлением задания | Реальный тендер через Контур и фактический запуск встроенного CLI, сверка процентов вручную по исходным строкам, сбой и повтор, доступность карточки после перезагрузки |

Для согласования предлагаются ручной запуск одного открытого тендера, взвешивание покрытия по штукам, оценка выгоды по ценам тендера и складской себестоимости и явное «Недостаточно данных», когда числитель или знаменатель нельзя подтвердить. Утверждение этой спецификации фиксирует правила продукта. Перед реализацией согласуется первый этап с его критериями проверки.
