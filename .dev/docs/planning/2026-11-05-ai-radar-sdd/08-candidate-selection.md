# Предварительный отбор кандидатов перед загрузкой карточек

Результат: из большого постраничного пула выбираются перспективные кандидаты, до 200 полных карточек проверяются по полноте и соответствию продукции. Подробное обоснование и диагностика — [исследование](../../research/2026-11-05-ai-radar-prefilter-strategy.md).

**Inputs.** `SettingsSnapshot`, фиксированные фильтры/время поиска; `SearchBudget{search_max,detail_max≤200,llm_max}`; `SearchPage{PageNumber,TotalCount,Items}` и `LimitGroup[]`. `Candidate{id,brief,query_refs,rank,uncertainty}` содержит только реальные search-поля; состав/полнота в нём до detail неизвестны. Источник при разработке и проверках — исключительно локальный симулятор.

**Outputs.** `SelectionResult{run_id,counters,accepted_ids,incomplete_ids,unknown_ids,irrelevant_ids,stop_reason,coverage_status}`; кандидаты, исходные страницы/карточки и основания решений в истории. Для каждого detail — `Completeness{requirements,economics,schedule,reasons}`, значения `complete|incomplete|unknown`.

**Preconditions.** Изолирован test, профиль и история готовы; контракт симулятора исправлен по исследованию, эталон скрыт от клиента. Права области и бюджета проверены; endpoint ограничен локальным тестовым адресом, production-ключ не передаётся. До полноценной приёмки добавлены случаи со сроками, корректными ценами лотов и отсутствующими сниппетами.

**Postconditions.** Сначала ветки семейство/стандарт и широкие запросы собираются постранично и объединяются по ID; затем дешёвый рейтинг и проверяемое LLM-переранжирование ограниченного пула формируют очередь. Полные карточки загружаются по уникальным ID в пределах бюджета, проходя три допуска и действующий товарный matching. Готовая подборка содержит только полные для текущего расчёта профильные карточки; неполные сохраняются отдельно с причинами. Фиксируются версия алгоритма, остаток бюджета и охват.

**Error cases & Invariants.** До detail нельзя гарантировать полноту; 200 вызовов не гарантируют 200 пригодных карточек. Нет выдуманных search-фильтров полноты/позиций/ОКПД2 или сортировки API. Нет скрытого обращения к production, fallback или автоматического расширения квоты. Недостаток сниппетов/общий заголовок не равен отказу; маскированные реквизиты не равны маскированным требованиям. Цена, остаток, мощность и отсутствие данных различаются. Срок подачи не используется как срок поставки. Квоты учитывают отправленные попытки и неизвестный исход; `limitGroups` читается как массив. Профильные полные карточки не скрываются из-за плохой экономики/сроков выполнения.

**Acceptance Criteria.** GIVEN 51 результат THEN прочитаны две страницы; GIVEN дубли в ветках THEN detail одного ID вызван один раз; GIVEN одинаковые brief и разная полнота card THEN окончательный допуск различается; GIVEN полный набор кроме срока поставки THEN `schedule=unknown`; GIVEN нулевой склад, но известная продукция THEN кандидат не исключён; GIVEN 200 вызовов, 130 пригодных THEN показаны 130 и причины остальных; GIVEN production URL THEN отказ до сети. На отложенном симуляторном корпусе: ноль ложных `complete`, все контрольные подходящие случаи найдены при достаточной квоте, рост yield относительно порядка API; LLM принимается только при пользе относительно дешёвого рейтинга.

**Реализация и проверка.** `ai_tender_radar/selection.py` владеет политикой очереди и бюджетами; `completeness.py` — допусками. В `infrastructure/kontur.py` выделить `search_page`, `read_limits`, `fetch_tender`; исходный transport сохранить с явными типами ответов. Связать с `service.py`, историей и UI счётчиков. Исправления/сценарии симулятора — `.dev/scripts/kontur_simulator.py`; тесты — `.dev/tests/test_ai_radar_selection.py`, `test_ai_radar_completeness.py`, `test_ai_radar_selection_http.py` и скрытый эталон fixtures. Порядок: контракт симулятора → бюджет/пагинация → ранжирование → допускающий фильтр → сравнение стратегий → сквозная проверка. Это внутренние шаги одной вертикали; внедрение в рабочую среду отдельно согласуется.
