# Тендерный радар ИИ — план вертикалей SDD

Дата: 05.11.2026. Статус: проект для согласования. Текущий этап — только план и спецификации.

Цель: оценивать весь тендер с учётом склада, подтверждённого производства и экономики; объяснять оценку 0–100 в отдельном AI-ревью каждой карточки и сохранять проверяемую историю.

Рабочий корень: `C:/OSPanel/home/bervel.local`, Personal, основная рабочая ветка `core`; remote `mentalghostt/bervel`, remote HEAD `main`. Это основной checkout, не worktree задачи. В дереве есть изменения нескольких сессий; Git-операции записи не выполнялись. Чужой worktree `ui-variants` вне задачи.

## Основа и границы

- Использовать действующий `src/bervel/modules/ai_tender_radar/`. Старый `tender_radar` удалён.
- Сохранить AI-сопоставление и проверку ссылок/атрибутов в `matching.py`, распределение остатка и десятичные расчёты в `calculation.py`. Текущая экономика умеет `full|confirmed`: прибыль покрытой части не доказывает прибыль исполнения всего заказа.
- Использовать существующие задания PostgreSQL, отдельный AI-worker, модельный шлюз, архивный импорт и симулятор `.dev/scripts/kontur_simulator.py`. Новый оркестратор и новые библиотеки для первой версии не нужны.
- Python/FastAPI/PostgreSQL и React/TypeScript сохраняются. API/UI передают данные; предметные правила не зависят от HTTP, SQL и LLM SDK. Сборка зависимостей — в `app_setup.py`/`ai_tender_radar_setup.py`.
- Настройки принадлежат существующей `data_scope` предприятия. Новый личный склад на каждого посетителя и новая система входа не создаются.
- LLM извлекает неоднородные требования, сопоставляет товары и объясняет. Код проверяет контракты, считает количество, мощности, сроки, деньги и балл. Для известного структурированного CSV LLM не нужна.
- Экспериментальность, участие в поиске и подтверждённое производство — разные признаки. Наличие позиции на складе само по себе тоже не доказывает собственное производство.
- Оценивается возможность исполнить весь обязательный состав карточки; самостоятельная оценка отдельных лотов допускается только при подтверждённом праве отдельного участия. Заявки, закупка недостающего у третьих лиц, резервирование и управление заводом в объём не входят.
- Новый предварительный отбор сначала собирает краткие записи постранично, затем расходует отдельный бюджет до 200 полных карточек. Полнота окончательно проверяется после detail. Разработка и тестирование только на симуляторе; самостоятельные вызовы боевого Контур API прямо запрещены пользователем, включая проверку лимитов.
- Все карточки считаются по отдельности с учётом уже подтверждённых обязательств. Высокие оценки двух карточек не означают, что их можно выполнить одновременно. Портфельная оптимизация здесь не обещается.

## Общие контракты

Существующие `StockData`, `TenderData`, `MatchingResult`, `AnalysisResult`, `JobView` расширяются совместимо. Ниже — предлагаемые новые DTO (структуры передачи данных), не уже существующий API.

| DTO | Минимальное содержание |
|---|---|
| `SettingsSnapshot` | `id, data_scope, stock_artifact_id, stock_sha256, products[], experimental_products[], include_experimental, production[], resources[], scoring_policy, created_at` |
| `Product` | `id, sku?, name, unit, attributes, enabled, manufactured_before: true|false|null, evidence` |
| `ExperimentalProduct` | `id, product_id?, name, unit, attributes, enabled`; связь с подтверждённым `Product` обязательна для допроизводства |
| `ProductionCapability` | `product_id, resource_group_id, units_per_workday, production_unit_cost, currency, setup_workdays, material_ready_at, confirmed_at, evidence` |
| `ResourceAvailability` | `group_id, calendar, free_capacity_by_day, confirmed_at`; свободная доля одного ресурсодня 0–1 после текущих обязательств |
| `ScoringPolicy` | `version, target_margin=0.30, comfortable_utilization=0.70, minimum_production_factor=0.60, high_score=80, medium_score=50, stress_price_factor=0.90, stress_cost_factor=1.10, stress_rate_factor=0.80, max_age_by_source` |
| `RunSnapshot` | `run_id, environment, data_scope, settings_snapshot_id, input_hashes, tender_snapshots[], stage_versions, created_at` |
| `FulfillmentPlan` | `status: feasible|infeasible|needs_review, stock_allocations, production_allocations, schedule, utilization, costs, assumptions, reasons` |
| `TenderAssessment` | `score: int|null, feasibility, full_economics, stock_share, production_factor, stress_score: int|null, policy_version, reasons` |
| `CardReview` | `analysis_id, state, recommendation, evidence_refs[], risks[], assumptions[], model_version, prompt_version` |

Числа и деньги передаются десятичными строками, даты содержат часовой пояс; `null` означает неизвестное, `0` — подтверждённый ноль. У каждого факта сохраняется источник. Политика задаёт предельный возраст данных; просроченные данные не дают уверенного положительного заключения. Оценка всегда связана с неизменяемыми снимками и версиями правил.

## Что подтвердить до соответствующей реализации

Предлагаемый путь импорта — файл плюс редактор настроек, с единым сохранённым снимком; конкретный внешний складской сервис не задан. Для реальных оценок завод должен подтвердить производимую номенклатуру, нормы, общие ресурсы, свободную загрузку, себестоимость, сырьё, сроки поставки и свежесть данных. Неизвестное отображается явно, тестовые числа не становятся производственными фактами.

`max_age_by_source` задаётся для склада, мощности и затрат по реальной частоте обновления источников. Если допустимый возраст не подтверждён, свежесть остаётся неизвестной и уверенная рекомендация недоступна; искусственный общий срок свежести не назначается.

Параметры score-v1 в [спеке оценки](05-scoring.md) — проверяемая стартовая политика. Они требуют калибровки на ручных оценках; утверждение «самые оптимальные веса» без таких данных было бы необоснованным. Вопросы об алгоритме решены в этой редакции; значения заводских фактов не выдумываются.

Для новой вертикали предварительного отбора подготовлены [контрактное исследование](../../research/2026-11-05-ai-radar-prefilter-contract.md) и [алгоритм с результатами HTTP-опыта](../../research/2026-11-05-ai-radar-prefilter-strategy.md). Файловые номера сохраняют идентичность документов; порядок исполнения задан таблицей выше.

Это обоснование подхода, а не источник наших численных коэффициентов.
