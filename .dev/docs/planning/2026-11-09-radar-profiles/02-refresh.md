# Вертикаль 2 — обновление единой базы

`execute_profile_refresh(pipeline,job,run,profile,stock)->None` вызывается общим RadarRuns.execute. `profile` и `stock` — актуальный сохранённый snapshot предприятия, зафиксированный при enqueue. Источник только из `pipeline.sources[operation.profile_source]`; идентичный код для обоих адаптеров.

## Этапы

1. Сохранить начальное состояние конкретного refresh, heartbeat, счётчики и immutable входы. Старые карточки остаются видимы при ошибке/остановке.
2. Ручные keywords — все фразы пользователя; auto — существующий model_search_queries по текущей включённой продукции склада. Авто-ключи сохранять с fingerprint продукции, чтобы одинаковый профиль не менял область случайно каждый раз; изменившаяся продукция позволяет обновить их. Нельзя расходовать детали для генерации/оценки briefs.
3. Поиск одним массивом Text, PurchaseStatuses=[1,4], страницы по 50, page 0..199, максимум min(200, available search), максимум 10 000 briefs. Все уникальные Id сохраняются немедленно как карточки профиля **до ИИ**. Сохранить исходные pages, счётчик attempts ДО запроса и pending. Дубликаты не удваивают карточки.
4. Обновить metadata существующих карточек, сохранив source details/позиции/документы и stable analysis_id. Свежий brief имеет приоритет для срока/стадии/цены/типа торгов, даже если full snapshot старее. Сохранить last_seen_at, search_fingerprint и факт получения подробностей отдельно от completeness.
5. При полностью успешном обходе менее 10 000 результатов ранее виденные **в той же области ключевых слов** отсутствующие карточки помечаются source_missing. При смене ключевых слов старые не делать неактуальными из-за отсутствия. Достигнутый cap, лимит квоты, неполная страница/невалидный ответ, сбой или stop запрещают массовую неактуальность. Истёкший срок действует всегда.
6. Для активных карточек без полученных подробностей: rank_briefs_with_model по всем претендентам, сохранение проверенных оценок/очереди. Высший score первым, одинаковый score — стабильный ID. Ничего не отбрасывать из общей базы. Сбой ИИ не заменяется придуманным рейтингом; briefs сохраняются, детали не тратятся.
7. Детали: min(введённая квота, доступные purchase; локальный максимум 200 при симуляторе без provider quotas). null = доступный максимум. Не связывать search budget с detail_max: при 0 поиск полный. Не запрашивать повторно карточки с details_loaded, даже при неполном составе у провайдера. Детальный запрос/unknown фиксировать ДО I/O; после неизвестного исхода не отправлять автоматически повторно. Известный 404 — отметка неактуальности source_unavailable, без удаления.
8. Для новых details — существующие enrich/match_positions/calculate/evaluate/review через `_analyze` с AI_SELECTION_VERSION. Все исходные данные сохраняются до ИИ. Для уже подробных — пересчитать соответствие/покрытие/экономику/AI-ревью на текущем складе; при появлении новых SKU переиспользовать доказательства только если они всё ещё валидны и выполнять новое сопоставление, когда прежний результат не покрывает новый каталог. Нельзя имитировать свежесть заменой даты. Не расходовать Kontur details на повторный анализ. Параллелизм моделей ограничен существующим сценарием до 4 карточек; source I/O учитывает gate.
9. Сравнительную итоговую ИИ-оценку рассчитывать существующим rate_run по актуальным агрегатам; первичный приоритет — отдельная сущность, не выдавать его за итоговый рейтинг. Полностью неизвестные метрики не подменять 0. Завершить состояние refresh/расписания, сохранить точный расход и ошибки.

## Карточка и политика root

Новые дополнительные поля RunCard: `information_state:'primary'|'full'`, `details_loaded:boolean`, `search_fingerprint:string`, `last_seen_at`, `inactive_reason:string|null`, `source_missing:boolean`, `priority_score:number|null`, `priority_reason:string|null`. `state` остаётся техническим primary/analyzing/accepted/needs_data/irrelevant/failed; пользовательских статусов полноты больше нет.

Метрики дополняются `actuality:'active'|'inactive'`, `inactivity_reason:string|null`, `trade_type:string`.

`profile_policy.py` (пишет root) экспортирует:

- `search_fingerprint(keywords:list[str])->str`: нормализованный независимый от порядка/регистра набор фраз, привязка к двум стадиям.
- `card_actuality(card:dict,now:datetime|None=None)->dict`: `{actuality,inactivity_reason}`. Причины: deadline_expired, source_missing, source_unavailable, stage_closed; флаги cancelled/abandoned и явный не-open/planned stage закрывают. Неполнота/низкое соответствие/ошибка модели актуальность не меняют. Свежий brief важнее full metadata. Непарсимая/неизвестная дата не объявляет просрочку.
- `trade_type(card:dict)->str`: `fz44|fz223|pp615|commercial|small|commercial_small|cis|unknown`. ApiSearchLaw 1/2/5/8/9/3 соответственно; 3 означает объединённую категорию commercial_small, а не догадку. CIS только при явном поле/значении источника, неизвестное не угадывать.
- `profile_metrics(card:dict,now:datetime|None=None)->dict`: существующие result_metrics + актуальность и тип, с приоритетом свежего brief; без внешнего I/O.

## Проверки

В обоих источниках: первая выдача всех briefs, второй refresh дополняет ту же базу, подробности только отсутствующим, приоритет не совпадает с порядком выдачи, квота 0 не ограничивает поиск. 10 000 → нет source_missing; 9 999 и полный обход → есть; 9 999 и quota/error → нет. Смена keywords сохраняет старые active; deadline всё равно закрывает. Stock refresh меняет реальное покрытие и анализ без нового details request; чат и analysis_id прежние. Проверить pending/unknown, source error, границу даты, planned с истёкшим сроком и два одинаковых ID разных источников.
