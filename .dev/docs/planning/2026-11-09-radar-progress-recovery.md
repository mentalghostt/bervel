Задача пользователя: сохранять обработанные результаты при прерывании, продолжать с первого незавершённого тендера; допускается повтор незавершённой оценки ИИ. После этого установить статусы фаз с точными счётчиками. Пользователь разрешил исправление неустойчивости и необходимый перезапуск первичного анализа.

## Найденные причины

- rank_briefs_with_model держит все evaluations в RAM до конца; нет durable intermediate counters.
- Полные карточки записываются до analyzed_ids checkpoint, возможен повтор после crash в этом промежутке; finally дренирует futures по порядку отправки, задерживая запись уже готовых результатов.
- claim маркирует потерявший lease job failed, но нового recovery job нет. Нельзя просто переочередить same job_id: старый worker получит возможность писать как новый.
- Сравнительный рейтинг сохраняет пакеты, но текущее reuse превращает незавершённый отчёт в unknown вместо продолжения. Нужно сохранить исходный snapshot/cohort.
- У старого текущего запуска нет checkpoint первичных оценок, но SDK rollouts существуют в `/data/codex/sessions`; подтверждённые ответы можно строго проверить и перенести. Журналы только читать, модель/runner не менять.

## Выбранное исправление

Без новых таблиц/библиотек/процессов. Существующие карточки, run JSON checkpoint, rating reports и очередь достаточно.

1. Первичная оценка: callback до/после model batch, проверка response, сохранение evidence и `priority_refresh_id` каждой карточки сразу после подтверждения. При повторе — использовать только валидные evidence того же логического refresh и frozen inputs. Счётчик — подтверждённые записи, не model_attempts. Незавершённый пакет разрешено повторить; завершённые карточки не пересчитывать.
2. Полный анализ: `analysis_completed_refresh_id` вместе с результатом в одном upsert; восстановление analyzed_ids из этих маркеров, пропуск завершённых карточек. Futures сохранять по фактическому завершению. Первичная информация, оплаченные детали и документы остаются в базе.
3. Возобновление: новый фактический job_id, прежний `refresh_id`, snapshot/keywords/budgets/checkpoint. Автоматически продолжать только истёкшие по lease profile_refresh, игнорировать ручной Stop и модельные/источниковые бизнес-ошибки. Явное resume разрешено для установки. Все записи worker транзакционно проверяют scope/run/current_job_id, включая скрытый prepare_card, archive и rating. Поздний старый worker не может перезаписать новое исполнение.
4. Источники: pending неизвестного платного запроса не повторять. Если raw search page уже сохранена, завершить её обработку из архива без повторного HTTP. Если исход неизвестен и архива нет — показать точную ошибку, не придумывать успех. Детали с неизвестным исходом сохраняют блокировку повторного расхода.
5. Итоговый рейтинг: сохранять frozen snapshot, lineage refresh_id и завершённые пакеты; при recovery продолжить незавершённый пакет в новом отчёте/квитанции, не повторять complete. Старый unknown отчёт не переписывать.
6. UI: «Поиск тендеров»; «Оценка первичной информации: N из T»; «Подтягиваю детали тендеров»; «Анализирую детали тендеров: N из T»; «Рассчитываю оценку ИИ». При Stop/ошибке/очереди — соответствующий статус. Неизвестный счётчик не показывать как0.
