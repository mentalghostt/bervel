# Пресейл-конвейер — план реализации

**Исполнение 10.11.2026:** все восемь этапов реализации и подготовки отдельного выпуска завершены в режиме АВТОНОМНО; затем пользователь явно разрешил установку. Подготовленный выпуск установлен, проверены рабочая схема, API/frontend, worker и настройки 50/70. [Фактический отчёт](../quality/2026-11-10-presales-pipeline.md) содержит результаты и ограничения. Пункты ручной промежуточной приёмки заменены автономными проверками; отдельная граница установки соблюдена.

> Для исполнителя: выполнять этапы через `executing-plans` либо, после выбора пользователем, `subagent-driven-development`. В обычном режиме реализуется только разрешённый этап; после его проверки и показа результата требуется явное разрешение на следующий. Контрольные пункты отмечаются через `- [x]`.

**Цель:** превратить выбранный комплект файлов клиента в сохраняемый анализ заявки и автоматический черновик КП с PDF/DOCX.

**Архитектура:** отдельный модуль `presales` в существующем модульном монолите, своя история и очередь на PostgreSQL, общие оригиналы, модель и настройки предприятия. Общие товарные проверки выделяются из радара минимально; тендерный сценарий и его история остаются у радара.

**Стек:** действующие Python/FastAPI/SQLAlchemy/PostgreSQL, React/TypeScript; имеющиеся openpyxl, PDF/OCR-инструменты, ReportLab и стандартная библиотека для DOCX. Новые сервисы и библиотеки не запланированы. Перед использованием библиотечных API исполнитель проверяет актуальную документацию через Context7; отсутствие необходимой возможности согласовывает до добавления зависимости.

**Спецификация:** [согласованные требования и проект решения](2026-11-10-presales-pipeline-spec.md).

## Общие ограничения

- Корень — `C:/OSPanel/home/bervel.local`, Personal, основной checkout `core`, origin `mentalghostt/bervel`. Перед правками повторить read-only проверку root/remote/branch/dirty/index и незавершённых операций; не включать прежние изменения в эту задачу.
- Git в основной ветке только читается. Staging/commit/push/PR не входят в механические шаги этого плана. Если позже выбран worktree, его путь согласуется отдельно по личным правилам.
- Все создаваемые проверки, исходные тестовые примеры, отчёты, снимки экрана и временные файлы — внутри `.dev`; рабочий каталог артефактов: `.dev/local/presales-pipeline-2026-11-10/`.
- Один комплект файлов — одна заявка. Оригиналы неизменяемы, копии проекта не создаются.
- Ровно четыре товарных статуса: `full_stock`, `partial_or_manufacture`, `not_manufactured`, `special_order`. Неполнота и подтверждения хранятся отдельно.
- Цена только от складского `unit_cost`; видимые начальные настройки маржи — `50` и `70`. Производственные расходы, закупки у партнёров, новые интеграции и дополнительные критерии прибыли исключены.
- Настройки предприятия общие. Пресейл не меняет политику радара `scoring_policy.target_margin` и не использует её как скрытую настройку своих цен.
- Конечный объём заявки не обрезается под контекст модели. Порции обработки и страницы интерфейса не являются максимальным количеством сохраняемых позиций.
- Завершённые редакции и готовые файлы неизменяемы. Уточнение/новый анализ создают новую редакцию; Resume сохраняет исходные снимки.
- `core` не импортирует бизнес-модули; между модулями — только публичные интерфейсы. Пресейл не читает таблицы/приватные методы радара.
- VPN/сетевой адаптер не меняются. Модули Open Server Panel включает/переключает только пользователь по отдельному запросу с указанием версии.
- Реализация не означает разрешение на установку, отправку КП, резерв или запуск производства.

## На что обратить внимание при проверке

| Риск | Ожидаемое поведение | Где закрепляется |
|---|---|---|
| Похожее название, но разные материал/размер/количество в двух файлах | Не скрыть различия автоматическим удалением дубля | Этап 3, `test_presales_intake.py` |
| Повторный SKU, смешанные единицы, нулевой остаток | Не задвоить остаток, не заменить неизвестное нулём, учесть изготовление с нуля | Этапы 1 и 4, `test_product_analysis.py`, `test_presales_analysis.py` |
| Спецзаказ рекомендован, но себестоимость/адаптация ещё не подтверждены | Отдельное ожидание проверки; нет подтверждённой цены в КП | Этапы 4–6, `test_presales_special_order.py`, `test_presales_offer.py` |
| Потеря HTTP-ответа/завершение lease/дублированная вкладка | Одно намерение создаёт одну редакцию и один комплект экспорта, старая попытка не перезаписывает новую | Этапы 5 и 7, `test_presales_jobs.py`, `frontend-presales-recovery.cjs` |
| Независимая отложенная миграция и старые анализы радара | Адресно установить пресейл, не применить `0028_inspection_followups`, не пересчитать историю | Этапы 2 и 8, `test_presales_migration.py`, регрессии радара |

## Известные факты текущего кода

- Общий список оригиналов уже доступен через `/api/v0.1/artifacts`; frontend использует `frontend/src/api.ts`. Готового универсального выбора нескольких файлов нет.
- `DocumentReader`/офисные readers и поисковый индекс не гарантируют полного товарного состава: есть пределы страниц/строк, потеря структуры таблиц и отдельные ограничения OCR. Простого вызова поиска по файлу недостаточно.
- `ai_tender_radar/matching.py`, `calculation.py`, `production.py` содержат полезные правила, но общий оркестратор зависит от лотов, тендерных цен, допуска и сроков подачи. Переиспользовать весь оркестратор нельзя.
- `company_settings` уже владеет версионируемыми каталогом/складом/мощностями. В API сборке он сейчас находится внутри сборки радара; пресейлу передаётся публичный сервис владельца этих данных, а не ссылка на `run_pipeline.settings`.
- Общий renderer чата не является генератором коммерческих документов; его DOCX — текстовые абзацы. Для КП нужна собственная структурированная таблица.
- Общий `migrate(engine)` вызывает Alembic `upgrade heads`; исходники содержат две независимые ветви `0027b_radar_profiles` и `0028_inspection_followups` от `0027a`. Это учитывается адресной миграцией при выпуске.

Эти факты установлены чтением исходников. Runtime, тесты и качество распознавания этим этапом планирования не проверялись.

## Контракты, которые связывают этапы

Числа в JSON передаются десятичными строками; внутренние денежные вычисления — `Decimal`. UUID и timestamps проверяются на HTTP-границе. Время сохраняется с часовым поясом, даты клиента показываются в Europe/Moscow с сохранением исходного контекста.

`models.py` пресейла определяет:

- `PresalesSettings`: `target_margin_percent`, `special_min_margin_percent`, `seller_contacts`, `offer_terms`.
- `CreateRequest`: непустые уникальные `artifact_ids`, `command_key`. Название/клиент извлекаются из документов и могут уточняться; ручное имя до запуска необязательно.
- `RequestLine`: стабильный `line_id`, исходные/уточнённые наименование, количество, единица, требования, `evidence`, происхождение списка и известность данных.
- `ManagerDecisions`: выбор основного списка, исправления значений, подтверждённый аналог, подтверждения адаптации и применимости себестоимости конкретного SKU; причина/автор/время каждого изменения.
- `AnalysisLine`: исходная позиция, кандидаты и доказательства, выбранный SKU, четыре `supply_status`, `needs_review`, складское/производственное/предлагаемое количество, сроки, внутренний расчёт цены, причина исключения из ценовой таблицы.
- `RequestRevision`: `request_id`, `revision_id`, номер, родитель, неизменяемые входные снимки, версии правил/промптов, состояние/стадия, метрики, внутренний AI-review/score, структурированное КП и ссылки экспорта.
- `OfferDraft`: стабильные номер/дата/редакция, клиент, контакты/условия, ценовые строки, итоги по валюте, сроки, уточнения и неподдержанные позиции. Внутренние себестоимость/маржа/AI-review в этот тип не входят.

Предлагаемый HTTP-контракт, отдельный префикс `/api/v0.1/presales`:

| Метод и путь | Операция |
|---|---|
| `GET/PUT /settings` | Чтение/сохранение собственных настроек с `base_snapshot_id` и `command_key` при записи |
| `GET/POST /requests` | Постраничная история / создание одной заявки и первой редакции |
| `GET /requests/{request_id}` | Сводка профиля, список редакций, состояние текущего задания |
| `GET /requests/{request_id}/revisions/{revision_id}` | Метрики, предупреждения, отчёт и ссылки КП без всего большого массива строк |
| `GET /requests/{request_id}/revisions/{revision_id}/lines` | Постраничная таблица строк с cursor |
| `POST /requests/{request_id}/revisions` | `kind=manager_update` с исходной редакцией и решениями либо `kind=reanalyze` с новым снимком входов; оба создают дочернюю редакцию |
| `POST /requests/{request_id}/jobs/{job_id}/stop` | Остановить отправку новых действий и сохранить готовые стадии |
| `POST /requests/{request_id}/jobs/{job_id}/resume` | Продолжить исходную редакцию после остановки/сбоя с теми же входами |

Создание/изменение/Stop — `process:start`, чтение — `process:read`, Resume — `process:recover`, файлы — `artifact:read`/`artifact:write` по операции, настройки — `settings:read`/`settings:write`. Каждый сервис проверяет область данных и права независимо от HTTP. Экспорт скачивается через существующий API артефактов, без второго download-хранилища.

## Этап 1. Общие товарные правила без изменения поведения радара

**Результат:** радар и будущий пресейл могут использовать одни чистые проверки, при этом прежние ответы радара совпадают.

**Файлы:** новый `product_analysis/`; адаптеры в четырёх файлах радара из карты. Проверки: `.dev/tests/test_product_analysis.py`, существующие matching/calculation/production-наборы.

**Интерфейсы:** `models.py` общего пакета определяет `Demand`, `StockRow/StockData`, `CandidateSelection`, `PreparedCandidates`, `MatchResult`, `AllocationResult`, `ProductionJob`, `ResourceCalendar`, `ScheduleResult`. Публичный вход только через `product_analysis/__init__.py`:

- `prepare_candidates(demand: Demand, rows: Sequence[StockRow]) -> PreparedCandidates`;
- `validate_selected_evidence(demand: Demand, rows: Sequence[StockRow], selections: Sequence[CandidateSelection]) -> MatchResult`;
- `allocate_stock(demands: Sequence[Demand], stock: StockData, matches: Mapping[str, MatchResult]) -> AllocationResult`;
- `weighted_piece_coverage(allocation: AllocationResult) -> CoverageResult` (`CoverageResult` также определяется в общих моделях);
- `production_workdays(quantity: Decimal, units_per_workday: Decimal, setup_workdays: Decimal, *, rate_factor: Decimal) -> Decimal` — действующая формула `quantity / (units_per_workday * rate_factor) + setup_workdays`, без преждевременного округления до целых дней;
- `schedule_work(jobs: Sequence[ProductionJob], resources: Mapping[str, ResourceCalendar], *, capacity: Callable[[ResourceCalendar, date], Decimal | None]) -> ScheduleResult` — минимальный календарный расчёт без знания тендера/цен/дедлайна подачи. `ProductionJob` сохраняет нужные действующему алгоритму release/deadline/work/resource/alternative/confirmation-факты, `ScheduleResult` — размещение, готовность и неизвестные/неразмещённые объёмы. Радар передаёт прежний расчёт дневной мощности через callback, сохраняя legacy-режимы и смысл существующих monkeypatch-тестов. Для пресейла календарь ограничен реально известными данными; отсутствие дальнейшего календаря даёт неполноту, а не доказанную невозможность выпуска.
