# Пресейл-конвейер — согласованные требования и проект решения

Дата: 10 ноября 2026. Основание: ответы владельца в интервью `grilling`, Q1–Q28, и поручение составить план реализации.

Статус на 10.11.2026: требования согласованы в чате, реализованы по [плану](2026-11-10-presales-pipeline-plan.md) и установлены после отдельного разрешения пользователя. [Фактический отчёт](../quality/2026-11-10-presales-pipeline.md) подтверждает проверки реализации и рабочего выпуска.

## 1. Цель и границы

Создать раздел «Пресейл-конвейер»: комплект уже загруженных файлов клиента → отдельная заявка в истории → извлечение всех товарных позиций → сравнение с данными предприятия → анализ и черновик коммерческого предложения (КП).

- Один выбранный комплект файлов — одна заявка. Оригиналы повторно не загружаются и не изменяются.
- Вход: XLSX, CSV, DOCX, PDF, сканы и изображения. Выход: черновик на экране, PDF и редактируемый DOCX.
- Аналоги и частичное исполнение разрешены. Закупка недостающего у сторонних поставщиков исключена.
- Формирование КП автоматическое; отправка клиенту, резервирование склада, запуск производства и CRM/1С в первую версию не входят.
- Каталог, выбранный склад и производственные мощности общие для всех бизнес-модулей. Пресейл не создаёт вторую копию настроек предприятия.
- Модель и её провайдер используются из действующих общих настроек ИИ.

## 2. Выбор файлов, извлечение и основной список

При подтверждении выбора сразу создаются профиль заявки, первая редакция и фоновое задание. Ошибка последующего разбора не удаляет заявку из истории.

Для каждого файла сохраняются ID оригинала, имя и SHA-256. Для каждой позиции и существенного параметра сохраняются источники: файл, страница либо лист/строка, исходный фрагмент. Параметры включают наименование, количество, единицу, стандарт, размер, материал, покрытие, класс прочности и прочие фактически заявленные требования. Отсутствующий параметр не заполняется предположением модели.

Полное извлечение требует обхода всех страниц, листов и строк. Обработка идёт порциями с сохранением прогресса; бюджет одного запроса модели не ограничивает число товаров заявки. Текущие пределы поискового индекса и тендерного извлечения не становятся пределами пресейла. Ошибка OCR, повреждённый файл, формула без доступного результата или непрочитанная часть явно отражаются в полноте.

Правила комплектов:

1. Совпадающие позиции из разных файлов — дубли, их количества не складываются. Доказательства из обоих источников сохраняются. Совпадение одного названия при различающихся характеристиках не доказывает дубль.
2. При различающихся списках основной — список с большим числом уникальных товарных позиций; при равенстве — с большей заполненностью характеристик.
3. Отличия составов, количеств и характеристик сохраняются в отчёте для менеджера; второстепенный список не удаляется.
4. При равнозначности противоречащих списков менеджер выбирает основной. До выбора анализ имеет признак неполноты, модель не принимает скрытого решения.
5. Менеджер может уточнить извлечённые значения, выбрать основной список и подтвердить аналог; правки сохраняются отдельно от оригинальных фактов и создают новую редакцию результата.

## 3. Четыре статуса исполнения

| Код | Подпись | Правило |
|---|---|---|
| `full_stock` | Есть полностью | Подходящий товар на складе полностью закрывает требуемое количество. |
| `partial_or_manufacture` | Частично + допроизводим | Склад закрывает только часть и/или требуется собственное изготовление, включая изготовление всего количества при нулевом остатке. Показываются отдельно подтверждённые количества и неизвестная часть. |
| `not_manufactured` | Не производим | Подтверждено отсутствие допустимого исполнения своим складом/производством. Недостаток сведений не является таким подтверждением. |
| `special_order` | Спецзаказ | Точного материала/изделия нет, найден близкий собственный товар для возможной адаптации, LLM рекомендует спецзаказ по выгодным условиям клиента; возможность адаптации и база себестоимости подтверждаются менеджером. |

`needs_review`, причины неполноты и состояние подтверждения — отдельные поля, а не дополнительные товарные статусы. Если данных для любого из четырёх статусов пока недостаточно, `supply_status` остаётся пустым с понятной причиной.

Одинаковый SKU распределяется между позициями одной заявки из одного общего остатка. Полный складской остаток не используется повторно для каждой строки. Между независимыми заявками резерва нет.

Технически неподходящий вариант не считается частично исполненной позицией. Аналог становится допустимым предложением только после явного подтверждения менеджером; до этого показаны кандидат и отличия.

## 4. Цена, маржа и спецзаказ

Настройки пресейла:

| Поле | Начальное видимое значение | Назначение |
|---|---|---|
| `target_margin_percent` | `50` | Целевая маржа обычного предложения. |
| `special_min_margin_percent` | `70` | Минимальная и расчётная маржа спецзаказа. |
| `seller_contacts` | Пустой текст | Контакты в бланке КП. |
| `offer_terms` | Пустой текст | Общие условия и примечания КП. |

Значения 50/70 видны в форме и сохраняются явно. Первый запуск требует сохранённых настроек; отсутствие поля не заменяется скрытым процентом. Маржа — десятичное значение `0 ≤ m < 100`; порог спецзаказа выше обычной маржи. Значение 100% недопустимо из-за деления на ноль.

Единственный источник себестоимости — `unit_cost` выбранного складского товара. Не добавляются производственные затраты, упаковка, доставка, налоги, минимальная прибыль или иные пороги. Производственные нормы используются для возможности исполнения и сроков, но не для цены.

Формула: `цена = складская себестоимость / (1 − маржа / 100)`. При себестоимости 100 ₽ обычная цена до округления — 200 ₽; спецзаказ при 70% — 333,333… ₽. Денежные вычисления выполняются десятичной арифметикой. Предлагаемое техническое правило: округлять цену вверх до денежной точности валюты, чтобы округление не уменьшало целевую маржу; суммы строк считать от отображаемой цены и предлагаемого количества. Это правило включено в план для приёмки.

Перед расчётом себестоимость приводится к единице предлагаемого товара по подтверждённым коэффициентам. Например, 100 ₽/кг и подтверждённая масса 0,5 кг/шт дают 50 ₽/шт себестоимости и 100 ₽/шт цены при марже 50%. Если коэффициента нет, цену не вычисляют. Для исполнения одной позиции несколькими SKU предлагается показывать их отдельными строками КП с собственной ценой и общей ссылкой на исходную позицию; себестоимость разных SKU скрыто не усредняется.

Валюта сохраняется из складской себестоимости. Автоматическая конвертация и расчёт НДС не добавляются. Неизвестная валюта/себестоимость не превращаются в ноль; несовместимые валюты не суммируются в одну неразмеченную сумму. Неутверждённые налоговые условия не выдумываются.

Для аналога используется себестоимость подтверждённого складского SKU. Для спецзаказа менеджер отдельно подтверждает применимость себестоимости близкого SKU для предварительного расчёта. Без подтверждения цена и маржа спецзаказа остаются неизвестными.

LLM оценивает выгодность условий спецзаказа по фактам заявки: цене/бюджету клиента, объёму, срокам и другим явно указанным условиям. Вывод содержит обоснование и ссылки на факты. Само сходство товара или высокая цена не доказывают возможность адаптации. Арифметика маржи и проверка порога выполняются кодом по подтверждённым числам.

Если цены клиента нет, разрешена предварительная рекомендация спецзаказа с признаком «Требует проверки»; подтверждённая выгодность не выдумывается. Предложенная цена рассчитывается по марже спецзаказа после подтверждения базы себестоимости. Если явно указанные клиентом денежные ограничения не позволяют достичь 70%, конфликт показывается менеджеру; LLM не отменяет числовой порог. Бюджет всего заказа не распределяется по позициям произвольно.

## 5. Показатели и анализ ИИ

- Соответствие продукции: подтверждённые технически подходящие позиции / все уникальные позиции основного списка. Подтверждённый аналог учитывается, неподтверждённый — нет. Неизвестные требования отражаются признаком неполноты, а не положительным соответствием.
- Покрытие склада: обеспеченное складом количество / требуемое количество всей заявки, с корректным приведением к штукам по подтверждённым данным. Будущее производство не увеличивает складское покрытие. Непереводимые единицы или неизвестный состав списка означают неполноту; достоверный общий процент в таком случае не подставляется.
- Оценка ИИ: индивидуальное число 0–100 и краткое объяснение по фактам этой заявки; не сравнительный рейтинг истории. Ошибка модели не становится оценкой 0.
- Анализ ИИ: решение по заявке, причины, риски/уточнения, предложения аналогов и спецзаказов. Числа и технические доказательства не переписываются текстом модели.
- Таблица соответствия: исходная позиция и параметры → выбранный SKU/аналог → доказательства и отличия → складские/производственные количества → статус → себестоимость и цена → вопросы и решения менеджера.

Срок клиента извлекается из заявки и может уточняться вручную. Производство оценивается по общим мощностям. При отсутствии даты клиента показывается расчётная готовность по доступным нормам; соблюдение клиентского срока остаётся неизвестным. Тендерная дата подачи и запас 48 часов не используются. При недостаточных нормах дата не выдумывается.

## 6. Черновик КП

Черновик создаётся автоматически по завершении доступного анализа, в том числе для частичного предложения. Он содержит:

- шапку BERVEL, клиента, стабильный номер и дату предложения;
- таблицу предложенных товаров: наименование/характеристики, количество, единицу, цену, сумму;
- общую сумму предложенных товаров по валюте, сроки готовности и примечания;
- отдельные разделы «Требует уточнения» и «Не можем предложить» с привязкой ко всем исходным строкам;
- контакты и общий текст условий из сохранённых настроек пресейла.

Неподтверждённый аналог/спецзаказ или позиция без подтверждённой цены не попадают в ценовую таблицу как готовое обещание. Цена частичного предложения применяется к предлагаемому количеству. Неясные данные о клиенте оставляются незаполненными для правки менеджером.

Себестоимость, маржа и внутренние выводы ИИ доступны в профиле анализа; в клиентские файлы они не экспортируются. PDF и DOCX создаются из одной структурированной редакции предложения, с одинаковыми числами, номером и датой. DOCX содержит настоящую редактируемую таблицу. Произвольный текст LLM не управляет шаблоном, формулами или исполняемым содержимым.

## 7. История и выполнение

Профиль заявки хранит исходные ссылки, редакции, прогресс, результаты и КП. Новая редакция закрепляет снимки компании/склада и настроек пресейла, решения менеджера, версию правил/промптов и время расчёта.

- Новый анализ по изменившимся данным создаёт новую редакцию. Завершённые результаты и экспортированные файлы прежней редакции не меняются.
- Возобновление остановленного задания продолжает те же закреплённые входы; новые настройки для него не подмешиваются.
- Уточнение менеджера создаёт дочернюю редакцию и пересчитывает зависимые части, переиспользуя неизменившееся извлечение.
- Закрытие/перезагрузка страницы не останавливает серверную обработку. Stop сохраняет готовые стадии; явное Resume не повторяет завершённые стадии.
- Команды имеют устойчивый ключ; повтор нажатия/потерянного ответа не создаёт вторую заявку, редакцию или два комплекта КП.
- GET читает сохранённое состояние и не запускает модель, индексацию или пересчёт. Список истории и строки результата выдаются порциями.
- Неизвестный исход модельного вызова фиксируется отдельно; автоматический слепой повтор не закладывается.

## 8. Предлагаемые технические границы

Предпочтительный вариант — отдельный модуль `src/bervel/modules/presales/`, собственные таблицы/очередь на имеющемся PostgreSQL и отдельная роль существующего Python worker. Подключение зависимостей — в `app_setup.py`/`presales_setup.py`; `core` не импортирует бизнес-модули.

Чистые технические проверки товаров, единицы, распределение остатков и необходимые календарные операции предлагается выделить в небольшой `src/bervel/product_analysis/`. Радар сохраняет прежние публичные функции, версии и тендерные правила как адаптеры к этим функциям. Пресейл не вызывает приватные методы/таблицы радара и не копирует его бизнес-расчёты.

Отклонённые направления для этого плана: добавление пресейла в таблицы/профили радара смешивает жизненные циклы; отдельный сервис или универсальный движок процессов избыточны для первой версии. В общий пакет не переносятся весь `production.py`, тендерные цены, лоты, отсев кандидатов или правила допуска к участию.

Интерфейс: новый маршрут `#/presales`, история заявок слева, анализ выбранной редакции справа; отдельная карточка настроек пресейла в общих «Настройках» открывает `#/presales-settings`. Используется действующая визуальная система приложения. Детали разметки подлежат приёмке этапа интерфейса.

## 9. Проверочные примеры

1. Два файла с одинаковой спецификацией дают один состав, без удвоения количества; обе ссылки на источники сохранены.
2. Разные списки выбираются по согласованной подробности; менеджер видит отличия и может поменять выбор.
3. Из 10 уникальных строк технически подтверждены 8 — соответствие 80%; из 1000 шт склад закрывает 700 — покрытие 70%.
4. Один SKU с остатком 100 для двух строк по 80 закрывает суммарно 100, а не 160.
5. Нулевой остаток при собственном изготовлении даёт «Частично + допроизводим», не отдельное «Производим».
6. Себестоимость 100 и маржа 50 дают цену 200. Спецзаказ при 70% даёт предварительную цену 333,34 при точности 0,01.
7. Неизвестная себестоимость, непрочитанная страница и неопознанный параметр видны в уточнениях; неизвестное не становится нулём/невозможностью.
8. Неподтверждённые аналог/адаптация не улучшают подтверждённое исполнение и не попадают в ценовую таблицу.
9. Изменение склада или маржи не меняет прежнюю редакцию. Resume использует старые входы; новый анализ создаёт новую редакцию.
10. PDF и DOCX совпадают по всем коммерческим значениям и не содержат внутренних себестоимости/маржи/оценок ИИ.
