# Cloudflare: настройка и сетевой блокер, 10 ноября 2026

Корень: `C:\OSPanel\home\bervel.local`, Personal, основная ветка `core`.
Предшествующий общий dirty tree сохранён; Git использовался только для чтения.

Подготовлены `.dev/scripts/cloudflare.ps1` и [инструкция](../operations/cloudflare-sharing.md).
Команды: `install`, `start`, `status`, `stop`. cloudflared хранится в исключённой из Git
`.dev/local/cloudflare/`; системная установка, служба и автозапуск не создаются.
Закреплён официальный Windows amd64 релиз 2026.10.7 с проверкой SHA-256.
Публикуется только существующий Nginx frontend, серверный ключ не раскрывается.
В BERVEL нет отдельного входа: обладатель рабочей ссылки получает общую область сайта.

Docker Desktop первоначально не работал. Запущено существующее приложение Docker Desktop;
прежние контейнеры поднялись со своими образами, без Compose up, пересборки и миграций.
Локально HTML, JavaScript (500 453 байта) и GET `/api/v0.1/artifacts?limit=1` отвечают HTTP 200.

Наблюдения проверки:

- Системный DNS не возвращает SRV `_v2-origintunneld._tcp.argotunnel.com`.
  Официальный DNS Cloudflare по HTTPS возвращает корректные region1/region2.
  Помощник при отсутствии SRV использует эти актуальные имена только для своего процесса.
  Применяется скрытый `--edge` закреплённого клиента; совместимость при обновлении проверять отдельно.
- После этого HTTP/2-соединение регистрируется, небольшая публичная HTML-страница отдаётся с HTTP 200.
  Это оказалось недостаточной проверкой готовности: большой JavaScript не передаётся полностью.
- Публичный JavaScript: HTTP 520, HTTP 200 с неполным телом или тайм-аут без тела.
  Диапазоны 1 024 и 8 192 байта отдавались с HTTP 206; 32 768 байт зависли.
  API после разрыва туннеля возвращал 502/530 вместо локального 200.
- HTTP/2 затем пишет `Error shutting down control stream: context canceled` и переподключается.
  QUIC зарегистрировался, затем дал `timeout: no recent network activity`; `/ready` стал 503.
- Одинаковая проблема полной передачи воспроизведена на официальном Windows 2026.10.7,
  Linux-контейнере 2026.10.7 и предыдущем Windows 2026.9.1.
  Сжатие ответа не устранило сбой.
- Штатный US-регион также проверен: `us-region1/2.v2.argotunnel.com:7844`, TLS EOF,
  диагностика клиента сообщает недоступность HTTP/2 и QUIC. Он не выбран для рабочего помощника.
- Повторный старт существующего процесса вернул тот же URL без второго процесса.
  Остановка закрыла прежнюю ссылку (после остановки HTTP 530).

Результат: настройка подготовлена, **работоспособная интернет-ссылка не подтверждена**.
Препятствие находится на пути обмена с Cloudflare; точный сетевой компонент, вызывающий
обрыв, не установлен. Не приписывать причину VPN, firewall, провайдеру или Cloudflare без новых доказательств.
Для завершения необходима возможность устойчиво передавать данные к Cloudflare по исходящему
TCP 7844 (либо работоспособный QUIC/UDP 7844). См. [требования Cloudflare](https://developers.cloudflare.com/tunnel/configuration/).

Помощник теперь проверяет публичный HTML, полный SHA-256 JavaScript и чтение API перед
сообщением об успехе. При провале завершает только свой процесс. Недостаточная регистрация
соединения больше не считается готовой ссылкой. Изменения приложения ради сетевого сбоя не вносились.

VPN, его адаптеры, системный DNS, firewall и модули Open Server Panel не менялись.
Данные приложения, серверные ключи и конфигурация контейнеров не редактировались.
Вспомогательные тестовые туннели и пробный контейнер остановлены; локальный BERVEL оставлен работающим.
Технические журналы находятся в `.dev/local/cloudflare/`; не публиковать приватные ответы API из этой папки.

Финальная проверка помощника: PowerShell parser без ошибок; `install` сверил бинарный файл
и показал версию; `status` выполнен также в Windows PowerShell 5.1; `stop` при остановленном
туннеле завершился штатно. Финальный `start` обнаружил неполный ответ (`ResponseEnded`),
вернул ошибку и удалил state.json; процессов cloudflared и пробного контейнера не осталось.
Дополнительный динамический тест защиты от подставного PID не выполнен: автоматическая
проверка отклонила тестовые команды с причиной `blocked by policy`. Проверка пути и времени
старта присутствует в коде; этот сценарий не заявляется как динамически проверенный.

## Продолжение диагностики

Проверены дополнительные пути без изменения VPN: существующие SOCKS5/HTTP CONNECT
входы Xray, другие IP из официального DNS Cloudflare, привязка только сокета cloudflared
к существующему локальному адресу, отдельная отправка ClientHello и небольшими блоками.
GOST использовался только как временный локальный TCP-переходник, не установлен системно
и не добавлен в рабочий запуск. Устойчивый туннель эти варианты не дали.

В изолированном Docker DNS-proxy (DNS-over-HTTPS Cloudflare, без публикации портов)
подтверждено штатное разрешение SRV. cloudflared запущен с этим DNS без `--edge`:
DNS/QUIC/HTTP2/API prechecks PASS, регистрация есть, полный JS снова оборвался с 520.
Проверочные контейнеры остановлены и удалены. Настройки DNS Windows, Docker daemon
и существующих контейнеров приложения не менялись.

Отладка HTTP/2 показала DATA-кадры всего ответа с END_STREAM; локальный Nginx также
записал передачу всех 500 453 байт. На внешнем клиенте тело оставалось пустым.
Отладочный журнал может содержать служебные данные туннеля; он сохранён только
в `.dev/local/cloudflare/http2-debug-private.log`, не предназначен для публикации.

После отдельного явного согласия пользователя в Happ выполнено ровно разрешённое
переключение «MOX» (VLESS/XHTTP/REALITY) → нижний «MOX-vision» (VLESS/TCP/REALITY,
275 мс в списке). UI подтвердил «ПОДКЛЮЧЕН», остальные настройки не менялись.
Повтор исходного помощника всё ещё завершился ResponseEnded. QUIC с отключённым
PMTU discovery (`--quic-disable-pmtu-discovery`) также не передал большой ответ.
Настоящий Chromium загрузил HTML, но интерфейс BERVEL остался пустым: это не только
особенность curl/HTTP 1.1. Не считать смену VPN-сервера подтверждённым исправлением.

Поведение коротких/больших ответов похоже на описанное Cloudflare
[ограничение передачи около 16 КБ](https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/),
но это сходство симптомов, не установление причины для данной машины.
Ответ Cloudflare Status API имел `page.updated_at=2026-08-27`, поэтому не использован
как доказательство состояния Cloudflare на 10 ноября.
