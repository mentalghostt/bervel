# Этап 2 ядра: проверка ручного восстановления n8n

Дата: 14 октября 2026. Статус: четыре дополнительных проверки выполнены; профиль n8n принят владельцем разработки для ядра v0.1 по [ADR-0002](../adr/0002-durable-orchestration.md). Продуктовая реализация не начата.

**Вывод:** n8n пригоден как кандидат для v0.1 с ручным восстановлением аварийных исполнений, если ядро обеспечивает защиту от повторов, сохраняет исходную версию и проверяет эффект операции. Штатный повтор n8n сам по себе не обеспечивает единственность запроса восстановления: два одновременных обращения к старому аварийному исполнению создали два новых исполнения, даже когда оно уже было успешно восстановлено ранее.

Пользователь после [первого эксперимента](core-stage-2-n8n-report.md) выбрал продолжение проверки n8n с ручным восстановлением, а после её результатов явно принял этот профиль для разработки ядра v0.1. Приёмка не утверждает промышленную эксплуатацию или новые API, состояния и полномочия ядра.

## Результаты

| ID | Сценарий | Наблюдение |

Все четыре проверки прошли свои измерительные критерии. MR02 фиксирует отсутствие гарантии единственного восстановления у проверенного пути n8n; MR04 проверяет ожидаемое отклонение несовместимого повтора. Эти результаты не означают, что n8n самостоятельно обеспечивает предметную идемпотентность.

Доказательства — [машинный отчёт](core-stage-2-n8n-manual-results.json). Исполняемый сценарий — `.dev/experiments/n8n/manual_recovery.py`; команды и состав — [описание стенда](../operations/n8n-manual-recovery.md).

## Как выполнена проверка

Использованы прежние n8n 2.43.5, PostgreSQL 17.9, Redis 8.6.1 и Node.js 24.19.0. Сервисы были включены пользователем и проверены доступными; их состояние агент не менял. Для каждой новой аварии получен отдельный искусственный `run_id`. Приёмник записывал эффект, задерживал ответ на 45 секунд, затем стенд завершал только собственный worker и запускал новый.

Список `error`/`crashed` и отдельные исполнения получены через аутентифицированный API интерфейса n8n. В MR02 две отдельные HTTP-сессии отправили запросы одновременно; клиент не сериализовал их. Результат проверен по `retryOf`, `retrySuccessId`, статусам исполнения и независимому журналу попыток/эффектов. Пароли и cookies в машинный отчёт не сохранялись.

Публикация v1/v2 использовала проверенный API, а не проблемный в первом опыте Server CLI. Фактический ID версии разрешён по тестовой истории n8n. Конфликт MR04 обнаружил приёмник, а не движок: ключ оставался прежним, тело с версией v2 отличалось от сохранённого v1.

## Что должен видеть оператор

Аварийное родительское исполнение после успешного повтора сохранило статус `crashed`. У №11 после первого восстановления появился `retrySuccessId=12`, а после двух последующих — ссылка на один из успешных повторов. Наличие старого исполнения в списке ошибок поэтому не означает, что его нужно снова восстанавливать. Требуется проверять успешные и активные дочерние исполнения вместе с состоянием процесса ядра.

Штатный интерфейс n8n различает повтор с исходной схемой и с текущей сохранённой схемой. Для восстановления той же операции нужен **Retry with original workflow**. [Документация списка исполнений и повтора](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions.md) описывает обе опции. В проверенных исходниках `loadWorkflow=true` загружает текущие сохранённые узлы; это не обещание использовать только согласованную опубликованную версию.

Предлагаемый порядок действий сохранён в [регламенте ручного восстановления](../operations/n8n-manual-recovery.md). Принят принцип ручного восстановления по исходной версии; подробная процедура требует уточнения перед эксплуатацией. Экран очереди, уведомления, права оператора и защита команды в приложении пока не реализованы.

## Принятый профиль v0.1

Для разработки v0.1 принят n8n в режиме очередей с отдельными main/worker, PostgreSQL и Redis. Аварии worker обнаруживаются и восстанавливаются явно уполномоченным оператором, без обещания автоматического продолжения. Повтор использует прежнюю схему и входы; новая версия процесса предназначена для новых запусков или отдельно разрешённой повторной обработки.

Условия допуска к реализации:

- Команда восстановления и изменение состояния процесса защищены ядром от повторов и конкуренции. Повторный запрос не должен создавать второй бизнес-запуск или выдавать дополнительное одобрение.
- Публикация проверяет неизменный ключ, точную редакцию и тело. Повтор того же эффекта возвращает прежний результат; изменение тела вызывает конфликт. Эта часть ещё не реализована в ядре.
- Сохраняются ссылки на родительское и повторное исполнения, исходную версию и входы. Успешный повтор отмечается в очереди восстановления; статус старого родителя не используется как единственный признак необходимости действия.
- Неизвестный результат внешней операции сначала сверяется. Успех технического повтора не разрешает отправку КП, резерв, проводку или иное предметное действие.
- Публикация версий проходит проверку реального исполняемого указателя; испытанный путь Server CLI не считается надёжным без отдельного исправления и повторной проверки.

Эти условия закреплены в принятом [ADR-0002](../adr/0002-durable-orchestration.md). Детализация команды восстановления и её прав нужна до продуктовой реализации. Контракт принятой спецификации v0.1 сохраняет прежнюю редакцию; её API, состояния и полномочия этим отчётом не изменены.

## Границы

Это продолжение того же одноразового стенда на искусственных данных. Native API интерфейса используется для исследования выпуска; стабильный программный контракт адаптера ещё не выбран. Поддержка клиентского сервера, способ поставки, уведомления, дежурство, нагрузка, RPO/RTO, права обычных сотрудников и правила сверки реальных внешних эффектов остаются отдельными проверками/решениями.

Автоматическое восстановление не стало подтверждённым после этих тестов. Зависимость приложения от Open Server или `.dev` не добавлена. CORE-V01 и CV01–CV20 остаются `not_run`. Выбор движка для разработки в DEC-02 принят; клиентские эксплуатационные условия и оставшиеся проверки B06 открыты. Технический этап 2 завершён в согласованном объёме; очередной продуктовый этап не начат.
