# Этап 2 ядра: результаты эксперимента с n8n

Дата: 14 октября 2026. Первый эксперимент завершён; выбор движка процессов DEC-02 остаётся открытым. Это часть B06 внутри E1 общей дорожной карты, а не E2 сквозного продуктового импорта.

**Вывод:** n8n в проверенном профиле сохраняет ожидание человека, позволяет штатный ручной повтор и сохраняет семантику старого исполнения при корректной публикации новой версии через API. Автоматического продолжения после аварийного завершения worker в испытании не было. Принимать этот профиль как окончательный движок ядра пока не рекомендую: сначала нужно решить требование к автоматическому восстановлению и сравнить альтернативу на тех же воздействиях.

Пользователь выбрал n8n для первого эксперимента и сам включил PostgreSQL 17 и Redis. Окончательный выбор n8n, отказ от Temporal или изменение принятой спецификации этим не утверждаются.

После этого отчёта пользователь выбрал продолжение проверки n8n с ручным восстановлением, затем принял профиль для разработки ядра v0.1. [Дополнительный отчёт](core-stage-2-n8n-manual-report.md) и [принятый ADR-0002](../adr/0002-durable-orchestration.md) фиксируют актуальное решение; первоначальные наблюдения и рекомендация ниже сохранены как история первого эксперимента.

## Что проверено

| Проверка | Результат | Факт и значение для ядра |
|---|---|---|
| OR01: перезапуск во время ожидания | Пройдено | После остановки и запуска n8n main/worker исполнение №1 продолжилось с тем же ID; до подтверждения завершения не было, после него — одно |
| OR02: повторное подтверждение | Пройдено | Второй ответ на уже завершённое ожидание получил HTTP 409; повторного завершения того исполнения нет |
| OR02: повтор команды запуска | Защита движком отсутствует в проверенном пути | Одинаковый `run_id` создал исполнения №2 и №3. Было две попытки публикации; один эффект обеспечил измерительный приёмник, а не n8n |
| OR03: авария worker после записи эффекта до HTTP-ответа | Автоматическое продолжение не прошло | Исполнение №4 стало `crashed`; за 150 секунд новый worker не продолжил его. Один эффект уже был записан и не исчез |
| OR03B: штатный ручной повтор | Пройдено | API повторного исполнения создал №8 с `retryOf=4`; процесс достиг ожидания и завершился после ответа. Повторные обращения не создали второй эффект благодаря ключу в приёмнике |
| OR04: смена версии через Server CLI | Не прошло в испытанной версии | Текущая версия стала v2, указатель опубликованной остался v1. Старое и новое исполнения №5/№6 выполнились по v1 |
| OR04B: смена версии через API интерфейса n8n | Пройдено | После публикации и перезапуска старое исполнение завершилось с меткой v1, новое — с меткой v2. Реальные ID версии прочитаны из n8n, а не взяты из импортируемого JSON |

Факты и снимки — [машинный отчёт](core-stage-2-n8n-results.json). Контроллер повтора и публикации использован через аутентифицированный API интерфейса n8n только для диагностики. Стабильный контракт управления для будущего адаптера ещё не выбран.

## Стенд и способ измерения

Версии: n8n 2.43.5, Node.js 24.19.0, PostgreSQL 17.9, Redis 8.6.1, Windows. Закреплённые зависимости, искусственные процессы и команды — [стенд](../operations/n8n-manual-recovery.md).

В режиме `queue` главный процесс принимает запрос, Redis передаёт задание отдельному worker, а n8n сохраняет сведения исполнения в PostgreSQL. Такое разделение описано в [официальной документации queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode.md). В сценарии worker вызывает независимый измерительный HTTP-приёмник, достигает Wait, затем продолжает работу после искусственного HTTP-подтверждения. [Wait сохраняет данные ожидания в БД](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait).

У приёмника собственный журнал SQLite: попытки сохраняются отдельно от эффектов. Одинаковый ключ и одинаковое тело возвращают прежний эффект; другой результат под тем же ключом вызывает конфликт. Это позволяет увидеть повтор операции, не приписывая защиту самому движку. Три проверки этого инструмента прошли: повтор, конфликт тела и сохранность при новом открытии БД.

В OR03 приёмник сначала фиксирует эффект, затем задерживает ответ на 45 секунд. Стенд принудительно завершает только созданный им процесс worker и запускает новый. PostgreSQL и Redis продолжают работу; их пользовательские модули не выключаются и не перезапускаются. Таким образом проверяется реальное окно «эффект состоялся, подтверждение не получено».

Параметры очереди для ускорения наблюдения: lock duration 30 секунд, продление 5 секунд, stalled interval 5 секунд. Это настройки испытания, а не производственный норматив. В установленном `dist/scaling/scaling.service.js` настройки Bull дополняются `maxStalledCount: 0`; журнал подтвердил `job stalled more than maxStalledCount` и переход №4 в `crashed`. Вывод об отсутствии автоматического продолжения ограничен этим выпуском и профилем; политика восстановления продукта пока не согласована.

Стенд использует отдельные БД/роль PostgreSQL и пустую при подготовке базу Redis №15 с собственными префиксами. Ни общей очистки Redis, ни изменений существующих БД не выполнялось. После прогона процессы n8n и приёмника остановлены, тестовая история сохранена. Модули Open Server оставлены включёнными пользователем.

## Что уточнилось при испытании

1. HTTP readiness ответил раньше завершения запуска worker и регистрации webhook. Первые четыре диагностических запроса дали 404; после ожидания фактической готовности стенд выполнил целевые проверки. Эти первоначальные запросы не являются отказом целевых сценариев.
2. n8n присваивает импортированным версиям собственные ID. Переданная в JSON версия не должна считаться ID зарегистрированного исполнения движка. Дополнительное испытание разрешило ID по сохранённому содержимому в тестовой истории.
3. Для проверки ручного повтора первоначальный HTTP timeout 15 секунд оказался меньше искусственной задержки 45 секунд. После исправления измерительного протокола повтор завершился штатно. Неудачная диагностическая попытка сохранена отдельно; она не используется как вывод о поддержке ручного восстановления.
4. Расхождение публикации CLI подтверждено чтением `workflow_entity`, `workflow_history` и `workflow_published_version`: содержимое v2 существует, но исполняемый опубликованный указатель остался v1. Штатный API публикации синхронизировал его. Официальная [инструкция Server CLI](https://docs.n8n.io/deploy/host-n8n/configure-n8n/use-the-command-line.md) требует перезапуска после публикации; перезапуск в OR04 выполнен, но в этой проверке не устранил расхождение. Причина внутри реализации CLI полностью не локализована, поэтому вывод относится к проверенному способу публикации этого выпуска.

В журналах также есть `Missing lock for job ... failed`, предупреждения о старых записях лидера после принудительных остановок и о будущем отказе от запуска вне контейнера. Успешные наблюдения при этом подтверждены независимым приёмником и статусами БД. Производственную пригодность и отсутствие эксплуатационных ошибок такой прогон не подтверждает.

## Следствия для реализации и следующая развилка

Требования [принятой спецификации](../architecture/12-core-v0.1-spec.md) сохраняются: ядро отвечает за идентификатор команды, запись намерения запуска и защиту от дублей; компонент публикации — за ключ операции, точную редакцию и проверку конфликта. Движок не заменяет эти предметные гарантии. Время ожидания, задания и исполнение остаются его ответственностью; второй самодельный оркестратор ради исправления отказа не создаётся.

При интеграции потребуется связывать версии процесса ядра с реальными ID определения и исполнения движка; одобрение должно проверяться ядром до обращения к resume URL. Успешный искусственный webhook не доказывает авторизацию или согласование производственного действия.

Рекомендую следующий технический эксперимент в рамках выбора DEC-02 — Temporal с теми же четырьмя основными воздействиями. Альтернатива для отдельного рассмотрения — n8n с явно принятым ручным восстановлением после аварии и проверенной процедурой публикации. Этот компромисс нельзя утверждать только по успешному ручному повтору: нужен выбор владельца разработки и согласование эксплуатационных требований. Одновременно два движка для приложения не вводятся.

## Границы результата

Продуктовое ядро не написано; CORE-V01 и CV01–CV20 остаются `not_run`. Не проверены OCR/модели, права, предметные схемы и хранилище приложения, 1С, реальная документация, нагрузка, отказ или восстановление PostgreSQL/Redis, RPO/RTO и установка заказчика. Искусственный подтверждающий запрос не является проверкой личности сотрудника.

Запуск n8n выполнен отдельно от Open Server, а его сервисные адреса заданы окружением. Это подтверждает способ подключения стенда; полная переносимость приложения без Open Server будет проверяться после реализации. Зависимость приложения от `.dev` не добавлена: сейчас там находится только одноразовый эксперимент.

Общий B06 и DEC-02 остаются открытыми: нагрузка, условия промышленной эксплуатации и решение по движку ещё не получены. Следующий продуктовый этап не начат.

Проверка материалов завершилась с `ok=true`: 36 файлов Markdown, 140 локальных ссылок, пять контрольных сумм исходных предпроектных источников. Прошли три проверки приёмника и две проверки отбора документации; последнее изменение исключает установленные зависимости и локальные генерируемые материалы из проверки проектных ссылок. Программные наблюдения движка остаются смешанными: четыре положительных и два отрицательных результата по таблице выше. Код завершения измерительного сценария означает завершение сбора фактов, а не успешность всех требований ядра.

Автоматическая проверка команд отклонила рекурсивное удаление трёх временных папок тестов с сообщением `blocked by policy`. Папки оставлены в .dev/experiments/n8n и исключены из Git; обход блокировки не выполнялся.
