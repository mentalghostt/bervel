## Итоговая схема

Рабочие `compose.yaml`, `compose.orchestration.yaml`, Dockerfile, init PostgreSQL и runtime lock находятся вне `.dev`. API установлен как пакет с собственными ресурсами. `.dev/docker` содержит только дополнительные профили разработки и проверок. Windows venv, node_modules и кэши Codex в образах не используются.

API слушает `0.0.0.0` внутри контейнера, по умолчанию локальный запуск сохраняет `127.0.0.1`. Публикация портов Docker ограничена loopback хоста. БД приложения, тестов и n8n разделены ролями; Redis доступен только внутри сети. PostgreSQL проверяется по TCP, затем одноразовый migrate завершает обновление до старта API.

Браузерные проверки используют отдельную тестовую БД, отдельный ключ/область и отдельный volume. Для secure browser origin браузер подключается к localhost в сетевом пространстве тестового frontend; отключение browser security не используется.

Четыре сценария n8n: ожидание переживает restart main/worker; одинаковая команда создаёт два исполнения с одним эффектом у идемпотентного observer; ручной повтор аварийного исполнения сохраняет v1 после публикации v2; старое ожидание использует v1, новый запуск — v2. Автоматическое продолжение аварийного worker не подтверждено: исходное исполнение остаётся crashed, штатный ручной retry завершает дочернее. Docker не добавляет n8n идемпотентность команды или эффекта.

## Исправления по независимому review

1. `.gitattributes` закрепляет LF для shell-скриптов PostgreSQL; Windows checkout не должен ломать первую инициализацию CRLF.
2. Restore проверяет наличие и совпадение сохранённого ключа n8n до записи; три проверки ключа сначала воспроизвели дефект, затем прошли.
3. Restore исходной копии заранее проверяет оба дампа, пустоту обеих БД и volume, состав и SHA-256 оригиналов. `pg_restore` выполняется одной транзакцией на БД. Это не распределённая транзакция между двумя БД.
