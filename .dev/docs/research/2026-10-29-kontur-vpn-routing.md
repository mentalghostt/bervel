## Подтверждённые факты и минимальные действия пользователя

1. Родительский агент сообщил результат проверки установленного приложения: `C:/Program Files/FlyFrogLLC/Happ/Happ.exe`, версия `4.3.0.610`, адаптер `happ-xray` включён. Сам исследователь локальные настройки Happ не читал.
2. В Happ 4.x маршрутизация привязана к подписке; глобальный экран стал библиотекой профилей только для чтения. Поэтому искать действующий профиль следует у подписки текущего сервера. Точную последовательность кнопок без осмотра интерфейса подтвердить нельзя. Основание: [официальный релиз 4.0.5](https://github.com/Happ-proxy/happ-desktop/releases/tag/4.0.5).
3. В действующем профиле добавить домен в список прямого подключения (`DirectSites`); GlobalProxy оставить включённым. Проверить отсутствие пересекающегося Proxy/Block-правила. RouteOrder задаёт последовательную проверку; при отсутствии совпадения GlobalProxy=true оставляет трафик в Proxy. После изменения требуется Reconnect, выполняемый пользователем. JSON-подписки могут запрещать ручное управление профилями. Основание: [официальная документация маршрутизации](https://www.happ.su/main/ru/dev-docs/routing.md), разделы «Децентрализация архитектуры», «Основные настройки», «Правила», «Порядок маршрутизации».

## Синтаксис и приоритет

Официальный [Routing Builder](https://routing.happ.su/en) содержит DirectSites и RouteOrder. Его [публичный JavaScript](https://routing.happ.su/_next/static/chunks/f8aea177853b7036.js), прочитанный без запуска, принимает hostname `api-zakupki.kontur.ru` и префикс `domain:`; `full:` его валидатором не принимается. Точная семантика совпадения обычной строки в документации Happ не описана, поэтому совпадение исключительно с одним полным hostname этим исследованием не доказано.

В редакторе исходное RouteOrder=`block-proxy-direct`; есть вариант `block-direct-proxy`. Следствие: при пересечении списков Proxy может победить Direct. Переставлять категории без проверки не следует: меняется приоритет всех существующих пересечений. Для одного исключения достаточно DirectSites, если более ранние правила его не перехватывают. Содержимое действующего профиля неизвестно; пригодность такого условия не проверена.

Не требуется импортировать новый полный профиль, заменять геобазы или добавлять всю Россию в DIRECT.

## Windows, TUN и Docker: границы доказательств

Официальные документы Happ указывают, что Sniffing определяет домен из SNI/Host первых пакетов и по умолчанию включён. Также упоминают меньшую вероятность конфликтов Docker у gvisor, но это не подтверждает необходимость смены TUN-режима на этой машине. Основание: [управление приложением](https://www.happ.su/main/ru/dev-docs/app-management.md), разделы Sniffing и «Режим TUN».

Предположение: распознавание домена позволяет применить DirectSites к HTTPS-запросу контейнера независимо от общего процесса worker. Специальной гарантии Happ для Docker Desktop/WSL2 + Windows Xray TUN в изученных официальных источниках не найдено. Не подтверждены фактические Sniffing, DomainStrategy, тип подписки и пересечения правил пользователя.

До приёмки остаётся проверить интерфейс текущего профиля и после пользовательского изменения — один обычный запрос Контур и один embeddings-запрос из radar worker. Это не выполнено в рамках исследования. Изменение VPN и Reconnect требуют отдельной явной инструкции пользователя по его правилам; исследование такого разрешения не создаёт.

Установленный Happ4.3.0.610 и включённый adapterhapp-xray подтверждены чтением Win32_Process/Get-NetAdapter. DNS api-zakupki.kontur.ru на момент проверки дал46.17.203.73. Неавторизованный GET `/external/v1/limitGroups` из Windows и из существующего bervel-worker-radar-1 завершился URLError; HTTP-ответ не получен. Ключ не использовался, лимит поиска/полных карточек не расходовался. Не выполнено ни одного изменения правил, DNS, адаптеров, профилей или подключения.

Официальная [документация Docker Desktop](https://docs.docker.com/desktop/features/networking/) подтверждает, что внешний TCP/IP-трафик Linux-контейнеров Windows идёт через com.docker.backend.exe. Поэтому исключение этого процесса затронуло бы оба назначения. DirectSites действует по назначению, что соответствует задаче; применимость на конкретном подключении остаётся проверить после изменения пользователем. Простой `NO_PROXY` не является подтверждённым решением для текущего TUN-перехвата: доменное правило нужно на уровне фактического маршрутизатора.
