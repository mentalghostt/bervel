# Предварительный отбор тендеров — исследование и предлагаемый алгоритм

05.11.2026. Основание: новый запрос пользователя; вызовы боевого Контур API запрещены. Исследованы локальная OpenAPI-схема, текущий клиент и симулятор. Проведён диагностический опыт только на двух независимых экземплярах симулятора в контейнере `--network none`; работающие сервисы и их квоты не изменялись.

## 1. Что нужно оптимизировать

Цель — максимизировать число пригодных и соответствующих каталогу карточек на ограниченное число подробных запросов. Полнота и релевантность — разные признаки: полная закупка молока не нужна заводу, подходящая закупка болтов с закрытыми характеристиками недостаточна для уверенного анализа.

Текущий клиент смотрит до трёх страниц и загружает первый необработанный ID; межстраничного ранжирования нет. Предлагается сначала собрать большой пул кратких записей, затем ранжировать его и лишь после этого расходовать бюджет подробных карточек. У исходной API-выдачи нет подтверждённого порядка по полезности для нашего завода. [Разбор контракта](2026-11-05-ai-radar-prefilter-contract.md), `src/bervel/modules/ai_tender_radar/infrastructure/kontur.py:229–258`.

**Принципиальное ограничение:** search не содержит объектов закупки, характеристик, цен строк или сроков поставки. До card эти сведения недоступны. Поэтому обещать 200 полных пригодных карточек за 200 card-запросов нельзя. Целевой показатель — выход годных на бюджет; неполные кандидаты сохраняются с причинами, но не входят в готовую подборку. [Первичные поля и ограничения](2026-11-05-ai-radar-prefilter-contract.md).

## 2. Что показал HTTP-опыт

Скрипт: `.dev/local/ai-radar-prefilter-2026-11-05/probe.py`; числа и SHA256 исходников: `probe-result.json` рядом. Профиль содержит три семейства синтетического каталога — болты, гайки и шайбы. Оба варианта получили одинаковые 3 000 уникальных brief из 60 страниц (из найденных 3 582), затем загрузили ровно по 200 полных карточек. Ранжировщик видел только заголовок/сниппеты, ID использован только для стабильного разрешения равенства. Эталон вычислялся отдельно после фиксации выбора и в ранжирование не поступал.

| Показатель из 200 карточек | Порядок API | Простое ранжирование заголовка/сниппетов |
|---|---:|---:|
| Полные требования по текущему нормализатору | 183 | 161 |
| Полные требования и цены позиций | 162 | 132 |
| Полный состав относится к синтетическому каталогу | 73 | 140 |
| Одновременно целевой состав и доступные цены | 68 (34%) | 132 (66%) |
| Подтверждённый график поставки | 0 | 0 |

Число полезных по ограниченной метрике выросло на 64, в 1.94 раза. При этом общая техническая полнота снизилась: **ранжирование релевантности само по себе не является фильтром полноты**. В просмотренном пуле эталон знает 1 025 карточек, проходящих ограниченную проверку, но это скрыто от алгоритма до detail. Из-за отсутствующих сроков поставки ни одну из них нельзя объявить готовой к полному производственно-экономическому решению.

Дополнительный контрпример: один и тот же brief получен от двух вариантов карточки — с нормальным составом и с пустым `JointObjects`. Search-ответы побайтно равны, результаты проверки полноты различаются. Любой алгоритм, видящий только brief, вынужден обращаться к полной карточке, чтобы различить эти варианты.

**Границы опыта:** это сравнение двух порядков одного поискового пула, а не проверка нового продукта, LLM или реального Контура. Локальная семантика OR и морфологии не подтверждает API-семантику. Ограничение частоты выключено только для ускорения диагностического опыта; лимиты по 200 запросов сохранены. Порядок корпуса и явные названия упрощают задачу. Проверка цен не включает все коммерческие условия, НДС и расходы; нельзя называть 132 полностью готовыми тендерами.

## 3. Предлагаемый конвейер

### A. Снимок профиля, бюджета и поисковых условий

Вход — активный каталог завода, включённые экспериментальные продукты, подтверждённые наименования/синонимы, стандарты и атрибуты. Нулевой остаток не исключает товар из поиска. Экспериментальный интерес не означает производственную возможность.

Зафиксировать время начала `T`, диапазон публикации и открытый этап закупки. Срок подачи заявки используется только для доступности участия, не как срок производства. По умолчанию сохранять неизвестную цену (`MaxPriceNone`) и валюту среди кандидатов, пока полная карточка не проверена. Ограничения региона/закона/цены применяются только из настроек пользователя.

Отдельные бюджеты `B_search`, `B_detail`, модельных вызовов и документов. `B_detail≤min(200, доступный остаток группы)`; 200 — целевой лимит этого продукта, не универсальная гарантия API. Чтение `limitGroups` предусмотрено для разрешённого источника; текущая работа обращалась только к симуляции. У существующего `_request` нужно разделить типизированные ответы object и array: limits возвращает массив. Локальный учёт отправленных/неопределённых попыток общий для ключа и не позволяет параллельным прогонам обещать один и тот же остаток; после 429 запросы приостанавливаются с причиной, бюджет не обнуляется самостоятельно.

### B. Поиск множеством веток с обязательным широким охватом

Сначала хотя бы одна широкая ветка для каждого активного семейства; затем точные «семейство + стандарт» и подтверждённые синонимы. Отсутствующий стандарт в названии не основание исключать товар. Не использовать только точные ветки: реальные требования могут лежать в документах, а название быть общим.

Стартовая политика распределяет 40% поискового бюджета широким веткам, 60% точным; неиспользованный остаток переносится. Это гипотеза для сравнения на симуляторе. Первые страницы распределяются по кругу, затем приоритет получают ветки, дающие больше новых перспективных ID на запрос; 20% оставшихся поисковых вызовов продолжает обход менее представленных веток. Если веток больше бюджета, фиксировать непроверенные семейства.

Параметры каждой ветки фиксируются, `PageNumber` последовательно растёт, записи объединяются по `Id`, сохраняются все ветки/страницы происхождения. Search ограничен 50 элементами и глубиной 10 000 результатов в сохранённом контракте. При превышении глубины делить диапазон дат на неперекрывающиеся логические окна; если API границы включительные, дедуплицировать совпадения. Не тратить вызовы на заведомо недоступную страницу. Если разделить временное окно дальше нельзя, честно отметить усечение. Изменение выдачи между страницами тоже исключает обещание полного снимка базы.

### C. Дешёвый рейтинг и осторожное AI-переранжирование

Сначала правила: валидный ID, отмена, явный закрытый этап, подтверждённо просроченная подача и дубли. Такие кандидаты можно исключить с точной причиной. Общий заголовок, отсутствие сниппета/цены или слово «ремонт» не являются достаточным основанием: бывает поставка с монтажом и товар в смешанной закупке.

Дешёвый рейтинг использует семейство в названии, точные указанные атрибуты, сниппеты и контекст поставки/услуги. Упоминание крепежа только при обслуживании понижает приоритет. Несовпадение явно указанного стандарта понижает соответствующую ветку, но не исключает другие товары смешанной закупки. ID, ordinal и скрытые поля симулятора запрещены как признаки.

LLM получает ограниченный пул `min(число кандидатов, 5×B_detail)` (при бюджете 200 — до 1 000): лучшие по дешёвому рейтингу плюс неопределённые и недопредставленные семейства. На пакет — не более 20 brief и лимит токенов модели. Структурированный ответ: `candidate_id`, `relevance=strong|possible|weak`, `matched_product_ids`, цитаты из title/snippets и `uncertainty`. Код проверяет ID и цитаты. Модель не может выдавать `requirements_complete=true` без полной карточки; её уверенность не трактуется как вероятность.

На подробные запросы стартово выделяются 80% мест верхней очереди и 20% — сомнительным/разнообразным кандидатам. Это защищает от самоусиливающегося отбора только очевидных названий. При сбое LLM доступен детерминированный рейтинг с пометкой деградации; неопределённые не объявляются неполными или нерелевантными. Сравнить такой вариант с одним детерминированным рейтингом и оставить LLM только при измеримом улучшении выхода годных за её стоимость.

### D. Полные карточки и три независимых допуска

Загружать уникальные ID по очереди, небольшими партиями до 20 с сохранением прогресса. Запросы последовательные с консервативным ограничением частоты; отдельные счётчики attempts/success/failure и журнал неизвестного исхода. Кэш первичного ответа допустим лишь по области доступа/источнику и проверенной свежести; для нового источника старые карточки не переиспользуются молча.

После загрузки:

1. **Requirements:** полный обязательный состав, количества/единицы, видимые обязательные характеристики, согласованность сводного и заказческого состава. `#####` в реквизитах не равно скрытым требованиям. Разрешённая инструкция участнику выбрать значение отличается от маскированного обязательного значения. Общая карточка с неполным обязательным лотом не проходит.
2. **Economics source:** достаточные сведения о цене/валюте/условиях для выбранного способа расчёта. Общая НМЦ не распределяется произвольно по строкам. Если подтверждена только общая цена, допустима общая экономика при известной стоимости всего объёма, но стоимостные веса строк для score-v1 остаются неизвестными; нужен отдельный валидный режим политики, а не выдуманные цены.
3. **Schedule:** подтверждённое окно исполнения/поставки, включая относительный срок от события. `ApplicationDeadline` и `CommissionDeadline` его не заменяют. `StartContractDate`/`EndContractDate` — текстовые поля условий договора и требуют проверки смысла. При необходимости LLM извлекает условия из доступных документов с цитатами; неизвестная дата начала остаётся неизвестной.

Каждый допуск даёт `complete|incomplete|unknown` с путём источника. Общая готовность к оценке требует полного набора данных для текущей версии расчёта, а не просто пустой `limitations`. Дополнительно точный товарный matching проверяет каталог. Нехватка склада, низкая маржа и нехватка мощности — бизнес-результаты, а не неполнота источника: такие полные карточки остаются в выдаче с причиной/баллом. Неполные сохраняются в истории и отдельном списке «Недостаточно данных».

При исчерпании 200 detail-запросов выдать фактически пригодные N карточек; не подменять их неполными для красивого числа. UI показывает краткие записи, уникальных кандидатов, загруженные detail, полные/неполные/неизвестные, нерелевантные, лимит и причину остановки. Профильные материалы текущего завода проверяются отдельно: полная карточка API не гарантирует полноту заводской себестоимости/мощностей.

## 4. Что требуется от симулятора перед приёмкой

Текущий корпус годится для разведочного опыта, но не для приёмки нового конвейера. Исправить shape `Lots[].Price`; добавить корректные условия поставки/оплаты и локальные документы, варианты без `Snippets`, независимые маскировки/отсутствия данных. Точные расхождения и schema-ссылки перечислены в [контрактном исследовании](2026-11-05-ai-radar-prefilter-contract.md).

Набор должен содержать: нейтральные заголовки с целевым товаром в документах, услуги с сильными совпадениями, поставку с монтажом, смешанные лоты, разные языки/морфологию, близкие несовместимые размеры, нулевой склад при известном производстве, экспериментальные позиции, обязательные неизвестные данные. Перемешивать порядок/ID независимо от целевого статуса и полноты; фиксировать seed и дату. Эталон не отдаётся HTTP-клиенту и не попадает в промпт.

Для каждого варианта — новый изолированный экземпляр симулятора с одинаковым корпусом, бюджетами и профилем API. Сравнить: порядок API, дешёвый рейтинг, гибрид с LLM, гибрид с резервом неопределённых. Это анализ альтернатив, не обещание, что сложный вариант обязательно лучше.

## 5. Измерение и обязательные проверки

- `detail_precision@200`: полные по трём допускам и релевантные / реально запрошенные подробные карточки. Отдельно: техническая полнота, релевантность и готовность именно к score-v1.
- `yield`: число пригодных карточек; запросов search/detail и LLM-токенов на одну пригодную; время до первой пригодной и до завершения.
- `recall_in_pool`: найденные пригодные / известные пригодные в просмотренном размеченном пуле. Отдельно recall среди всего размеченного корпуса, соответствующего фильтрам. Ни одна из этих метрик не является полнотой реального Контура.
- Покрытие каждого семейства и включённой экспериментальной категории; число пригодных, потерянных дешёвым отсечением и выбором пула LLM. При гипотезах о весах — обучение/подбор на одном наборе, приёмка на отдельном.
- Обязательные тесты: 0/50/51/10 000/>10 000 результатов; дубли/смена порядка; повтор и восстановление после каждой страницы/карточки; 429/403/тайм-аут/неопределённый исход; остаток меньше 200; отсутствие сниппетов; неправильный shape limits; фальшивые модельные ID/цитаты; запрещённый production URL до сетевого вызова.
- Проверка квот и лимита частоты запускается отдельно с включёнными ограничениями. Для детерминированных тестов LLM заменяется фиксированным ответом; для приёмки AI-переранжирования нужен отдельный опыт настоящей модели на тех же синтетических brief через шлюз с доступом только к локальным материалам. Боевой Контур не требуется ни для одной проверки.

До калибровки нельзя назначить достоверный универсальный процент precision. Приёмочный минимум: ноль ложных `complete` на контрольных неполных кейсах; все специально заданные существенные положительные случаи найдены при достаточном бюджете; бюджеты не превышены; гибрид превосходит порядок API по yield на отложенных сценариях и не уступает дешёвому ранжированию, иначе сложность LLM-переранжирования не принимается. Изменения ранжирования не обходят ни один жёсткий допуск полноты.
