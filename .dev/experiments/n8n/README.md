# Эксперимент этапа 2 ядра: n8n

Одноразовый измерительный стенд на искусственных данных. Он не является кодом приложения, не реализует ядро и не должен импортироваться из приложения. Основание — [принятая спецификация](../../docs/architecture/12-core-v0.1-spec.md), разделы 6–9. Пользователь выбрал n8n для первого эксперимента; выбор промышленного движка остаётся отдельным решением.

## Состав

- `package.json`, `pnpm-lock.yaml`: закреплённые зависимости n8n 2.43.5.
- `launch.py`: параметры тестового n8n и запуск его CLI; серверные модули Open Server не запускает.
- `workflows.py`, `workflow-v1.json`, `workflow-v2.json`: искусственная цепочка загрузки, публикации, ожидания HTTP-подтверждения и завершения. Вторая версия меняет наблюдаемую семантическую метку.
- `observer.py`: независимый HTTP-приёмник и журнал SQLite. Каждая попытка публикации учитывается; по одному ключу публикуется один эффект, а изменение тела вызывает конфликт. Эта защита принадлежит стенду, а не n8n.
- `test_observer.py`: проверки измерительного стенда.
- `probe.py`: реальные вызовы n8n и преднамеренные остановки только созданных им процессов n8n. PostgreSQL и Redis не останавливает.
- `followup.py`: дополнительные проверки штатного ручного повтора и публикации через аутентифицированный API интерфейса n8n. Это диагностика выпуска, а не стабильный контракт адаптера приложения.
- `manual_recovery.py`: продолжение по выбору пользователя — обнаружение аварии, два одновременных повтора, сохранение исходной схемы после публикации новой и конфликт изменённого результата.

Данные, ключ шифрования n8n, журналы и кэш пакетов находятся в исключённой из Git `.dev/local/core-stage-2/`. Секреты не включаются в отчёт. Redis использует базу №15 и префиксы `bervel-core-stage-2`/`bervel-core-stage-2-bull`; команды очистки общей БД Redis не используются. PostgreSQL: отдельные БД `bervel_core_spike_n8n` и роль `bervel_n8n_spike` без административных полномочий. Серверные модули включает пользователь.

## Проверяемые вопросы

| ID | Воздействие | Наблюдение |
|---|---|---|
| OR01 | Остановить n8n main и worker во время ожидания человека, запустить их заново | Сохраняется ID исполнения; до ответа завершения нет, после ответа оно одно |
| OR02 | Повторить подтверждение и отдельно команду запуска с тем же входом | Отдельно посчитать исполнения, попытки и эффекты; определить владельца защиты от дублей |
| OR03 | Записать эффект, задержать HTTP-ответ на 45 секунд и принудительно остановить worker | Проверить автоматическое продолжение после запуска worker; сохранить состояние при отказе |
| OR04 | Сохранить ожидание v1, опубликовать v2 и перезапустить n8n | Старый запуск завершается с меткой v1, новый — с меткой v2 |

Готовность HTTP health-проверки сама по себе не означает, что n8n закончил запуск worker и регистрацию webhook. Стенд ждёт готовности этих компонентов перед началом проверок.

## Воспроизведение

Для этого закреплённого пакета нужен Node.js 24 или выше согласно его `engines`; эксперимент выполнен с Node.js 24.19.0. Для другого выпуска совместимость проверяется заново. Требуются доступные PostgreSQL 17 и Redis, отдельная тестовая БД и роль с правом создавать таблицы внутри неё. На испытанной локальной БД разрешены соединения тестовой роли без пароля; это свойство окружения эксперимента, а не требование к установке заказчика.

1. Установить закреплённые зависимости локально в этой папке, направив кэш и store менеджера пакетов в `.dev/local/core-stage-2/`. Текущий lock-файл получен pnpm 11.25.0; установка выполнена с `--ignore-scripts`.
2. Задать `SPIKE_PG_HOST` и `SPIKE_REDIS_HOST` адресами уже работающих тестовых сервисов; при необходимости также `SPIKE_PG_PORT`, `SPIKE_REDIS_PORT`, `SPIKE_NODE_PATH`. Пути Open Server в коде запуска не используются.
3. Из корня репозитория выполнить `python .dev/experiments/n8n/workflows.py` и `python .dev/experiments/n8n/launch.py import:workflow --input=.dev/experiments/n8n/workflow-v1.json`.
4. Выполнить `python -m unittest discover -s .dev/experiments/n8n -p test_observer.py -v`.
5. Выполнить `python .dev/experiments/n8n/probe.py`. Перед повторным прогоном снова импортировать v1: проверка OR04 оставляет опубликованной v2.

Для дополнительных проверок задать `SPIKE_PSQL_PATH` путём клиентского `psql` и выполнить `python .dev/experiments/n8n/followup.py`. Этот сценарий создаёт только тестовую учётную запись `core-spike@example.invalid` в отдельном n8n; пароль находится в локальном файле окружения и не выводится. Импорт n8n меняет ID версии: сценарий разрешает фактические ID по содержимому тестовой истории. Если `.dev/local/core-stage-2/owner.env` удалён при сохранённой БД, для повторного входа потребуется восстановить тестовый пароль либо подготовить новый изолированный стенд.

Для продолжения ручного профиля после импорта v1/v2 и подготовки учётной записи выполнить `python .dev/experiments/n8n/manual_recovery.py` с теми же переменными окружения. Сценарий активирует версии штатным API, создаёт свежие искусственные аварии и останавливает только свои процессы; результаты первого прогона не переписывает. Четыре сценария и выводы — в [дополнительном отчёте](../../docs/quality/core-stage-2-n8n-manual-report.md), данные — в [manual-results](../../docs/quality/core-stage-2-n8n-manual-results.json). Успех MR02 означает измерение поведения двух запросов и сохранение одного эффекта приёмником, а не единственную попытку восстановления в n8n; успех MR04 означает ожидаемое отклонение конфликта.

Во время прогона порты 5688 (n8n), 5689 (стенд), 5679/5680 (внутренние task broker) должны быть свободны. Стенд не завершает чужие процессы, занявшие порт. В конце созданные им процессы останавливаются. Сервисы, БД и история остаются для проверки.

Результат — [машинный отчёт](../../docs/quality/core-stage-2-n8n-results.json). Прохождение OR02 не означает автоматическую защиту n8n от повторного запуска: этот факт вынесен в отдельное поле отчёта. Подтверждение в стенде искусственное; права пользователя, корпоративный вход, OCR, модели, предметные схемы, нагрузка, отказ БД/Redis и промышленное восстановление здесь не проверяются.

Выводы, диагностические ошибки и ограничение способов публикации — в [отчёте этапа 2](../../docs/quality/core-stage-2-n8n-report.md). Ожидаемые отрицательные наблюдения OR03/OR04 сохраняются как `fail`; сценарий не превращает их в успешные ради общего результата и не утверждает выбор движка.
