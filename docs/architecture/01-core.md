# Общее ядро

Статус: предлагается. Ядро предоставляет технические возможности обоим модулям и не интерпретирует характеристики крепежа.

Уточнение от 14 октября 2026: форма модульного монолита принята владельцем разработки. Конкретные контракты и гибридное стандартизированное хранение описаны в [спецификации v0.1](12-core-v0.1-spec.md), подготовленной для приёмки этапа 1. Этот документ сохраняет исходное описание; при реализации учитывается указанное уточнение границ.

## Владение и интерфейсы

| Компонент | Ответственность | Не владеет |
|---|---|---|
| identity-access | Аутентификация, области данных, разрешения на действия | Техническим соответствием изделия |
| module-registry | Манифест, версия, совместимость, конфигурация модуля | Произвольной загрузкой недоверенного кода |
| workflow | Запуск, ожидания, отмена и восстановление процесса | Формулами экономики |
| revisions | Снимки входов, версии результатов, зависимости актуальности | Истиной о ценах в 1С |
| approvals | Запрос проверки, решение по редакции, срок действия | Самостоятельным решением участвовать |
| model-gateway | Разрешённые модели, проверка схем, квоты, учёт вызовов | Достоверностью технического заключения |
| audit | История изменений и происхождение фактов | Неограниченным хранением конфиденциальных промптов |
| external-actions | Реестр разрешённых внешних действий и их сверка | Гарантией однократной доставки у любого провайдера |

## Единица работы

ProcessRun с идентификатором, модулем, версией процесса, ссылками на снимок входов, состоянием и сроком. В истории оркестратора фиксируется исполнение; в прикладной БД - бизнес-решения и результаты. Согласованность обеспечивается устойчивыми идентификаторами и сверкой; история оркестратора не заменяет журнал бизнес-решений.

Предварительные состояния: QUEUED, RUNNING, WAITING_DATA, WAITING_REVIEW, READY, COMPLETED, FAILED, CANCELLED. Они описывают исполнение; решение «отказаться» в радаре является отдельным бизнес-результатом.

## Согласование

Вход: субъект, редакция, действие, снимок исходных данных, правила, срок действия.
Выход: Approval с проверяющим, решением и обоснованием.
Перед внешним действием повторно проверяются полномочия, активная редакция, актуальность данных, адресат и документ. Изменение проверяемого содержимого требует новой редакции и, если нужно по политике, нового согласования.

Одновременное редактирование контролируется номером редакции. Одобрение устаревшего номера отклоняется. Автоматически перенести старое одобрение на новый результат нельзя.

## Манифест модуля

Поля: module_id, version, core_api_compatibility, dependencies, permissions, configuration_schema, workflow_types, event_types, owned_data, health_checks. Регистрация проверяет совместимость. Отключение запрещает новые запуски; текущие задания завершаются или отменяются по явной политике, сохраняющей историю.

## Вызов модели

Контракт включает цель, разрешённый класс данных, версию промпта, ожидаемую схему, доказательства, предел ресурсов и идентификатор операции. Ответ валидируется по схеме, затем прикладными правилами. Корректная схема не доказывает фактическую верность. При ошибке - ограниченный повтор, явное состояние и ручной путь.

Смена модели/промпта требует проверки качества. Fallback допускается только к заранее разрешённой модели для соответствующих данных и задачи.

## Внешние действия

Бизнес-изменение и запись намерения в outbox создаются в одной транзакции. Обработчик получает intent_id и устойчивый ключ операции. При известном успехе сохраняет внешний ID. При неизвестном результате переводит операцию в UNKNOWN и сначала сверяет внешнее состояние. Если API не даёт гарантии идемпотентности/сверки, нужен ручной разбор; нельзя обещать «ровно один раз».

## Готовность ядра

- Повтор команды не создаёт второй процесс.
- Перезапуск обработчика не теряет подтверждённые результаты.
- Старое согласование не разрешает новый документ.
- Сбой одной очереди не блокирует кабинет.
- Действия по чужой области данных запрещены.
- Неоднозначный внешний результат виден оператору.
