# Первый проверочный сценарий ядра BERVEL v0.1

Дата: 14 октября 2026. Сценарий `CORE-V01`. Статус исполнения приложения: `not_run`. Основание: [спецификация ядра](../architecture/12-core-v0.1-spec.md).

## Цель и входы

Проверить, что ядро сохраняет разные типы материалов в общем формате, поддерживает редакции и согласования, а второй модуль подключается без правок внутренних механизмов ядра. Прикладные обработчики в этом сценарии простые и детерминированные; внешняя модель и реальные системы завода не требуются.

[Искусственные примеры](core-v0.1-examples.json) содержат два CSV в UTF-8, два манифеста, наборы ожидаемых записей и точные ссылки на схемы. Это тестовые данные без сведений заказчика. CSV здесь выбран для проверяемости источника; промышленное распознавание других форматов проверяется отдельно.

Участники: оператор области `test-area-a`, проверяющий той же области и сотрудник области `test-area-b`. Учебные разрешения действуют только на стенде и не заменяют матрицу прав завода R10.

Модули:

- `demo.document-review`: читает строки спецификации, сохраняет название и количество, передаёт результат сотруднику. Не определяет техническое соответствие или производимость.
- `demo.stock-import`: читает складскую выгрузку, сохраняет SKU, склад, количество и время наблюдения. Не утверждает действующие остатки и не создаёт резерв.

## Основная последовательность

1. Зарегистрировать `demo.document-review` с диапазоном API ядра `>=0.1.0`, `<0.2.0` и схемой `demo.document-review.requirement-row@1.0.0`.
2. Загрузить первый CSV из примеров с ролью `test_fixture`. Сохранить оригинальные байты, checksum, область и `ArtifactRevisionRef`.
3. Запустить `demo.document-review.parse@1.0.0` с точной редакцией файла, редакцией конфигурации `1` и устойчивым ключом команды.
4. Обработать две строки. У первой количество `10 piece`; у второй исходная ячейка пустая, поэтому `state=UNKNOWN`, `value=null`. Источник количества — строка и колонка конкретного CSV.
5. Опубликовать первую редакцию набора: две записи, `quality_state=PARTIAL`, происхождение и замечание `MISSING_QUANTITY`. Частичный результат доступен как частичный.
6. Сотрудник открывает результат и исходную ячейку. Проверяющий принимает действие `demo.document-review.accept-extraction` с замечанием об неизвестном количестве. Это принятие извлечённых фактов, а не одобрение поставки или производства.
7. Загрузить новую редакцию того же искусственного материала с заполненным количеством второй строки `4`. Получить вторую редакцию набора; первая остаётся неизменной. Старое одобрение не разрешает действие по второй редакции.
8. Подключить `demo.stock-import`: добавить проверенный пакет, манифест и схему `demo.stock-import.stock-row@1.0.0`, не меняя внутренние компоненты ядра и базовые таблицы результатов.
9. Загрузить второй CSV и сохранить складской набор: `SKU-TEST-001`, `WH-TEST`, `3.500 kg`, наблюдение `2026-10-14T08:00:00Z`. Время загрузки не заменяет время наблюдения.
10. Прочитать точные редакции обоих наборов через `DatasetService.read`; прочитать исходники через `ArtifactService.read`. Наличие разных `payload` не меняет конверт и проверку доступа.

## Ожидаемые результаты и сбои

| Проверка | Условие | Ожидаемое поведение |
|---|---|---|
| CV01 | Первая загрузка и обработка | Байты восстанавливаются; количество и ссылки совпадают с примерами |
| CV02 | Пустое количество | `UNKNOWN` и `null`, замечание и `PARTIAL`; ноль не подставляется |
| CV03 | Повтор той же команды с тем же ключом | Те же ID запуска и результата; второй переход или редакция не создаются |
| CV04 | Тот же ключ с другим входом | `IDEMPOTENCY_CONFLICT`; второй вход не теряется под видом повтора |
| CV05 | Падение после фиксации результата до подтверждения | Повтор находит сохранённый результат; публикация не дублируется |
| CV06 | Старый обработчик завершился после новой редакции | Не заменяет текущую редакцию и её состояние |
| CV07 | Принято извлечение первой редакции | В аудите видны сотрудник, редакция, действие и замечание; внешней отправки нет |
| CV08 | Новая редакция после проверки | Старое одобрение не применяется к новой; старая редакция читается точно |
| CV09 | Два сотрудника меняют одну версию состояния | Один переход; второй получает явный конфликт |
| CV10 | Чтение сотрудником `test-area-b` | Нет содержимого, закрытых метаданных, источников или ссылки на объект |
| CV11 | Те же байты в другой области | Дедупликация хранения не расширяет доступ и не объединяет дела |
| CV12 | Второй модуль и складская схема | Новый payload хранится через тот же контракт; ядро и общие таблицы результатов не меняются |
| CV13 | Неизвестная схема или изменение схемы под той же версией | Публикация отклоняется; существующая схема и наборы не переписываются |
| CV14 | Количество строкой `неизвестно` вместо предусмотренного `null` | Ошибка схемы; результат не публикуется как валидный |
| CV15 | Сбой в середине записи большого набора | Подготовка не видна как опубликованная редакция; прежняя рабочая редакция сохранена |
| CV16 | Неподдерживаемый формат обработки | Оригинал сохранён после допустимого приёма; отсутствие извлечения явно показано |
| CV17 | Смена версии схемы с новым полем | Регистрируется новая версия; старые данные читаются своей схемой; старому читателю новая версия не подставляется автоматически |
| CV18 | Повтор загрузки старого склада | `observed_at` не меняется на время загрузки; положительная свежесть без политики не объявляется |
| CV19 | Отключение модуля с ожидающим процессом | Новые запуски запрещены в `DRAINING`; история сохранена, текущий процесс завершается либо явно отменяется |
| CV20 | Политика источника запрещает доступ, который раньше был разрешён | Производный результат не раскрывает закрытый источник через текст, API или экспорт |

CV01–CV20 являются планом проверки будущего приложения. Проверка структуры JSON-примеров и документации не означает выполнения этих сценариев.

## Что предъявлять при реализации

Оригиналы и их checksum; два набора с версиями схем; историю первой и второй редакций; аудит проверки; результаты повторов, конфликтов и отказов доступа. Для доказательства расширяемости — перечень изменений при подключении второго модуля: новый пакет, манифест, схема и состав сборки, без изменений внутренних компонентов ядра.

Если новый модуль требует собственной предметной таблицы, её миграция проверяется отдельно. Сценарий добавления складского формата проверяет расширение результатов; он не доказывает, что полноценная складская бизнес-модель обходится без миграций.
